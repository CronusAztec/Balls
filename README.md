# JumpingBallsLive – satisfying ball physics simulator

JumpingBallsLive is a full-featured, editable, free, browser-based
bouncing-ball physics simulator that exports vertical MP4 clips for TikTok, Reels and Shorts.

Built with **Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · next-intl**.
Everything runs client-side: physics, rendering, audio and video encoding happen in the visitor's browser.
The site is exported as plain static files, so it deploys to **GitHub Pages** (workflow included) or any
static host – no server required.

## Getting started

```bash
npm install
npm run dev        # http://localhost:3000 (plus the base path, if set) → redirects to your browser's language, /en by default
npm run build      # static export into ./out (+ 404.html and .nojekyll for GitHub Pages)
npm start          # serves ./out the way GitHub Pages does (base path, 404 page, trailing slashes)
```

Copy `.env.example` to `.env.local` to configure the build. Everything is optional for local development:

- `NEXT_PUBLIC_BASE_PATH` – sub-folder the site is served from (`/Balls` on `https://user.github.io/Balls`, empty for a root deployment).
- `NEXT_PUBLIC_SITE_URL` – public URL used for canonical links, hreflang, sitemap and Open Graph, including the base path. Defaults to `http://localhost:3000` plus the base path.
- Feedback channel, first one set wins: `NEXT_PUBLIC_FEEDBACK_ENDPOINT` (an endpoint that accepts a cross-origin JSON POST, e.g. Formspree, Basin or your own worker with CORS enabled), `NEXT_PUBLIC_FEEDBACK_EMAIL` (opens the visitor's email app) or `NEXT_PUBLIC_GITHUB_REPO` (opens a prefilled GitHub issue; needs a public repository with Issues on, and visitors need a GitHub account).
- `NEXT_PUBLIC_ANALYTICS_SCRIPT_URL` / `NEXT_PUBLIC_ANALYTICS_SITE_ID` – load a privacy-friendly analytics script (Plausible, Umami, Rybbit…).

`next build` reads `.env.local`; so do `npm start`, `npm run smoke` and `npm run previews` (for `NEXT_PUBLIC_BASE_PATH`),
so a base-path build previews correctly at `http://localhost:3000/<base path>/`. You can also pass it explicitly:
`npm start -- --base /Balls` and `BASE_URL=http://localhost:3000/Balls npm run smoke`.

Other scripts:

```bash

npm run lint                               # eslint

## Deploying to GitHub Pages

The repository ships with `.github/workflows/deploy.yml`:

1. **Enable Pages once**: repository *Settings → Pages → Build and deployment → Source: GitHub Actions*.
   The workflow cannot do this for you; until it is done the *deploy* job stops with a message saying so.
   Private repositories need a paid GitHub plan (Pro, Team or Enterprise) for Pages; public repositories work on
   the free plan.
2. **Push to the default branch** (or run the workflow manually from the *Actions* tab). Every push is linted,
   type-checked, unit-tested and built; pushes to the default branch are then published.
3. The site appears at `https://<user>.github.io/<repo>/` – for this repository
   `https://cronusaztec.github.io/Balls/`. The workflow reads the site URL from the repository's Pages settings
   on every run (falling back to that conventional URL while Pages is off) and builds with the matching base path.

**Feedback form**: on a public repository with Issues enabled the deployed form opens a prefilled GitHub issue
(visitors need a GitHub account). On a private repository, or to use another channel, set a repository
*Variable* (Settings → Secrets and variables → Actions → Variables): `FEEDBACK_ENDPOINT` (a form endpoint that
accepts a cross-origin JSON POST, e.g. Formspree) or `FEEDBACK_EMAIL`. Until one of these applies the form
tells visitors that no channel is configured. `ANALYTICS_SCRIPT_URL` and `ANALYTICS_SITE_ID` variables are passed
to the build the same way.

**Custom domain**: set it under *Settings → Pages → Custom domain* and point its DNS at GitHub Pages. For
Actions-based deployments GitHub ignores a `CNAME` file; the workflow picks the domain up from the Pages settings
and builds for the domain root (no base path) on the next run.

**Other static hosts** (Netlify, Cloudflare Pages, S3, nginx…): run `npm run build` with `NEXT_PUBLIC_SITE_URL`
set and upload `out/`. Point the host's "not found" page at `404.html`.

`.github/workflows/smoke.yml` builds the site under a base path and runs the browser smoke test on pull
requests and on demand.

### How the static export works

- `next.config.ts` sets `output: "export"`, `trailingSlash: true` (every page is `route/index.html`) and
  `basePath` from `NEXT_PUBLIC_BASE_PATH`.
- There is no middleware: `src/app/(static)/page.tsx` is the root page and redirects to the visitor's language
  in the browser (with a `<meta refresh>` fallback), `src/app/(static)/404/` is the localised not-found page
  and `scripts/postexport.mjs` copies it to `out/404.html`.
- `src/lib/site.ts` exposes `assetPath()` for `/public` files referenced from plain `<img>`/`fetch()` calls (Next's
  `Link`/`Image` add the base path on their own) and `pageUrl()`/`absoluteUrl()` for canonical, Open Graph and
  sitemap URLs.
- The feedback form talks to its channel directly from the browser (`src/components/site/FeedbackForm.tsx`).

  lib/project.ts        project files (.jumpingballslive.json): build, versioning / migration, validation · shareCode.ts (short ?c= share codes) · base64.ts
```

## How to extend it

### Add a setting
1. Add the field and its default to `SimulatorSettings` / `defaultSettings()` in `src/lib/settings.ts` (and a range in `RANGES` if it is numeric).
2. Optionally give it a short URL key in the `*_URL_KEYS` maps so it is shareable.
3. Render a control in `src/components/simulator/Controls.tsx` (use the `Slider`, `Toggle`, `ColorPicker` helpers from `ControlPrimitives.tsx` and wrap it in `Searchable` with a label key so the search box finds it; add the key to `SECTION_KEYS`). A bigger feature gets its own component in `src/components/simulator/sections/` that Controls.tsx renders inside the right section (see `SongSlicerSection.tsx`, which also exports its search keys).
4. Add the label + tooltip to every `messages/*.json` under `Controls`.
5. Apply it: either read it in `Canvas.tsx` (visual) or forward it to the engine in an effect in `Simulator.tsx` (physics).

### Add a game mode
1. Create `src/lib/physics/modes/<name>.ts` implementing `GameMode` (see `types.ts`; `classic.ts` is the minimal example, `portal.ts` a complete one, `drop.ts` a mode without rings built out of obstacles, `box.ts` a mode that owns its playfield entirely and folds the balls back in `onBallStep()`, `pendulum.ts` one whose motion is analytic – it overwrites every ball's position from the simulation clock in `onBallStep()` and solves its sound events inside each step). Use `ctx.random()` for randomness so the seed finder stays deterministic. Optional flags: `ballsMayRest` (no slow-ball boost), `ballsPassThrough` (no ball-to-ball collisions).
2. Register it: add the id to `MODE_IDS` in `types.ts`, instantiate it in `engine.ts` and add a case to `initMode()` (`activateMode()` takes the ring layout: `"classic"`, `"single-gap"`, `"solid"`, or `"none"` for a mode that builds its own playfield).
3. Draw anything mode-specific in `Canvas.tsx` (segments, overlays, HUD counters); obstacles are drawn for every mode. A mode that draws its own entities gets a small module next to the canvas (see `boxRenderer.ts`) and a branch in the ball pass.
4. Add the card order and the family (`MODE_CARD_ORDER`, `MODE_CATEGORIES`: `escape` or `rhythm`; the mode cards are grouped under a heading per family) in `src/lib/modes.ts`, names/descriptions in `messages/*.json` (`Modes`, `Controls.mode<Name>`, `Editorial.mode<Name>`), and a preview image in `public/modes/<name>.webp` (add the mode to `scripts/generate-mode-previews.mjs` and run `MODES=<name> npm run previews` against the served build).
5. Mode settings that the finder needs go into `ModeSettings` in `src/lib/simulation/finder.ts` and `createEngineForSettings()`, and a fingerprint of the new mode's default run into `tests/extras.test.ts`, so the physics extras are proven not to disturb it. A mode whose run cannot finish with some settings says so in `runNeverFinishes()` (the page then hides the finder and `findSimulation()` resolves with `endless` instead of searching); a mode whose run length is fixed by its settings whatever the seed (Pendulum Wave: cycles × cycle length) reports it in `fixedRunDurationSec()`, so the finder resolves with `fixedDuration` and the page explains what to change instead of testing seeds.

### Physics extras
`src/lib/physics/extras.ts` holds the optional forces and wall behaviours: `airDrag` (fraction of the velocity lost per 60 Hz step), `windX` / `windY` (acceleration as a fraction of the ball speed per second), `spinStrength` (wall contact spins the ball by the no-slip condition against the – possibly rotating – wall, `contactSpin()`, and a Magnus-style force `spinStrength × MAGNUS_COEFFICIENT × spin × (−vy, vx)` curves the flight; the integrated angle rotates custom ball images and emoji in `Canvas.tsx`), `wallBounciness` (restitution multiplied into every rebound speed, also the ones a mode sets itself), `breathingAmplitude` / `breathingSpeed` (wall radii pulse as `base × (1 + amplitude · sin(2π · speed · t))`) and `rotatingGravity` (degrees per second the gravity vector turns, starting straight down). They are part of `PhysicsConfig` (`PhysicsExtras` in `types.ts`), so they reach the engine through `engine.setConfig()` and the finder through `createEngineForSettings()` like every other physics value; `resolvePhysicsExtras()` fills in the defaults and clamps to `PHYSICS_EXTRA_RANGES`, which `RANGES` in settings.ts spreads for the sliders and the URL/preset validation.

The engine applies them in `update()`: drag once per fixed step, the gravity direction, wind and spin terms per sub-step, the contact spin and the restitution in `processWallCollisions()`. Each extra is skipped entirely at its default, so a run without extras takes the original code path and `tests/extras.test.ts` checks every mode against a trajectory recorded before the extras existed, plus determinism with all of them on. Breathing walls mutate `wall.radius` in place around the base radii the engine keeps in `wallBaseRadii` (`syncWallBaseRadii()` runs after every wall (re)assignment, including `ctx.setCircularWalls()`, and `setConfig()` restores the base radii before a mode rebuilds its walls), so gaps, modes and the renderer follow the pulse without knowing about it. The pulse is applied once per **sub-step** (the last sub-step lands exactly on the step's end time, so frames and `setConfig()` see the same radii as a per-step pulse would give) and the engine remembers where every wall was before the move in `wallPrevRadii`; the first collision pass of each sub-step then *sweeps* each wall over that move – the ball's side is judged against the previous radius and the hit test is one-sided (`outer >= radius` for a ball that was inside, `inner <= radius` for one that was outside), so a wall that jumped across the ball is still a hit, pushed back to the side it came from, and a gap that swept past the ball's centre counts as a pass. At the widest and fastest pulse the outer wall moves up to ~24 px per step in an 800×600 arena, more than the ±(ballRadius + 2) hit window, which is why both are needed; later passes of the collision loop use the plain current-radius test so push-outs and portal teleports are never re-judged against a stale sweep. Modes can read the unpulsed radii and the resolved extras through `ctx.getWallBaseRadii()` / `ctx.getPhysicsExtras()`: Grow caps the ball at the trough of the pulse (`base × (1 − amplitude) − 2`) instead of the live radius, so the ring never shrinks under a ball that outgrew it (and every step it holds a ball that a Ball Size change or a deeper keyframed pulse put above that cap back to it). To add another extra: add the field to `PhysicsExtras`, `DEFAULT_PHYSICS_EXTRAS` and `PHYSICS_EXTRA_RANGES`, apply it in the engine behind an "is it at its default?" check, give it a URL key in `NUMERIC_URL_KEYS`, a slider in `components/simulator/sections/PhysicsExtrasSection.tsx` (with its search key in `BALL_PHYSICS_EXTRA_KEYS` / `WALL_PHYSICS_EXTRA_KEYS` and the section defaults in `sectionDefaults()`), the label + tooltip in every `messages/*.json`, and add it to the finder-invalidation dependency list in `Simulator.tsx`.

### Ball interactions (merge, split, pass)
`src/lib/physics/interactions.ts` holds the "what balls do to each other" setting and its pure maths. `ballInteraction` is `bounce` (the classic equal-mass rebound), `merge`, `split` or `pass`; `splitMinRadius` (4–20 px) and `maxBalls` (2–64) limit the splitting. Like the physics extras, the three values travel inside `PhysicsConfig` (`BallInteractionConfig` in `types.ts`), so they reach the engine through `engine.setConfig()` and the finder through the copied config; `resolveBallInteraction()` fills in the defaults and clamps, `ballInteractionOf()` picks them out of the settings, and `RANGES` spreads `BALL_INTERACTION_RANGES`. With the default the engine takes exactly its old code path, so existing seeds and links behave as before.

- **Merge**: `handleBallCollisions()` runs the pair loop; in merge mode `mergeBallPair()` fuses two balls that overlap while approaching each other (balls that merely drift apart – e.g. freshly spawned at the same point – are left alone, as a bounce would leave them). `mergeBalls()` gives the result: mass ∝ area, so the merged ball has radius √(r₁² + r₂²), sits at the mass-weighted centre, keeps the total momentum and wears the mass-weighted blend of both colours (`blendColors()`; a non-hex colour wins by weight). The first ball of the pair becomes the merged one (keeping its id, trail and lifetime), the second is removed; a `merge` sound event and a burst of `burst` particles (glowing dots in the ball's colour, drawn by `Canvas.tsx`) follow. The merged size is kept relative to the Ball Size (`radiusScale` = radius ÷ `ballRadius`), so a Ball Size change – the slider or a keyframe – scales the merged ball instead of shrinking it back to a plain ball (`setConfig()` sets every ball to `ballRadius × radiusScale`). With a forced winner in play (rigged outcomes) a merge that absorbs the chosen team's ball hands the merged ball to that team, so the chosen team never drops out of its own race.
- **Split**: whoever breaks a wall reports it with `ctx.reportWallBreak(ball, wallIndex)` next to its `gap` sound event – the engine's own gap pass (Classic), Multiply's escape detection and Shatter's segment breaks do. In split mode the ball is queued and `flushSplits()` runs at the end of the step, after the rebound / escape bookkeeping and outside every loop over the balls (one split per ball per step). `canSplit()` checks the limits (both halves at least `splitMinRadius`, fewer than `maxBalls` balls) and `splitBall()` computes the halves: radius r/√2 each, side by side across the flight direction, each with the parent's velocity plus an equal and opposite sideways push, so the pair keeps the parent's momentum while diverging by 40–72° (the only random number, drawn from `engine.random()`). The parent becomes one half (keeping id, trail, lifetime and spin), the other is a new ball – both keep their size relative to the Ball Size (`radiusScale`), so a Ball Size change scales the halves instead of growing them back; a mode copies per-ball state to it in the optional `onBallSplit()` hook – Multiply marks the half of an escaped ball as escaped too, so it flies out with its parent instead of counting as a new escape and spawning another wave. A `split` sound event and a spark burst follow.
- **Pass**: the pair loop is skipped.

The sounds live in `src/lib/audio/interactionTones.ts` (`ToneGenerator.playInteraction("merge" | "split")`: a low sinking sine and a high rising triangle, on the beat grid and snapped to the scale like every other sound, ducking the music bed). The panel block – the bounce / merge / split / pass switch and the two split sliders, shown in the two-ball modes – is `components/simulator/sections/BallInteractionSection.tsx`, which exports its search keys; the settings are `ballInteraction` (URL `bi`), `splitMinRadius` (`smr`) and `maxBalls` (`mb`), and a mode change resets them like the physics extras. `tests/interactions.test.ts` covers the maths (radius, momentum, colour, caps), the engine behaviour in every mode that reports breaks and determinism. To let another mode split its ball, call `ctx.reportWallBreak()` where it breaks a wall and, if it keeps per-ball state, implement `onBallSplit()`.

### Obstacles and Ball Drop
`src/lib/physics/obstacles.ts` is a generic obstacle layer: an `Obstacle` is a `circle` (a peg: centre, radius) or a `segment` (a bar: centre, half-length, angle, optional `angularVelocity` in rad/s around its centre, optional `thickness`), each with a `restitution` (fraction of the approach speed kept) and a `friction` (fraction of the sliding speed lost per contact). Factories: `circleObstacle()`, `segmentObstacle()`, `segmentBetween(x1, y1, x2, y2)` for walls and floors; `segmentEndpoints()` writes a bar's ends into a caller-owned object so the renderer never allocates. The maths is pure and deterministic: `resolveBallObstacle()` pushes the ball out, reflects the normal component of its velocity (relative to the surface velocity of a spinning bar, so a bar can fling a ball) with the restitution, applies the friction and returns the approach speed of the contact (−1 when there is none). Both resolvers look at where the ball came from (`position − velocity × dt`): a fast ball that crossed a thin bar or passed a peg's centre within one sub-step is bounced back to the side it came from instead of popping out on the far side.

The engine keeps the list (`ctx.setObstacles()` / `engine.getObstacles()`, cleared with every mode init) and, in every sub-step after moving a ball, resolves it against every obstacle before the ring walls (`handleObstacleCollisions()`); `advanceObstacles()` turns spinning bars first. The wall-bounciness extra scales the obstacle restitution like every other rebound. A contact whose approach speed is at least `OBSTACLE_HIT_SPEED` (40 px/s, raised under heavy gravity to three times the speed one sub-step of gravity adds, so a resting ball never "hits" its support) is reported to the mode through the optional `GameMode.onObstacleHit(ctx, ball, obstacle, index, impactSpeed)` hook, which may return `{ frequency, suppressSound, suppressGlow }`; the engine then queues a `"hit"` `SoundEvent` carrying that `frequency` (without a hook or frequency the innermost-wall tone plays) and remembers the contact in `getObstacleHits()` for the glow. `ToneGenerator.playWallHit(wallIndex, frequency?)` plays a pitched hit like any other: snapped to the scale, on the beat grid, a hit sample transposed to it (`hitSamplePlaybackRate(wallIndex, pitchByWall, frequency)`), a loaded melody still taking precedence. `Canvas.tsx` draws every obstacle in the wall colour (per-obstacle hue in rainbow-gradient mode) with the `GLOW_LAYERS` halo on recent hits, and the reactive background flashes on obstacle hits too. Two small per-ball fields support all this: `Ball.gravityScale` (a per-ball gravity multiplier, 1 when absent – the engine multiplies it into the gravity term, which leaves every other mode's numbers bit-identical) and `Ball.radiusScale` (the ball's size relative to the configured radius, so `setConfig({ ballRadius })` keeps a size spread). A mode whose balls may come to rest sets `readonly ballsMayRest = true`; the engine then skips the slow-ball boost that keeps a ball moving in the ring modes.

**Ball Drop** (`src/lib/physics/modes/drop.ts`, id `drop`) is built entirely out of obstacles: `buildDropLayout(width, height, rows, ballRadius, loop)` lays out a portrait playfield that uses the full canvas height and fits the centred square the recorder crops to, closed by a left, a right and (unless raining) a bottom wall – the side walls continue `WALL_EXTENSION` (one) canvas height above the top, clipped by the canvas edge, so a pile that outgrows the board stays between them – with `rows` staggered rows between the top and the floor – every third row bars instead of pegs – spaced so the biggest ball of the size spread fits between two pegs and past the ends of a bar. `init()` sets the obstacles and releases the first ball; `onPreUpdate()` releases ball *k* at *k × spawnInterval* seconds at a random x along the top (a spot still taken by another ball waits for the next step, so balls never spawn inside each other), each with its own `radiusScale` (±75 % of the ball size at full size variation, never below 3 px) and `gravityScale` (½×–2× at full gravity variation, log-uniform). `onObstacleHit()` returns `dropHitFrequency(ball.radius)` – 5280 / radius Hz, i.e. the 8 px default ball plays E5 and bigger balls play lower, clamped to A2–A6 – and caps the queued sounds at `MAX_HIT_SOUNDS_PER_STEP` per step. The run is finished when every ball has been released and none has moved more than `REST_DISTANCE` (3 px) during a `REST_TIME_MS` (1 s) window (positions rather than speeds, because a resting ball still jitters by one sub-step of gravity; where a ball rests does not matter, a pile may reach above the top). A board that cannot hold every ball (40 balls of size 30, say) is not left waiting forever: `releaseDue()` reports a due release that found no free spot at the top, `onPreUpdate()` times how long that has been going on (`blockedMs`) and once it has lasted `REST_TIME_MS` while the pile is at rest, the board counts as full – the run finishes with the balls it holds and `getProgress().total` (the SETTLED! banner, the finder) reports that number instead of the setting; with **rain** (`loop`) the floor is left out, a ball that fell below the canvas re-enters at the top (fresh trail, spread over a band above the top) and the run never finishes, so the seed finder is hidden. Ball-to-ball collisions are damped to `BALL_TO_BALL_RESTITUTION` (0.6) in `onBallCollision()`, right after the engine's elastic pair rebound, so a pile settles instead of a cradled ball rocking forever. Safety net: a ball whose centre was shoved across a wall or floor line by another ball is put back inside in `onPostSubStep()`, so the run can still finish. A live change of the ball size re-spaces the board on the next step; a canvas resize rebuilds it in `onConfigChange()`. The settings are `dropBallCount` (URL `dbc`, 1–40), `dropSizeVariation` (`dsv`), `dropGravityVariation` (`dgv`), `dropRows` (`drows`, 3–12), `dropSpawnInterval` (`dsi`, 0–2 s) and `dropLoop` (`dloop`); `resolveDropSettings()` clamps them (URL parameters and presets alike), `engine.setDropSettings()` applies them on the next `initDrop()`, `Simulator.tsx` restarts the board when one of them changes (like Target does), the finder receives them in `ModeSettings.drop`, and the panel block is `components/simulator/sections/BallDropSection.tsx` (rendered in the Mode row, and in the Ball section while the settings search is in use, so the search box finds it). `tests/obstacles.test.ts` covers the collision maths (push-out, restitution, friction, end caps, thickness, tunnelling, spinning bars, the restitution cap and scale) and `tests/drop.test.ts` the settings, the pitch mapping, the layout counts, the release schedule, the per-ball sizes and weights, the sound events, settling (default, heavy-gravity, big-ball and overfull boards, including that a slow schedule or a burst is never mistaken for a full board), rain, the rescues, live changes and determinism; the smoke test drives the controls, the URL and a run with size-pitched sounds in the served export. To use obstacles in another mode, build them with the factories, hand them to `ctx.setObstacles()` in `init()` (and again in `onConfigChange()` when the size changed) and, if the mode wants its own pitches or silence, implement `onObstacleHit()`.

### Bouncing Shapes (box arena)
`src/lib/physics/modes/box.ts` (id `box`) is the project.jdm "DVD logo / count down from 60" format and the template for a mode that owns its playfield: it activates with the `"none"` ring layout, lays a box out with `buildBoxField(width, height, aspect)` (a rectangle of the given aspect fitted into the centred square the recorder crops to), spawns its shapes as ordinary engine balls (the engine integrates them, so gravity, drag, wind and the recorder work unchanged) and, in `onBallStep()`, folds every ball that crossed a wall back inside with `reflectAxis()` – a mirror reflection of the overshoot, so the motion is exactly the straight line a perfect reflection gives and the bounce period `(box − size) / speed` never drifts, whatever the step size. `ballsMayRest` switches the slow-ball boost off and `ballsPassThrough` the pair loop, so the shapes fly through each other and nothing disturbs their rhythm.

- **Rhythm and tempo**: `speedFactors(ratio, count)` cycles the ratio's numbers over the shapes and normalises the fastest to the Ball Speed, so shapes at 2:3 hit the walls 2:3 times; every speed is then multiplied by the run's **tempo**, drawn from the seed within 1 ± `TEMPO_SPREAD` / 2 (0.85–1.15, exposed as `BoxView.tempo`). The ratios between the shapes stay exact, but the run length becomes a continuous function of the seed instead of one of five values (one per axis ratio), which is what lets Find Simulation land inside its ±0.5 s tolerance – with the default box a 30 s target is met by roughly one seed in eight; when the target is out of the band, the finder's "closest" message says by how much to change the countdown or the Ball Speed. A live Ball Speed change scales the velocities, so the tempo survives it. `launchAngle(innerW, innerH, p / q)` picks the direction so a shape's vertical and horizontal bounce periods are in the ratio `p : q` (an `AxisPeriodRatio`, drawn per run with `ctx.random()`; shared by every shape unless the speeds are equal, when each shape draws its own).
- **Corners**: a shape launched from the centre reaches a corner only when its axis ratio is odd/odd. Squares and circles draw from `AXIS_PERIOD_RATIOS` (2:1, 3:2, 4:3, 5:3, 5:2 – mostly even, so two notes rarely land on one hit); DVD logos draw from `DVD_AXIS_PERIOD_RATIOS` (5:3, 7:5, 3:1, 7:3, 9:5), so the accent is on the schedule of every seed: the first corner is the ((p + 1) / 2)-th side-wall hit and then there is one corner every `hitsPerCornerCycle()` = p + q − 1 hits (3 to 13). Growth would detune that within a cycle or two (each hit takes a little more room across than down), so the **corner lock** (`lockCorner()`, DVD logos without gravity) counts the hits into the cycle (`BoxShapeState.cycleX` / `cycleY`) and, after every hit, re-aims the logo with `cornerAimAngle()` – the one direction whose unfolded paths to the scheduled corner take the same time in both axes – keeping its speed. The correction is a fraction of a degree per hit; a schedule that would need a grazing angle (`MIN_AIM_ANGLE`, e.g. after a live change) restarts its cycle from where the logo is.
- **Sound**: every hit queues a `"hit"` `SoundEvent` with `frequency = BOX_WALL_NOTES[wall]` (top E5, right G5, bottom C6, left C5); the ToneGenerator plays a loaded melody's next note instead when there is one, snaps the pitch to the scale, transposes a hit sample to it and places it on the beat grid like any other hit. A DVD logo reaching a corner (both walls in one sub-step, or the second wall within `CORNER_REACH_SUBSTEPS` – predicted at the first hit, so the pair counts as one hit) sets `accent: true`, which `playWallHit()` turns into a louder, longer note (`ACCENT_GAIN`, `ACCENT_LENGTH`; hit samples get the gain) and the canvas into a full-screen flash.
- **Countdown, growth, colour**: each shape's `BoxShapeState` (hue, count, hits, last hit tick, growth scale) lives in the mode and is exposed through `engine.getBoxView()` (the same object every call; hit ages are sub-step ticks × `tickMs`, so flashes freeze with a pause and replay in recordings). A hit advances the hue by `HUE_STEP`, grows the shape by `growPerHit` % up to `MAX_SHAPE_FRACTION` of the box, and decrements the countdown; at zero the shape freezes (`frozen`, zero velocity and gravity) and the run finishes once every shape is done. `ball.radiusScale` keeps the shape's size right across `setConfig({ ballRadius })`, and `onConfigChange()` re-lays the box out on a canvas resize.
- **UI**: `components/simulator/boxRenderer.ts` draws the box (each wall glowing after its hit), the shapes (rounded squares, circles or a stylised DVD-style plate – a rounded rectangle with a disc motif, no trademark artwork – with the countdown number, hit flash, glow and trail) and the corner flash; the canvas mirrors `data-box-hits`, `data-box-corners` and `data-box-done` onto the element for the smoke test. The panel block is `sections/BoxArenaSection.tsx` (shape, count, speed ratio, countdown, growth, gravity, aspect). Settings: `boxShapeCount` (URL `bxn`), `boxShape` (`bxs`), `boxAspect` (`bxa`), `boxGravity` (`bxg`), `boxCountdown` (`bxc`), `boxGrowPerHit` (`bxgr`), `boxSpeedRatio` (`bxr`); `resolveBoxSettings()` clamps them for URLs and presets alike, and a change restarts the box like a Ball Drop change does. `tests/box.test.ts` covers the reflection, ratio and layout maths, the notes and accents, the countdown, determinism, the seeded tempo and the continuous run lengths the finder needs, the corner schedule of every DVD seed under growth (and the size of the lock's turns), the finder and the settings; the smoke test checks a DVD corner and a found 30 s seed in the served export.

### Pendulum Wave
`src/lib/physics/modes/pendulum.ts` (id `pendulum`) is the project.jdm pendulum-wave / phasing format and the template for a mode with **analytic motion**: it activates with the `"none"` ring layout, spawns one ordinary engine ball per bob (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`, so nothing in the engine moves them) and in `onBallStep()` overwrites every ball's position with the closed-form swing at that sub-step's time – no integration, no drift, bit-identical replays. The clock is the mode's own step counter (`steps × stepSec`, so consecutive steps share their boundary exactly) rather than the accumulated `elapsedMs`.

- **Tuning** (`pendulumFrequency()`): classic, fᵢ = (K + i) / T – pendulum *i* completes `baseOscillations` + *i* swings per `cycleSeconds`, the frequencies are 1 / T apart and the whole row is back in phase after exactly T (at T / 2 the odd and even bobs are on opposite sides – two groups; at T / 4 half the row crosses the centre together). **Phasing** keeps the same range of tempi but makes the swing *times* an arithmetic series (each bob's swing lasts a fixed bit longer than the next one's), so neighbours drift apart by a constant time lag per swing and the row never snaps back as a whole. `relativeLengths()` gives every bob L ∝ 1 / f² (the row's strings, the bouncers' heights) and `pendulumAngle()` is θ(t) = A cos(2π f t), the seed picking the side the row starts on and the direction the frame / polygon turns.
- **Layouts** (`buildPendulumField()` – the centred square the recorder crops to – and `buildPendulumRig()`, both pure): `row` hangs the bobs from a bar across the middle 40 % of the field and shortens the longest string so the outermost bob still fits at full swing ((0.3 S − r) / sin A, capped by the height); `arc` puts the pivots on a ring with every string hanging toward the centre; `circle` / `galaxy` move each bob along its own radius between ρ₀ ± ρ_A (the travel follows the amplitude up to ~30° and is capped at the rim and above the centre), `polygon` 3–8 maps the radius onto a polygon outline (`polygonRadius()`) that turns once per cycle and `galaxy` turns the whole frame once per cycle too; `sliding` stacks rails; `bouncing` stands the balls on a floor and lifts each by the rectified free-fall arc `bounceHeight()` = 4 H u (1 − u) of its own period, so every ball hits the floor at its frequency and the slow ones bounce highest. `placeBob()` is the one hot-loop function (no allocation) and the bob radius follows the Ball Size (`radiusScale`, capped by the spacing of each layout); a live size change or a canvas resize rebuilds the rig in place.
- **Sound**: `eventPhases()` says at which fractions of a swing a bob sounds (¼ and ¾ for the centre crossings, 0 and ½ for the extremes; the floor hit at 0 and the apex at ½ when bouncing) and `crossingTimes()` solves the exact event times inside each 60 Hz step (starting one index early and comparing strictly against the shared step boundary, so an event is never missed or doubled). Every event becomes a `"hit"` `SoundEvent` with `frequency = pendulumPitch(index)` – the bob's rank as a degree of C major from C4 over at most three octaves, low → high or high → low – which the ToneGenerator snaps to the chosen scale, plays with the instrument or the hit sample, places on the beat grid and lets a loaded melody override, like any other hit. With **wave chord** on, `groupChords()` merges events within `CHORD_WINDOW_SEC` (20 ms) into one event carrying `chord` (its distinct pitches, at most `MAX_CHORD_NOTES`) – a chord is only flushed once its window has closed, so one straddling two steps is still one chord – and a chord of at least `ACCENT_CHORD_FRACTION` of the row is `accent`ed. `ToneGenerator.playWallHit(wall, frequency, accent, chord)` voices every pitch of a chord at once (`hitPitches()`, `chordGain()` = 1 / √n, at most `MAX_CHORD_VOICES`; the sampler plays the clip once per pitch), in one beat-grid slot with one duck, while a melody still plays a single note. At most `MAX_PENDULUM_SOUNDS_PER_STEP` events leave one step; every note still flashes its bob.
- **Run, finder, UI**: the run finishes at `cycles × cycleSeconds` (the events of that instant are still queued, so the final alignment is heard; then the clock stops, so the row holds that alignment in silence under the end screen instead of swinging and sounding on) or never with `cycles` 0, which `runNeverFinishes()` reports; because the length is the same for every seed, `fixedRunDurationSec()` tells `findSimulation()` to resolve at once with `fixedDuration` when it misses the target and the page explains what to change (`Simulator.finderFixed`). `PendulumView` (`engine.getPendulumView()`, the same object every call) carries the field, the rig, the per-bob states (hue, frequency, pitch, last-note tick), the clock, the rotations and the counters; `components/simulator/pendulumRenderer.ts` draws the rig of the layout, the strings / radius lines / floor shadows, the bobs (rainbow by index, brightened for `NOTE_FLASH_MS` after a note, glow on request), the **trails** – `drawPendulumTrails()` samples every bob's path from the analytic swing (`placeBobAt()`, the same placement the mode writes into the balls) over the last `trailWindowSec()` of simulation time and strokes it in `TRAIL_BANDS` bands of falling opacity (a time constant of 0.12 + 3 · trails² s, drawn back to 2 %, within `MAX_TRAIL_POINTS` for the whole rig), so a trail is exactly the path taken whatever the frame rate or speed, fades out completely (an offscreen layer faded with `destination-out` would keep an 8-bit residue of every path forever), freezes with a pause and starts empty on a restart – and the screen flash of a big chord; the canvas mirrors `data-pendulum-notes`, `data-pendulum-chords` and `data-pendulum-cycles` onto the element. The panel block is `sections/PendulumWaveSection.tsx` (layout, polygon, count, base swings, cycle length, swing, phasing, trails, where a note plays, pitch direction, wave chord, cycles). Settings: `pwCount` (URL `pwn`), `pwBaseOscillations` (`pwk`), `pwCycleSeconds` (`pwt`), `pwAmplitude` (`pwa`), `pwLayout` (`pwl`), `pwPolygon` (`pwp`), `pwPhasing` (`pwph`), `pwTrails` (`pwtr`), `pwSoundOn` (`pws`), `pwPitchDirection` (`pwpd`), `pwWaveChord` (`pwch`), `pwCycles` (`pwc`); `resolvePendulumSettings()` clamps them for URLs and presets alike (a polygon of 1–2 sides is the circle) and a change restarts the rig like a Ball Drop change does – except the trails, which only change the drawing and follow live (`PendulumMode.setSettings()` applies them to `PendulumView.settings` at once; the mode itself always runs on the settings of its last init). `tests/pendulum.test.ts` covers the tuning maths, the crossing detection and chord grouping (including across step boundaries), the pitches, every layout staying inside the field for every count, amplitude and ball size, the mode in the engine (analytic positions, notes and chords, bouncing, cycles and the finish, the silent hold after it, live changes and the live trails, determinism, the per-step cap), the trails (window, sampling budget, the exact path, no residue), the finder and the settings; `tests/toneGenerator.test.ts` the chord dispatch (a hit sample that is not pitched by wall plays a chord once); the smoke test drives the controls, the URL, the fixed-length finder message, a run with scale-degree notes, a trails change mid-run and the silent finish in the served export.

### Metronomes & Polyrhythms
`src/lib/physics/modes/polyrhythm.ts` (id `polyrhythm`, family `rhythm`) reuses the Pendulum Wave mechanism for a mode that owns its playfield with analytic motion: it activates with the `"none"` ring layout, spawns one ordinary engine ball per voice (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`), computes every voice's position once per 60 Hz step in `onPostUpdate()` and pins the balls there in `onBallStep()`; `components/simulator/polyrhythmRenderer.ts` draws the stage and the voices from the mode's view in a branch of the canvas' ball pass, like `pendulumRenderer.ts` does.

- **Exact tempo arithmetic** (`buildTempoSeries()`): voice *i* ticks `a[i] / D` times per second with whole numbers `a` and `D` – harmonic: `a = 10 (i + 1)`, `D` = the cycle length in tenths of a second; custom: `a = 10 × ratio`; BPM steps: `a` = the tempo in tenths of a BPM, `D = 600`. The ticks of a voice inside step *s* are the whole numbers in [⌈s·a / 60D⌉, ⌈(s+1)·a / 60D⌉) (`ticksInStep()`, with the exact `ceilDiv()` / `floorDiv()`), its position the remainder of `s·a` modulo `2·60D` (`tickPhaseMod2()`), so nothing accumulates, however long the run or large the count. Every voice ticks together exactly at the multiples of `D / gcd(a)` (`alignmentsInStep()`) – that is the alignment, detected analytically, never by comparing floating-point times; a cycle is the cycle length (harmonic, custom) or the alignment period (BPM steps), and the run's last step is `finalStep()`.
- **Sound**: all ticks of a step become one `"hit"` `SoundEvent` – a note, or a `chord` of the ticking voices' distinct pitches (at most `MAX_STEP_PITCHES`, `MAX_ALIGN_PITCHES` on an alignment, spread evenly by `spreadPitches()`) – `accent`ed on an alignment or when a voice's k-th tick is a multiple of `accentEvery`. The ToneGenerator plays it like any other hit (instrument, scale snap, beat lock – one grid slot per step –, hit samples, melody, music-bed ducking). `polyrhythmPitch()` gives a voice the Pendulum Wave's scale degree by index, or its tempo ratio as a harmonic of C3 folded into four octaves – a harmonic or custom voice its own ratio (ticks per cycle, so `3,4,5` plays G4–C5–E5), a BPM-steps voice its tempo relative to the slowest voice.
- **Layouts** (`buildPolyGeometry()`, `placeVoice()`; pure, inside the centred square the recorder crops to, dot size from the Ball Size capped by the spacing): rings (polygons via `polygonRadius()` of the Pendulum Wave, turning once per cycle so a corner meets the dot at every tick), chords / semicircles (a triangle wave of the tick phase, `tickTriangle()`), metronomes (θ = A cos(π·ticks)) and the spiral (tick points on a one-turn spiral). The layout, arc style, polygons, accents, pitch mapping and numbers change live (`setSettings()` rebuilds the geometry and re-places the voices at the current step); the tempo settings and the cycles restart the run (`Simulator.tsx`). The seed only picks the direction the dots turn / the side they start on.
- **Finder, UI, tests**: `runNeverFinishes()` is true with the cycles at 0 and `fixedRunDurationSec()` returns cycles × cycle length, so the page says what to change (`Simulator.finderFixedPolyrhythm`) instead of testing seeds. The panel block is `sections/PolyrhythmSection.tsx` (Mode row; its keys are pushed into `SECTION_KEYS.ball` for the search box); the canvas mirrors `data-poly-voices`, `data-poly-ticks`, `data-poly-alignments`, `data-poly-cycles` and `data-poly-layout`. Settings: `prCount`, `prLayout`, `prArcStyle`, `prTempos`, `prCustom` (sanitised to digits and separators, parsed by `parseCustomRatios()`), `prCycleSeconds`, `prBaseBpm`, `prBpmStep`, `prPolygon`, `prAccentEvery`, `prPitchBy`, `prNumbers`, `prCycles`, resolved by `resolvePolyrhythmSettings()` for URLs and presets alike. `tests/polyrhythm.test.ts` covers the exact arithmetic, the three tempo series, tick and alignment detection against brute force, the pitches, every layout staying inside the field, the mode in the engine (positions, notes, chords, accents, the finish, live changes, determinism, 400 voices), the finder and the settings; the smoke test drives the controls, the URL, the fixed-length finder message, a run with alignments and scale-degree notes, a live layout switch, a pitch-by-ratio run (3:4:5 sounds G4–C5–E5) and 400 voices.

### Collision Playground
`src/lib/physics/modes/collide.ts` (id `collide`) is the template for a mode with **many interacting bodies**: it activates with the `"none"` ring layout, spawns its orbs as ordinary engine balls (so the engine integrates them – gravity via `Ball.gravityScale` = the playground's gravity, drag and wind apply – and pause, playback speed and the recorder work unchanged), opts out of the engine's O(n²) pair loop with `ballsPassThrough` and resolves the collisions itself:

- **Broad phase**: `src/lib/physics/spatialHash.ts` – a uniform grid (counting sort into typed arrays, reused every build, so it allocates nothing once warm) with a cell as wide as the largest contact distance; `collectContacts()` visits each cell and its four "forward" neighbours, so every pair of touching discs is found exactly once (`tests/collide.test.ts` checks it against brute force). `onPostSubStep()` rebuilds it every sub-step from the orbs' positions.
- **Narrow phase**: `COLLISION_ITERATIONS` (3) passes over the candidate pairs, alternating direction: overlap beyond `POSITION_SLOP` is pushed apart by inverse mass (`POSITION_CORRECTION`), approaching pairs exchange an impulse with the restitution; after each pass the orbs are put back inside the container, so a heavy pile pushes its neighbours rather than the wall. The container itself (circle or square, `buildCollideField()` in the centred square the recorder crops to) is resolved per ball in `onBallStep()`, with the restitution × the wall-bounciness extra. Masses are radius²; sizes are log-uniform (`sizeFactor()`, 1/3×…3× at full spread) and scaled so the orbs cover `COLLIDE_FILL` (30 %) of the container at the default Ball Size, capped at `COLLIDE_MAX_FILL`. A speed cap (`MAX_SPEED_FACTOR` × the ball speed) is only a safety net: an elastic gas keeps its energy exactly.
- **Sound**: every impact faster than a resting contact is offered to a per-frame budget of `MAX_SOUNDS_PER_FRAME` (12) slots that keeps the most energetic (½ μ v²) across every 60 Hz step the frame runs (one at 1×, up to eight and more at 8× or on a late frame); `flushPendingSounds()` – the optional `GameMode` hook `engine.consumeSoundEvents()` calls once per batch, i.e. once per rendered frame – queues them strongest first as `"hit"` events with `frequency = collidePitch(smaller radius)` – the run's size range mapped onto a C major pentatonic ladder from C3 (bigger = lower) – and `level = collideLevel(impact speed)`. `SoundEvent.level` / `ToneGenerator.playWallHit(…, level)` scale the loudness of one hit (voice, melody note or hit sample; `hitLevel()` clamps it), so the notes are soft and the texture stays musical under the scale snap, beat lock and music bed.
- **Variants**: squishy orbs store their last impact per body (`CollideView.impactTick / impactNx / impactNy / impactAmount`) and the renderer flattens them with `squashAt()` over `SQUASH_MS`; sync start places them with `syncGridPitch()` / `syncGridCells()` (the widest lattice that fits) and releases them together; the anti-collision switch (`onPostUpdate()` at `antiCollisionAt` seconds of simulation time) stops the pair solver, recolours the orbs and queues an accented chord; the ring variant keeps its bodies in `src/lib/physics/ringTrack.ts` – arc positions and velocities on a circular track, 1-D collisions between neighbours in a fixed cyclic order (they cannot overtake), contact at the chord distance (`contactArc()`), optional tangential gravity – and places the balls from it every sub-step.
- **UI**: `components/simulator/collideRenderer.ts` batches the orbs by hue bucket (one path per colour, `HUE_BUCKETS`), draws short motion streaks, the glow, impact sparkles, squashed orbs as ellipses, lollipop sticks, the container glow and the anti-collision flash and caption; the circle container is wall 0 of the Wobbly Walls (`containerBounce()` logs every impact that sounds through `ctx.recordWallContact()`, `drawCollideArena()` traces the circle through the `WobbleLayer`), so the Visual section offers the slider for it; the canvas mirrors `data-collide-bodies`, `data-collide-collisions`, `data-collide-notes` and `data-collide-anti`. The panel block is `sections/CollisionPlaygroundSection.tsx`. Settings: `cpCount` (URL `cpn`), `cpSizeSpread` (`cpsz`), `cpContainer` (`cpc`), `cpGravity` (`cpg`), `cpRestitution` (`cpe`), `cpSquishy` (`cpsq`), `cpSyncStart` (`cpsy`), `cpAntiCollisionAt` (`cpac`), `cpRing` (`cpr`); `resolveCollideSettings()` clamps them, a change restarts the playground, `runNeverFinishes()` reports the mode as endless and `createEngineForSettings()` builds it from `ModeSettings.collide`. `tests/collide.test.ts` covers the spatial hash, the ring collisions, the helpers, the mode in the engine (energy, piles, sound budget, pitch, squash, sync start, anti-collision, ring, live changes, determinism, finder) and the settings; the smoke test runs 300 orbs for 5 s at 30+ fps in headless Chromium and checks that 8× playback still starts at most 12 notes per frame.

### Glass Smash
`src/lib/physics/modes/glass.ts` (id `glass`) is the first mode of the Boris family (the borisbounces formats) and combines the owned-playfield pattern of Bouncing Shapes with the obstacle layer of Ball Drop and a camera of its own:

- **Level** (`buildGlassLevel(width, height, settings, ballRadius, random)`, pure): a portrait shaft (`buildGlassField()`, `SHAFT_ASPECT` 0.62) filling the height of the centred square the recorder crops to; its height is the layout unit ("view height"). The stages are stacked below each other in world pixels – stage 0 starts at the top of the field, the rest continue below the canvas – each with a top pad for the ball to fall in (and the banner), `stageRows(rows, s)` panes (the setting plus a third of it per stage, at most 30) spread over `PANE_ZONE` view heights (never closer than the ball needs) and `stageHp(hp, s)` hit points (one more every other stage, at most two more; `paneThickness()` grows with them). From stage 1 on a pane may get a hole (`stageHoleChance()`, wide enough for the ball, away from the walls), from stage 2 on it may slide (`stageMoveChance()`: 62 % of the shaft wide, a sine of 2.2–3.6 s on the simulation clock); the first pane of a stage is always whole. Below the last stage lies the HOME area: the ground and a doorway on a seeded side. `random` is the engine's generator; every pane draws the same three numbers whatever its kind, so one pane never shifts the next one's.
- **Physics**: the ball is an ordinary engine ball with `gravityScale` 0 – the mode integrates `glassGravity()` (3.2 view heights/s² × the Gravity setting, 0.3×–3×) itself in `onBallStep()`, so the audio-reactive engine gravity never touches it – and resolves the panes there with the obstacle layer's capsule maths (`resolveBallSegment()`; a pane is one segment, two around a hole, moved in `onPreUpdate()` when it slides). The shaft walls and the ground are ordinary engine obstacles (`buildGlassObstacles()`), drawn by the canvas in the wall colour with the wall glow; `onObstacleHit()` keeps the walls silent and lets the ground thud (C3). Any contact from above is a landing, however slow – a graze on the end of a hole's glass, a sliding pane lifting the ball onto its top – so the ball never comes to rest on unbroken glass (the capsule maths alone would only damp its bounce there and the run would never end); a knock from below needs `HIT_SPEED`. A landing cracks the pane and re-launches the ball to the stage's hop height (`GlassStage.bounceHeight`: 0.8 × the pane spacing within 0.06–0.15 view heights, × the seeded tempo², so the pulse quickens as the panes get denser and the run length varies continuously with the seed) with a small seeded sideways kick; a knock from below cracks it too. The last hit point shatters the pane: `makeCrack()` / the shards are drawn from `ctx.random()`, the ball keeps `SHATTER_KEEP` of its speed and crashes through. Falling through a hole or past a sliding pane skips that pane (`cleared` without `shattered`); a pane above the ball can still be cracked from below. Once the ball lands on the ground it rolls to the door; in the doorway the run celebrates for `CELEBRATION_MS` (three confetti bursts) and then finishes.
- **Camera and stages**: `GlassView.cameraY` (world offset: screen y = world y − cameraY) eases toward `cameraTarget()` – the top of the stage the ball is in, following the ball down a stage taller than the view, or the ground at HOME – with `CAMERA_TAU` on the simulation clock and is clamped so the ball never leaves the field. Entering a stage sets `bannerStage` / `bannerAtMs`. Everything is advanced per 60 Hz step, so a pause freezes it and a recording replays it.
- **Sound**: a crack queues a `"hit"` with `frequency = glassPitch(stage, row)` (the row as a C-major degree from C4, each stage two degrees higher, folded into two octaves), which the ToneGenerator plays as the next melody note, the instrument voice or the transposed hit sample, snapped to the scale and on the beat grid like every other hit; a shatter queues the same note with `accent: true` (louder and longer – the hit-sample accent path) plus a `"gap"`, i.e. the wall-break sound, and the page wide-eyes the ball characters on it. `modeWallBreakSound()` (`src/lib/audio/songs.ts`, `MODE_WALL_BREAK_SOUNDS`) makes the new `glass` clip – synthesised by `scripts/generate-sounds.py` (`glass()`: a high-passed noise crash, a thump and a shower of inharmonic tinkles) and listed in `WALL_BREAK_SOUNDS` so any mode can pick it – the wall-break sound of this mode while none is chosen; `Simulator.tsx` applies it and the Sound section names it ("Mode default (Glass)"). HOME plays an accented C-major chord. At most `MAX_GLASS_SOUNDS_PER_STEP` notes leave one step.
- **Drawing** (`components/simulator/glassRenderer.ts`): `applyGlassCamera()` scrolls the canvas' camera transform (the mode's camera owns the view: Camera Follow and the cinematic camera's zoom and shake step aside), so the obstacle walls, the ball with its face and name, the trails and the particles scroll with the level; `drawGlassWorld()` draws the stage markers, the rails of sliding panes, the panes (tinted per stage, bright top edge, glints, a frost that thickens with the damage, a flash per hit), the cracks (one path, each grown over `CRACK_GROW_MS`) and the doorway with its roof and HOME sign (warm light once the ball is home); `drawGlassShards()` the shards (a fixed pool in typed arrays, bouncing off the shaft walls); `drawGlassOverlay()` the stage dots and the "STAGE n" banner in screen space. Only what is in view is drawn and the colours are cached per hue. The canvas mirrors `data-glass-stage`, `data-glass-stages`, `data-glass-hits`, `data-glass-shattered`, `data-glass-panes`, `data-glass-home` and `data-glass-camera`; the HUD shows "HOME!" with the pane count at the end.
- **Settings and UI**: `glassRows` (URL `glr`, 3–30), `glassHp` (`glhp`, 1–5), `glassStages` (`gls`, 1–10), `glassMoving` (`glm`), `glassHoles` (`glh`) and `glassGates` (`glg`, see below); `resolveGlassSettings()` clamps them for URLs and presets alike, a change restarts the shaft (`Simulator.tsx`), the finder builds it from `ModeSettings.glass`. The panel block is `sections/GlassSection.tsx` (Mode row; its keys are pushed into `SECTION_KEYS.ball` for the search box) with a line that sums the run up. A canvas resize rescales the whole level, the ball, the cracks, the shards and the camera onto the new field (`rescale()`).
- **Multipliers** (boris-multipliers, `src/lib/physics/multipliers.ts`): the ball's stat multipliers act on the glass too – `hitDamage()` takes that many hit points off a pane per hit (clamped at 0; `paneDamage()` – the hit points lost – sizes the cracks and the frost), a speed multiplier k runs the whole flight k× faster (`glassTempo()`: the mode's gravity × k², the hops, kicks and the walk to the door × k, so the ball flies the same arcs faster and the notes come quicker) and size grows the ball. With **Multiplier Gates** on (`glassGates`, URL `glg`, off by default) `buildGlassGates()` lays a row of three gates – x2 DMG, x1.5 SPEED, x1.25 SIZE (`GLASS_GATE_FACTORS`), in a seeded order drawn after everything else, so the glass is the same with or without them – across the shaft `GATE_Y` view heights below the top of every stage, under its banner and over its first pane. The ball's centre falling through a row picks the slot under it (`gateSlotAt()`, once per row, in `onPostSubStep()`); the multiplier is stacked at the end of the step through `ctx.getMultipliers().apply()` – the run's cap, the HUD badges, the adaptive sub-steps, which `markTouched()` switches on from the first step when the level has gates – with the rising arpeggio; a size gate never grows the ball beyond the room the panes and holes of the stages left leave (`glassMaxBallRadius()`, at most `MAX_BALL_OF_SHAFT` of the shaft). `drawGlassGates()` draws the rows (a tinted band and the label per slot; the slot taken flashes and stays lit, the others dim), the canvas mirrors `data-glass-gates`, and the Ball section's Multipliers group (the cap) shows in Glass Smash while the gates are on.
- **Tests**: `tests/glass.test.ts` covers the settings (URL, presets, ranges), the progression helpers, the pitches, the shard counts, the level (determinism, stacking, holes and slides only where they belong, everything inside the shaft), the cracks (determinism, inside the glass, never across a hole, longer with damage), the mode in the engine (gravity, crack/shatter state and its sounds, the hop height, a run through every stage to HOME with its banners and camera, the ball kept in the shaft and in view, sliding panes, exact replays, a resize mid-run), the finder, the default wall-break clip, a slow touch from above counting as a landing (and the seeds that used to come to rest on a pane reaching HOME) and the multipliers (a x2 DMG ball breaks a 2-hit pane in one landing, a x2 SPEED hop takes half the time for the same height, the gate rows: layout, seeded order, each slot's multiplier at the end of the step with the arpeggio, the whole run deterministic, the size limit, the cap, a resize); `tests/extras.test.ts` holds its fingerprint. The smoke test (section 17) checks the preview and the clip, the URL and the controls, the search box, the finder, the Sound section's default, a default run at 30+ fps with scale-degree notes and the glass clip, a short run to HOME at 8× and a run with the gates on whose rows stack multipliers on the ball on its way HOME.

### Double Pendulum Harp & sparring
`src/lib/physics/modes/doublePendulum.ts` (id `doublePendulum`, family `rhythm`) owns its playfield like the other ring-less modes: it activates with the `"none"` ring layout, spawns one ordinary engine ball per bob (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`), integrates its chains once per 60 Hz step in `onPostUpdate()` and pins the balls to the bobs in `onBallStep()` (wind or spin never move them); `components/simulator/doublePendulumRenderer.ts` draws the strings and trails before the ball pass and the rods, bobs and hit flashes in a branch of it, like `pendulumRenderer.ts` does.

- **Integrator** (`src/lib/physics/pendulumChain.ts`, pure and allocation-free): a planar chain of 2 or 3 point masses on massless rods, angles from the downward vertical. The Lagrangian gives Σⱼ μᵢⱼ lᵢ lⱼ cos(θᵢ − θⱼ) θ̈ⱼ = −Σⱼ μᵢⱼ lᵢ lⱼ sin(θᵢ − θⱼ) θ̇ⱼ² − g μᵢᵢ lᵢ sin θᵢ (μᵢⱼ the mass hanging below rod max(i, j)), solved at every Runge–Kutta stage by Gaussian elimination (`solveSpd()`; the mass matrix is symmetric positive definite). Friction is the generalised force −kMθ̇ (`dampingRate()` turns the per-step loss `dpDamping` into k), so it can only remove energy. `ChainStepper` advances the chains in error-controlled sub-steps of the embedded Dormand–Prince 5(4) pair (`tryStep()` computes the fifth-order result and its error estimate without moving the chain, `acceptStep()` takes it, and the last stage is reused as the next step's first): a sub-step is at most an eighth of the 60 Hz step (`MIN_SUBSTEPS`), turns no rod more than `MAX_ANGLE_PER_SUBSTEP` (0.015 rad, so a bob's path between sub-steps is nearly straight for the string crossings), keeps the estimated error under `STEP_TOLERANCE` (1e-9; a rejected try is retried shorter) and is never shorter than 1/`MAX_SUBSTEPS` (1024) of the step, and the last one ends exactly on the step. The default rig takes about ten a step; a light bob over a heavy one is stiff – its light joint whips round at hundreds of rad/s for a few milliseconds – and gets hundreds of sub-steps where it whips (sizing the sub-steps from the rates at the start of a step alone let such rigs lose up to half their energy in two minutes). Every pendulum has its own stepper – only the two sparring pendulums are stepped together, their contacts need the same instant – and only the state decides, so a run stays deterministic. The model is one unit long with g = 9.81 × `dpGravity`; `buildDpField()` scales it into the centred square the recorder crops to, every length proportional to the side, so the physics – bob radii (`bobModelRadius()`, from the Ball Size and the bob's mass) included – is the same whatever the canvas size.
- **Start**: the three angles (`dpAngle1`–`dpAngle3`) or, with `dpRandomStart`, a seeded draw (the first rod 100°–170° to either side, the others anywhere). Every further pendulum sharing the pivot starts `BUTTERFLY_OFFSET_DEG` further on its last rod; sparring mirrors the start for the second pendulum and draws again (at most eight times) while the mirrored bobs would start inside each other (`mirrorOverlaps()`).
- **Harp**: `harpStringMidi()` samples the scale ladder (`harpLadder()`: the Sound section's scale from `harpBaseMidi()` across `dpOctaves`, a major scale while the scale is chromatic) evenly – the first string is the root, the last the root `dpOctaves` octaves up – and `buildHarpGeometry()` lays the strings over the reach (vertical) or around the centre (radial spokes outside a hub). After every sub-step `harpCrossings()` finds the strings each bob crossed: `crossedIndices()` counts the whole numbers a point passes in string-index space with half-open intervals, so a crossing is never missed or doubled across sub-step boundaries (the radial layout works on the unwrapped angle, outside the hub only). A pluck sets the string's `pluckTime` and `amp` (a re-pluck within `PLUCK_COOLDOWN_SEC` is silent); all plucks of a step go out as one `"hit"` `SoundEvent` – one note or a `chord` of at most `MAX_PLUCK_NOTES` distinct pitches, with the `level` of the fastest pluck (`pluckLevel()`) – so the ToneGenerator applies the instrument, the scale snap, the beat lock, hit samples, a loaded melody and the music-bed ducking. The strings, their layout and tuning, the trail and the end follow a change live (`setSettings()` re-tunes; the swing goes on).
- **Sparring**: the two pivots sit `SPAR_PIVOT_DISTANCE` apart; after every sub-step each pair of bobs of the two chains that overlaps and approaches exchanges an impulse along the line of centres (`collideBobs()`): the bobs' effective inverse masses nᵀJM⁻¹Jᵀn give the elastic impulse, applied to each chain's angular velocities as M⁻¹Jᵀp, so the kinetic energy is unchanged. A hit faster than `HIT_SOUND_SPEED` plays `sparHitPitch()` – the harp's root an octave down when hard, the fifth under the root when light, `accent`ed from `HIT_ACCENT_STRENGTH` – at most `MAX_HIT_SOUNDS_PER_STEP` per step, and is kept in the flash pool (`view.hits`).
- **Trails and drawing**: the last bob of every pendulum is sampled into a ring buffer (`TRAIL_CAPACITY` samples of x, y and time in model units, one per `TRAIL_MIN_PX` of travel, at most one per sub-step). `drawDoublePendulumTrails()` strokes the samples of the last `dpTrailSeconds` newest first in bands of one hue – the pendulum's rainbow at the band's time (`trailHue()`, a full turn per trail length), so the colours stay on the path – and one opacity and width falling to zero at the end (`trailFade()`): a trail fades out completely, freezes with a pause, survives a resize and needs no state between frames (the Visual section's Trails switch hides it too). A string bends by `stringDisplacement()` (a sine under an exponential decay, lower strings slower and longer), drawn as one quadratic curve; a bob flashes after its pluck; a hard hit flashes the screen (`drawDoublePendulumFlash()`). The canvas mirrors `data-dp-pendulums`, `data-dp-segments`, `data-dp-strings`, `data-dp-layout`, `data-dp-spar`, `data-dp-plucks`, `data-dp-hits`, `data-dp-drift` (the energy drift in ppm) and `data-dp-done`, and shows "TIME!" with the plucks, hits or seconds at the end.

### How a wall hit becomes sound
`ToneGenerator.scheduleHit()` dispatches every bounce in this order: the **song slicer** while it has a song to play, then the **hit sample** in `sample` mode once the clip is decoded, otherwise a **synthesised voice** – the next melody note (played with `melodyInstrument`, sine by default) or the wall tone (played with `instrument`), snapped to the chosen scale. A `SoundEvent` may carry its own `frequency` (Ball Drop pitches every hit by the ball's size); it replaces the wall tone's pitch and transposes the hit sample, and is snapped and beat-locked like any other hit. One with `melody: false` accompanies the tune instead of being a note of it (Paddle Keep-Up's walls, ceiling, misses and streak chime, the Beat Runner's crash): it skips the slicer and the melody – its own pitch with the bounce instrument, or the hit sample –, waits out no melody cooldown and fills a free beat-lock slot without taking it, so it never uses up or silences a note of the song (`playWallHit()` / `playMultiplier()` take it as their last argument). With the beat lock on, voices and hit samples alike are scheduled on the BPM grid and extra hits inside an occupied grid slot are dropped. Whatever path a hit takes, the sound that actually plays ducks the background music bed at its own scheduled time (see below). The Sound section of the panel follows the same order (bounce sound: mode, instrument or sample; melody; scale, root note and beat lock; song slicer; background music; wall-break sound), and controls that only apply in one mode – the sample picker, the melody instrument, the root note, the grid, the music mix sliders – are still rendered while the settings search is in use, so the search box finds them whatever the current mode is.

### Song slicer
The "each bounce plays the next bit of a song" format. `src/lib/audio/slicer.ts` holds the pure cursor arithmetic (`planSlice` picks the next slice, shortens the last one, wraps or stops at the end; `positionAt`, `sliceProgress`, `sliceCount`, `formatSongTime`) and is covered by `tests/slicer.test.ts`, which also drives a `SlicePlayer` through a fake `AudioContext` (next-bounce cut, pause/resume, switching off, reset); the smoke test checks the pause/resume position in the served export. `slicePlayer.ts` is the Web Audio side: it keeps the decoded `AudioBuffer` and the cursor, plays each slice through an `AudioBufferSourceNode` + `GainNode` with linear fades into the ToneGenerator's master gain (so recordings include it), fades out a slice that is still sounding whenever it is cut short (`stop()`: the next bounce, a pause, slicing switched off, restart, new song) and moves the cursor to the point where it was cut, so the song always continues from there and the HUD bar never jumps to the end of the cut slice. `ToneGenerator.getSlicer()` / `decodeAudio()` expose it and `scheduleHit()` hands every wall hit to the slicer first (a bounce falls back to the hit sample, tone or melody note when the slicer has nothing to play, e.g. a finished non-looping song). `Simulator.tsx` decodes the upload, mirrors the settings into the player, rewinds it on restart / mode change / preset load and pushes the song position to the canvas each frame (`CanvasHandle.setSongProgress`), where `Canvas.tsx` draws the thin progress bar along the bottom edge. The panel block lives in `components/simulator/sections/SongSlicerSection.tsx`. Settings: `sliceSong` (URL `slice`), `sliceMs` (`slms`, 80–1000 ms), `sliceLoop` (`sloop`) and `sliceFadeMs` (`slfade`); the song itself stays in memory and is not part of links or presets.

### Background music with ducking
The music bed mixes an uploaded track under the bounce sounds so an export is ready to post. `src/lib/audio/musicBed.ts` plays it through `AudioBufferSourceNode → fade GainNode → duck GainNode → volume GainNode → ToneGenerator master gain`; the master gain already feeds the speakers and the recorder's `MediaStreamDestination`, so the bed ends up in every export without touching `recorder.ts`. The ToneGenerator owns the bed (`getMusicBed()`, attached in `initAudioGraph()`, detached in `stop()`) and every bounce, gap pass or wall-break clip it schedules calls `duck(time)` at that sound's audio time – so beat-locked sounds and their ducks line up, and a hit that plays nothing (melody cooldown, occupied grid slot) does not duck. A duck drops the gain to `1 - ducking` instantly and ramps it back to 1 with `exponentialRampToValueAtTime` over the release time (`cancelAndHoldAtTime` where available, so a running recovery is held rather than dropped); several hits in one frame share one duck. The pure helpers (`duckedLevel`, `duckEnvelope`, `scheduleDuck`, `resolveOffset`, `playbackPosition`, `normalizeMusicOptions`) and the player itself (through a fake `AudioContext`) are covered by `tests/musicBed.test.ts`; the smoke test instruments `AudioBufferSourceNode.start` to check that the bed starts with the run, pauses, resumes from the pause position, restarts and – after Loop is switched off on a track that has already wrapped – still resumes from the wrapped position in the served export.

`Simulator.tsx` decodes the upload with `ToneGenerator.decodeAudio()`, hands the buffer to `MusicBed.setBuffer()`, pushes the settings with `setOptions()` and drives the transport from the run state: `play()` while the simulation runs, `pause()` (keeping the position) while it is paused, `stop()` when it finishes or a mode / preset change resets it, and `restart()` from the Restart button / R key (a non-looping track that reached its end stays silent until then). The position of the sounding source is tracked with the loop state that source actually had (a `looped` flag on the voice, set when it starts looping or is switched to loop mid-run): a source that has wrapped keeps sounding from `(start + elapsed) % duration` after Loop is switched off, so a pause/resume then continues from that wrapped position instead of treating the track as finished, while a source that never looped clamps at the end. The panel block – drop zone, track row with a live duck-level meter, volume, ducking, release, loop and start offset – is `components/simulator/sections/MusicSection.tsx`, which also exports its search keys. Settings: `musicVolume` (URL `mv`), `musicDucking` (`md`), `musicDuckRelease` (`mdr`, 50–1000 ms), `musicLoop` (`mloop`) and `musicStartOffset` (`mso`, seconds); the track itself stays in memory and is not part of links or presets. To route any other source into the recording, connect it to the ToneGenerator's master gain the same way.

### Picture Paint
Paint mode can reveal an uploaded picture instead of leaving a rainbow trail, in rhythm with a song. Three cooperating parts, all deterministic (no `Math.random`, no wall-clock time), so a run replays identically for the recorder:

- **Reveal** (`components/simulator/Canvas.tsx`): the picture (a `data:` URL kept in the page state like the custom ball image) is cover-fitted into the arena circle once, into a `source` layer the size of the arena in *device* pixels, plus a greyscale `ghost` of it. Every sub-step `PaintMode.onBallStep()` records a `PaintPoint` with its dab radius `r` (the ball radius in classic Paint; `ballRadius × paintBrush × paceScale × beatEnvelope` with a picture) and the canvas stamps only the points recorded since the last frame into a `mask` layer (one path, one fill – the mask is never redrawn from scratch), re-composites the `reveal` layer (`source` with `destination-in` the mask) only when new dabs arrived, and draws the ghost at `paintGhost` opacity under the reveal. `PicturePaintState.generation` (incremented by `PaintMode.init()`) tells the canvas to clear the mask on a restart; a resize rebuilds the layers and re-stamps every point. The coverage that finishes the run (≥ 95 %) still comes from the mode's 100×100 grid, which now marks the dab radius and counts painted cells incrementally, so the HUD percentage matches the mask; the finished picture is drawn crisp and `Simulator.tsx` holds the end screen back for `PAINT_FINISH_HOLD_MS` so it is seen (and recorded). The canvas mirrors the HUD state onto the element (`data-paint-coverage`, `data-paint-picture`, `data-paint-pace`, `data-paint-beat`), which the smoke test reads.
- **Beat sync** (`lib/audio/beats.ts`, `lib/simulation/beatClock.ts`): whenever a song is decoded for the music bed or the song slicer, `Simulator.tsx` runs `analyzeBeatsAsync()` – an onset envelope (Hann-windowed FFT frames every 512 samples, log-compressed spectral flux), adaptive-threshold onset picking, tempo by autocorrelation of the smoothed envelope over the 60–200 BPM range (three-harmonic comb score minus the half-lag peak, so the beat beats its half-tempo alias, times a gentle 120 BPM prior), the grid phase that collects the most envelope energy, and a least-squares refinement of period and phase on the onsets – in slices of a few milliseconds between idle callbacks, so a three-minute song never freezes the page. The result (`{ bpm, beatTimes, onsets, confidence }`) is shown in the section and handed to the engine through `engine.setPaintBeat()`, together with the music bed's start offset and loop flag (song time = offset + simulation time, wrapped at the track length), or the manual `bpm` setting when the source is "bpm". `BeatClock.sample(t)` maps simulation seconds to `{ index, sinceBeat, pulse }` with `pulse = exp(−decay · sinceBeat / period)` (1 on a beat, ~5 % before the next). `PaintMode.onPreUpdate()` scales every ball's velocity to `1 + paintBeatPulse × pulse`, undoing the previous step's scale first (and resetting it at a wall hit, where the engine assigns a fresh rebound), so the ball kicks on each beat and glides between while gravity and the rebounds act on the unscaled motion; the dab radius and the glow use the same envelope and the canvas draws a pulse ring. When the beat sync ends – switched off, no tempo to follow, or the picture removed mid-run – `releaseBeat()` undoes the scale still applied and clears the beat state on the very next step (also on the classic code path, where it is otherwise a no-op), so the ball resumes its natural speed at once, the pulse ring and the tempo hint disappear, and a picture loaded again starts from an unscaled ball. No sound is added: hits still play through the normal bounce path only when the ball actually hits.
- **Meticulous coverage** (`lib/physics/picturePaint.ts`): `summarizeCoverage()` reduces the 100×100 grid to a 24×24 map of painted fractions (blocks outside the circle read 1), `largestUnrevealedCluster()` flood-fills the blocks below 50 % and returns the weighted centroid of the heaviest cluster, and `steerAngle()` turns a rebound toward it by at most 18° – the same clamp as the cinematic director. The engine calls the new optional `GameMode.adjustRebound(ctx, ball, wallIndex, outAngle)` hook right after the director's nudge (Paint's wall has no gaps, so the director leaves the angle alone), which is where `PaintMode` steers with `paintGuided` on. Pacing: `paceBrushScale()` nudges the brush every second (`PACE_INTERVAL_MS`, simulation time) by the ratio of the expected coverage (`0.95 × elapsed / target`, linear) to the actual one, at most ×1.2 / ×0.85 per step and clamped to 0.7–2.5, and `paceStatus()` gives the HUD its "on schedule / behind / ahead" hint; `paintTargetSeconds()` picks the schedule – the loaded song's first pass from its start offset or the clip length, whichever ends first.

The settings are `paintBrush` (URL `pbr`), `paintGhost` (`pgh`), `paintBeatSync` (`pbeat`), `paintBeatSource` (`pbs`, `song` | `bpm`), `paintBeatPulse` (`pbp`), `paintGuided` (`pgd`) and `paintPaceToSong` (`pps`); `resolvePicturePaintSettings()` clamps them for URLs and presets alike; the picture itself never travels in links or presets. Everything is gated on `PaintModeOptions.picture`, so without a picture the Paint mode takes exactly its old code path (`tests/extras.test.ts` keeps its recorded fingerprint) and the finder is unaffected. The panel block is `components/simulator/sections/PicturePaintSection.tsx` (upload drop zone, ghost, brush, beat sync with its source switch, detected-BPM readout and pulse strength, guided and pace toggles), rendered in the Mode row of Paint mode and in the Visual section while the search box is in use. `tests/beats.test.ts` runs the detector on synthetic click tracks (90 / 120 / 150 BPM with an offset, stereo, accented, silence, the async slicing), `tests/beatClock.test.ts` the clock (manual and grid sources, offset, loop wrap, decay), `tests/picturePaint.test.ts` the coverage summary, the cluster centroid, the steering clamp, the pacing maths, the settings round trip and the engine behaviour (classic run untouched, brush and dabs, beat envelope, guidance, pacing, restarts); the smoke test generates a PNG in the page, uploads it, detects the tempo of a click-track music bed and checks that the reveal grows.

### Ball characters (faces, expressions and the Boris persona)
The borisbounces format – a ball with a face and a name that always escapes – as a visual layer over every mode. Nothing of it reaches the physics engine: the settings are read by the canvas only, so seeds, "rigged" outcomes and the finder are untouched (`tests/character.test.ts` runs a seeded engine with and without the tracker and compares the trajectories). The pure side lives in `src/lib/character/`, the drawing in `components/simulator/faceRenderer.ts`:

- **Settings** (`character.ts`): `ballFace` (URL `face`: `none` | `dot` | `cute` | `cool` | `cat` | `angry`), `ballName` (`bn`, trimmed to `MAX_NAME_LENGTH`), `nameLabel` (`nl`), `ballSquash` (`sq`, 0–1), `faceOverImage` (`fimg`) and `faceSounds` (`fsnd`) – all off by default; `resolveCharacterSettings()` validates URLs and presets alike, `borisPersonaPatch()` is the **Meet Boris** button (`BORIS_PERSONA`, and the ball grows to at least `BORIS_MIN_RADIUS` so the face reads on a phone), `characterRenderOptions()` turns the settings into what the canvas needs. `faceGeometry(style, r)` places the eyes, pupils, reach and mouth proportionally to the radius (a face scales with the ball size and with Ball Drop's size spread); below `TINY_FACE_RADIUS` every face becomes two dots.
- **Expressions** (`expression.ts`): a small, allocation-free state machine per ball, advanced once per frame on the **simulation clock** (`engine.getElapsedMs()`, so a pause freezes the face and a recording of a seed shows the faces of its run). Priority: `grin` (the ball is outside every intact wall, or the run is finished; lingers `GRIN_HOLD_MS`) > `shock` (a wall broke, `SHOCK_MS`; a running shock is never re-armed and the next one waits `SHOCK_COOLDOWN_MS`, so Shatter's burst of segment breaks startles the face now and then instead of freezing it wide-eyed) > `ouch` (a hard hit – a relative impact ≥ `OUCH_IMPACT`, i.e. a near head-on rebound – for `OUCH_MS`, then no new ouch for `OUCH_COOLDOWN_MS`) > `happy` (still for `REST_MS`) > `neutral`. `stepExpression()` returns the expression it *triggered*, which is what the cat chirps on.
- **Eyes, blink, squash** (`eyes.ts`): `lookTarget()` points the pupils along the velocity with a reach of `1 − e^(−speed / LOOK_REF_SPEED)` and `smoothToward()` eases it frame-rate independently; `BlinkClock` walks a Mulberry32 sequence seeded by `blinkSeed(runSeed, ballId)` – a blink every 1.8–5 s, sometimes a double one, never at the start – so blinks depend only on the seed, not on the frame rate or the playback speed (`blinkSchedule()` lists them); `squashAmount()` is a damped squash-then-stretch after an impact, `squashScales()` the area-preserving scale pair.
- **Tracker** (`tracker.ts`): `CharacterTracker.update(balls, frame)` derives per ball the impact (the change of velocity since the last frame beyond what gravity, wind and drag explain – rebounds off rings, pegs, box walls and other balls alike, no engine hook needed): the squash takes its strength relative to the Ball Speed, the ouch relative to the ball's own speed before the hit (at least `OUCH_SPEED_FLOOR` of the Ball Speed), so a mirror rebound scores 2·cos(angle to the normal) whatever the ball's speed and only near head-on ones hurt; its normal (for the squash), whether it rests or escaped (`escapeRadius`: the outermost intact ring), steps the expression, the eased look (for balls a mode moves by hand, like the Pendulum Wave bobs, from their movement) and the blink. It keeps up to `MAX_CHARACTER_BALLS` balls, starts over when the seed changes or the time goes back (a restart) and drops balls it no longer sees.
- **Drawing** (`faceRenderer.ts`): `FaceLayer` is created with the canvas loop. `beginFrame()` runs once per frame (the page forwards every `"gap"` sound event through `CanvasHandle.noteWallBreak()`, so every character is shocked when a wall breaks); around each ball's body `pushSquash()` applies the squash transform (pivoting on the side that hit), `drawBehind()` the cat's ears, `drawFront()` the face and `drawLabel()` the name under the first ball (white text, dark outline). Bouncing Shapes, Pendulum Wave, Metronomes & Polyrhythms and the Collision Playground draw their own bodies, so `drawOverlays()` puts the faces on them afterwards (two eyes above a countdown number; a DVD plate with a number stays plain). A custom image or emoji keeps its own look unless `faceOverImage` is on. The canvas mirrors `data-face`, `data-face-expression`, `data-face-count` and `data-name-label` for tools and the smoke test; the recorder copies the canvas, so exports have the faces and the label.
- **Sound** (`lib/audio/characterVoice.ts`): the cat's chirps are recipes (a sawtooth through a gliding band-pass formant – "mew!", "mrrp?", "meow~") scheduled by `ToneGenerator.playCharacterChirp()` like every other sound: on the beat grid, snapped to the scale (the contour follows its peak), ducking the music bed, into the recording. They play only with the cat face, `faceSounds` on and the bounce sound not an audio sample (`characterSoundsOn()`), at most one per `CHIRP_MIN_GAP_MS` (a second), so the cat comments on a minority of the bounces and never drowns the notes.
- **UI**: `sections/CharacterSection.tsx` is the "Character" group at the top of the Ball section (the face picker with a live preview that acts out every expression, Meet Boris, name, label, squash, face over image, cat sounds), exporting its search keys; a mode change keeps the character, the Ball section's reset clears it.
- **Extending**: a new face style is an id in `FACE_STYLES`, its proportions in `faceGeometry()`, its features in `drawFace()` (the `drawEye()` / `drawMouth()` branches), an icon and label key in `FACE_OPTIONS` (CharacterSection) and `Controls.face<Name>` in every messages file; a new expression is an entry in `EXPRESSIONS` with a rank and a trigger in `stepExpression()`, drawn in `drawEye()` / `drawMouth()` / `drawDotFace()`. `tests/character.test.ts` covers the settings, the geometry, the state machine, the eye-tracking maths, the blink schedule's determinism, the squash maths, the tracker (also on a real run), seeded Classic and Shatter runs through the `FaceLayer` (how often the face winces, is shocked and blinks, and how often the cat chirps) and the chirp; the smoke test checks the panel, the URL, the face and the label on the canvas, the emoji overlay option, the Bouncing Shapes bodies, the expression mix in Classic (mostly neutral, a minority of ouch) and Shatter (not stuck in shock) and the chirp (fewer than the bounce notes) in the served export.

Styled particles carry the optional `style` and `gravity` fields of `Particle` (`updateParticles()` multiplies the particle gravity), and like every visual effect they use `Math.random`, never the seeded generator: the tests replay a seeded run with every style and compare the trajectories. To add a style: its id in `PARTICLE_STYLES`, a recipe and a palette, the id in the `Particle.style` union (`types.ts`), a case in `drawStyledParticle()`, a button label in `PARTICLE_LABELS` (`ThemeSection.tsx`) and `Controls.themeParticle<Name>` in every message file.
- **Panel** (`components/simulator/sections/ThemeSection.tsx`, search keys `THEME_KEYS`): theme cards, background type with its colour pickers or the picture drop zone and dim slider, particle style and trail colours, rendered at the top of the Visual section; the section's reset restores the theme fields and drops the picture. `Simulator.tsx` decodes the upload (a file that is not a picture is refused), passes the look to the canvas and the particle style and palette to the engine. `tests/themes.test.ts` covers the catalogue, the merge, the URL / preset round trips, the carry-over, the bursts and the determinism; the smoke test (section 10) applies a theme and reads the gradient back from the canvas pixels, edits a colour, uploads a picture background, checks the reactive flashes over it and records a portrait clip.

### Team balls with scoreboard
The "which one wins" format – several balls, each one a team, a live scoreboard and a winner. Only the ball count reaches the physics (as "two balls" did before it); everything else is counted or drawn beside it, so a seeded run replays exactly with or without teams (the trajectories recorded in `tests/extras.test.ts` still match, and `tests/teams.test.ts` checks that a ball count of one and two replays the one-ball and the old two-ball runs exactly).

- **Several balls** (`src/lib/physics/ballStats.ts`): `MULTI_BALL_MODES` (Classic, Multiply, Lines, Grow, Shatter and Color Match – whose balls share the colour to match) start `startBallCount(config, mode)` balls: `PhysicsConfig.ballCount` (1 – `modeBallCap(mode)`) when the page sets it, else two with the old `twoBalls`. The cap is six (`MAX_TEAMS`) except where `MODE_MAX_BALLS` says otherwise: Grow grows every ball to about the radius of its sealed ring, so three or more balls crush each other through it (and the rest jam), and it keeps its old limit of two – one- and two-ball Grow runs replay exactly as before. `activateMode()` spawns them from the centre, the first one in the seeded random direction and the others spread evenly around it (`startBallAngle()`: the second of two flies straight back, exactly as before; no extra random draws), coloured by slot (`startBallColor()`: the ball colour, the second ball colour, then `EXTRA_BALL_COLORS`). Every starting ball carries its slot in `Ball.team`; Multiply's new balls and the halves of a split inherit it, and `setConfig()` recolours only slot 0 with the ball colour (slot 1 with the second colour), so the other slots keep theirs. `engine.setBallCount(n)` is the live change the page makes when the slider or the roster changes: it removes the balls of the slots beyond `n` (down to one: only the first ball, as the switch did) and adds the missing slots at the first ball, flying off in their start directions.
- **Per-ball stats**: the engine owns a `BallStatsBook` and records into it where things already happen – a rebound in the wall collision (a bounce), `reportWallBreak()` (the engine's own gap pass, Multiply's escapes and Shatter's segment breaks: a wall), the optional `ModeContext.creditWallBreak()` (Color Match's matching segments, which must not split balls) and `scanEscapes()` once per step after the mode's `onPostUpdate()` (a ball beyond the outermost wall's live radius – with breathing walls, where the pulse has it in that step – plus its radius and `ESCAPE_MARGIN`, has escaped; each ball once, and the half of an escaped ball inherits that). The live radius is what Multiply (+ `ESCAPE_MARGIN`), Shatter (+ 20 px) and Color Match (+ 30 px) test in their `onPostUpdate()` just before the scan, so the escape that ends a run is always counted in the step that ends it or earlier, and the frozen scoreboard and the winner never miss it. `getBallStats(id)`, `getTeamStats()` (six totals, reused objects), `hasBallEscaped(id)` and `getStatsGeneration()` (bumped by every restart) read them; nothing here draws a random number or moves a ball.
- **Settings** (`src/lib/teams.ts`): `ballCount` (URL `nb` above two; two is still `two=1`), `teams` (the roster: `{ name, color, emoji }[]`, at most six, URL `teams=name*rrggbb*emoji,…` with `%`, `*` and `,` percent-escaped inside a field), `showBallNames` (`tn`), `showScoreboard` (`tsb`) and `scoreboardPosition` (`tsp`: `top-left` | `top-right`). `writeTeamParams()` / `readTeamParams()` are called from `settingsToSearchParams()` / `settingsFromSearchParams()` and `resolveTeamSettings()` from `presetToSettings()` (a preset from before the ball count keeps its two balls). A roster sets the ball count to its size (`effectiveBallCount()`, capped by the mode's `modeBallCap()`, is what the engine and the finder get; a bigger roster than Grow takes keeps its teams, and the first two play there), `ballCountPatch()` / `rosterPatch()` keep the count, `twoBalls` and the roster in step, and `teamCarryOver()` takes the roster (and its balls) along when the mode changes.
- **Ranking**: `compareTeamStats()` – most escapes, then most walls broken, then most bounces, then the earlier first escape; `rankTeams()` sorts without allocating (the scoreboard ranks every frame) and `teamResult()` names the winner or the teams tied for first place.
- **Drawing** (`components/simulator/teamsRenderer.ts`): `TeamLayer` gives team balls their colour and emoji sprite in the ball pass of `Canvas.tsx`, rings a ball whose body does not show its colour and writes each team's name above its first ball; after the HUD it draws the scoreboard (layout, fonts and fitted names cached per size) in a corner of the centred square the recorder crops – below the page's Restart / Pause buttons on a square canvas, flush in a recording – and, once `isSimulationFinished()`, freezes the stats, pops up the banner (lower when the mode shows its own banner) and throws screen-space confetti from typed arrays. `Simulator.tsx` holds the end screen back for `WINNER_HOLD_MS` (3 s) while teams play, which also keeps a recording running through the celebration: an export whose length (`recordingDuration`) runs out after the run finished waits for that hold (and the escape replay) instead of stopping – the stop is left to the `finished` effect, with `END_HOLD_FALLBACK_MS` as a backstop – and Find Simulation sets the length to the found run plus the 3 s. The canvas mirrors `data-teams`, `data-team-stats` (`bounces/walls/escapes` per team), `data-team-winner`, `data-team-labels`, `data-scoreboard` and `data-scoreboard-bottom` (where the scoreboard ends) for tools and the smoke test.
- **Panel** (`components/simulator/sections/TeamsSection.tsx`, search keys `TEAM_KEYS`): the "Teams & Scoreboard" section – the Teams switch (default teams with translated names, at least two), a row per team (colour, emoji field with a datalist of suggestions, name, remove), Add Team (up to `maxTeamsIn(mode)`: two in Grow, with a note that the first two teams play there), Ball Names, Scoreboard and its corner; `BallCountControl` is the Ball Count slider of the Ball & Physics section (its maximum is the mode's cap). Its reset clears the roster and keeps the balls.
- **Extending**: to let another mode start with several balls, check that its logic copes with them (shared state like Color Match's colour is fine; a mode whose balls fill the arena, like Grow, needs a cap in `MODE_MAX_BALLS`), add it to `MULTI_BALL_MODES` and report its wall breaks through `ctx.reportWallBreak()` (or `ctx.creditWallBreak()` when a split would be wrong there). `tests/teams.test.ts` covers the URL form, the validation, the settings and preset round trips, the ranking, the stats book and seeded runs of every multi-ball mode; the smoke test (section 14) loads a roster from a link, edits it, runs three teams to a winner at 8× and records the banner, checks that a breathing Shatter run ends with its escape on the scoreboard, that Grow plays two of four teams without an escape, and that Find + Record at 1× keeps the banner in the export.

### Cinematic camera
A rendering layer over every mode; nothing of it reaches the physics (`tests/camera.test.ts` drives seeded runs through the camera with everything on and compares every step with the plain run):

- **Settings and maths** (`src/lib/simulation/camera.ts`, pure): `CameraSettings` – `cameraZoom` (URL `cz`), `screenShake` (`shake`), `slowMoOnNearMiss` (`slow`), `slowMoFactor` (`slowf`), `slowMoMs` (`slowms`), `replayOnEscape` (`replay`); `DEFAULT_CAMERA_SETTINGS` is all off, `CAMERA_RANGES` is spread into `RANGES` and `resolveCameraSettings()` validates URLs and presets alike. The view is a `CameraView` (focus offset + scale): `stepCameraView()` eases the focus toward the first ball with the classic follow's 0.08 inside `followLimit()` (half the arena at 1×, more when zoomed, so a ball at the outer wall stays in frame) and the scale toward `zoomScale()` (1 → `MAX_CAMERA_SCALE` 2.2), reduced by `fitScale()` so a second ball stays in frame – with zoom 0 it is exactly the old camera follow – and `cameraTransform()` turns it into the canvas translate + scale. The shake is `shakeEnvelope()` (quadratic decay over `SHAKE_DECAY_MS`) × `shakeOffset()` (a deterministic ~13 Hz wobble whose direction turns by the golden angle from one break to the next), at most `MAX_SHAKE_FRACTION` of the shorter canvas side. The slow motion is `slowMoTimeScale()` (eases in over 60 ms, holds the factor, eases out over 250 ms) driven by `SlowMotion` (a window per near miss, extended by another one inside it, then `SLOW_MO_COOLDOWN_MS` before the next, so a run is never slow throughout). The replay constants are `REPLAY_WINDOW_MS` (2 s), `REPLAY_SPEED` (½), `REPLAY_POST_ROLL_MS` and `REPLAY_MODES` (the modes whose run ends with an escape).
- **Events** (engine): `engine.getWallBreakSerial()` counts every `"gap"` sound event – the engine's gap passes and the modes' breaks, teleports and segment breaks – and `engine.getNearMissSerial()` the director's near misses (`CinematicDirector.getNearMissSerial()`: a gap pass within four ball widths of a gap edge, counted by the same geometric test whether the director is on or off, without drawing a random number). Both only ever grow; the camera polls them once per frame, however many steps the frame ran.
- **Replay buffer** (`src/lib/simulation/replay.ts`): `ReplayBuffer` keeps ~2.5 s of steps in typed arrays allocated once – position, radius, id, sprite angle, team slot and colour of up to 24 balls, rotation and radius of up to 32 walls, the broken-wall mask and the wall-break count – and `sample(t)` rebuilds the scene at any moment into pooled objects (balls matched by id and interpolated between two steps, rotations the short way round, a trail per ball from its recorded positions), so neither recording nor replaying allocates per frame. It freezes `REPLAY_POST_ROLL_MS` after every ball got outside the outer wall, so Classic – whose run only ends once the ball is far off-screen – replays the escape, not the flight.
- **Canvas** (`components/simulator/cameraRenderer.ts`, `CinematicCamera`, one per draw loop): `timeScale()` multiplies the time the canvas feeds the fixed-step engine – the engine still runs the same 60 Hz steps, so a slowed run is the same run, and the recorder, which copies real-time frames, exports the slow motion; `afterStep()` records each step (and, while the slow motion is switched on in a ring mode, keeps the step before it in a `StepInterpolator`, `src/lib/simulation/stepInterpolation.ts`); `slowView(engine, alpha)` hands the draw pass the balls (by id, with their live look and a trail whose newest point follows them), walls and rotations `alpha` – the canvas' leftover accumulator ÷ one step – of the way between the last two steps, from typed arrays and pooled objects like the replay: at 0.2× a step comes only every fifth frame, and the raw positions would stand still for four frames and jump (a 12 fps stop-motion in the export too). It draws one step behind the engine all the time the switch is on, so opening or closing a window never jumps the view by a step; a ball that moved more than `INTERP_SNAP_PX` in one step (a teleport) is drawn where it is, and the rhythm modes, which draw their own bodies, keep the engine's positions (`SLOW_VIEW_MODES`); `frame()` kicks the shake on new wall breaks, starts the slow motion on new near misses and, when a replay mode finishes, holds on for the post-roll (`postroll`) and plays the window at half speed (`playing`; a wall that breaks inside it shakes the view and bursts its particles again through `spawnWallBreakByStyle` – visual only, particles never use the seeded generator); `replayView()` hands the recorded walls, rotations, broken set and balls to the draw pass instead of the live ones (mode overlays such as Shatter segments or portals keep their live state, the mode banners wait); `applyView()` replaces the classic follow whenever zoom, shake or the replay need the view and hands back to it without a jump; `drawOverlay()` draws the REPLAY badge (blinking dot, label, speed, progress) in screen space, centred at the top of the square the recorder exports – at its bottom when a top text is set or the teams' scoreboard is shown (below the scoreboard when a bottom text is set as well) – so exports have it. `CanvasHandle.holdsEndScreen()` lets `Simulator.tsx` hold `finished` back – the end screen and the recording's stop – until the replay is over; with teams the winner banner (`TeamLayer.drawOverlay()`'s `holdBanner`) and its 3 s hold only start after it. The canvas mirrors `data-camera-replay` (idle / postroll / playing / done), `data-camera-scale`, `data-camera-time-scale`, `data-camera-shakes`, `data-camera-slow-mo`, `data-camera-replays`, `data-camera-slow-frames` and `data-camera-slow-still` (slow-motion frames drawn, and those that drew the first ball where the frame before did) for tools and the smoke test.
- **UI**: `sections/CameraSection.tsx` is the "Camera" group of the Visual section, under Camera Follow (zoom, shake, the slow-motion switch with its speed and length, the replay switch with a note outside the escape modes), exporting its search keys (`CAMERA_KEYS`); the Visual section's reset turns it all off and a mode change resets it like Camera Follow. The badge text is `Simulator.canvasReplay`, the labels live under `Controls` in every `messages/*.json`.
- **Tests**: `tests/camera.test.ts` covers the settings (defaults, clamping, URL and preset round trips), the zoom and follow maths (zoom 0 equals the classic follow frame for frame), the shake, the slow motion, the replay buffer (interpolation, ring wrap, trails, ids, walls, freezing, no allocation), the slow motion drawn between steps (`StepInterpolator`: interpolation, ids, teleports, the ball cap, walls, no allocation; and a seeded Classic run at 0.2× and 0.4× in which the drawn ball moves in every slowed frame while the engine's positions stand still in most of them), the engine events, determinism (Classic, Shatter and Portal) and the replay of real Classic and Accumulation escapes; the smoke test (section 15) drives the controls, the URL and the search, a zoomed, shaken and slowed run (whose ball moves in every slowed frame), and a recorded 8× escape whose replay plays before the export and the end screen; section 16 runs three teams with the replay (team names on the replayed balls, the winner banner after it).
### Multipliers
Stackable stat boosts for every mode, pickups in the ring modes and a board mode built on them. Everything that touches the physics draws from the engine's seeded RNG and runs in the fixed steps, so seeds, recordings and the finder replay exactly; with the settings at their defaults nothing changes (`tests/extras.test.ts` still reproduces every mode's recorded trajectory).

- **The stats** (`src/lib/physics/multipliers.ts`): `Ball.mult` (optional – absent is a plain ×1 ball) holds `speed`, `size`, `damage`, `bounce` and `gravity`. `applyMultiplier(ball, stat, factor, cap)` stacks a factor multiplicatively (`stackMultiplier()`, clamped to [1/cap, cap] – Infinity unless `mpUnlimited` is off and `mpCap` > 0 – and to a float-safety ceiling of 10¹⁵) and applies it: speed scales the velocity, size the radius and `radiusScale` (so a Ball Size change keeps it), gravity the ball's `gravityScale`. Where the others act: `cruiseSpeed()` is the ring modes' cruising speed (the engine's rebound speed, the slow-ball boost, Grow's and Accumulation's re-normalisation, Multiply's children – who also inherit the multipliers; while multipliers are in play Multiply stops spawning them at `MULTIPLY_MAX_BALLS_WITH_MULTIPLIERS` (200) balls, since inherited speed makes every escape come sooner and the count would explode), `hitDamage()` is what one hit takes off anything with hit points (Shatter's `segment.hp`, Target clears that many numbers per correct hit, the board's blockers, Glass Smash's panes), `effectiveBounce()` multiplies the restitution of the engine's rebounds and of obstacles (capped at `MAX_EFFECTIVE_BOUNCE` = 1.5; rebounds a mode sets itself – Portal, Grow – keep theirs) and `smashesWalls()` lets a ball whose damage reached `wallSmashThreshold` break a ring on contact in the escape modes (`SMASH_MODES`) – `engine.smashWall()` runs the wall-break effect, the "gap" sound, the split reporting and the director like a gap pass would. A grown ball is refitted by `fitBallToRings()`: moved radially clear of the rings of its corridor, bursting a ring it no longer fits inside, and – bigger than the outermost intact ring – "outgrowing" the arena: `MultiplierRuntime.outgrow()` stops the physics (`engine.update()` only moves the confetti from then on), `isSimulationFinished()` reports the end and the canvas shows the banner – which `Simulator.tsx` holds on screen for `MULT_FINISH_HOLD_MS` (2 s; `engine.endsWithMultiplierFinish()`, like the teams' winner banner) before the end screen covers it, so a recording keeps it too. A corridor that is too narrow even for the ball's un-multiplied size (many rings on a small canvas) is left as the engine always handled it.
- **Physics safety**: while multipliers are in play (`MultiplierRuntime.isActive()` – pickups on, the board mode, or any multiplier applied this run) the engine plans every 60 Hz step with `planStep()`: the bound on each ball's speed (its speed, or the fastest rebound the rings may give it, times `SPEED_MARGIN`, plus one step of gravity) over `maxMovePerSubStep()` (half its radius, at most `MAX_MOVE_PX` = 4 px) gives the sub-steps the step needs; up to `MAX_SUBSTEPS` (64) the step takes that many, beyond it `planForRatio()` halves the step until 64 suffice (**time dilation**: the simulation clock – `getElapsedMs()`, wall rotation, timers – runs slower and the HUD shows SLOW-MO x½, x¼ …). Multipliers change at step boundaries only (touched orbs and gate passes are queued and applied at the end of the step), so a plan always covers the speeds its step runs with. The swept obstacle and breathing-wall tests stay as they were on top. With more than `HASHED_PAIRS_FROM` (64) balls in a multiplier run the engine's ball-to-ball pass takes its pairs from a `SpatialHash` (the grid covers the canvas and a margin, far-flung balls are clamped into its border cells) instead of the n²/2 pair loop, which up to 64 sub-steps a step would multiply; every other run keeps the pair loop and its exact trajectories. `tests/multipliers.test.ts` proves the guarantees: a ball at ×1000 speed in Classic (and a two-ball run) never ends up outside an intact ring except through a gap or a smash, balls grown up to the arena stay inside their rings until the outgrow finish, the planner never exceeds its limits, and runs with multipliers are deterministic.
- **Pickups** (`MultiplierRuntime.stepPickups()` / `touch()` / `endStep()`, `PICKUP_MODES`): once per step the runtime schedules orbs `pickupInterval()` apart (0.5–1.5 × 10 s / `pickupRate`), places them inside the corridor of the first ball (`ballCorridor()`), drifts them off the corridor's rings and lets them fade after `pickupLifetime`; every sub-step each ball checks the few orbs afloat. At the end of the step a taken orb stacks its `PICKUP_FACTORS` entry through the cap (x2 BALLS clones the ball with a seeded turn, within the ball interaction's `maxBalls`, and calls the mode's `onBallSplit()` so Multiply marks the clone of an escaped ball), spawns a burst and queues a `"multiplier"` sound event carrying the new total. `ToneGenerator.playMultiplier()` (`src/lib/audio/multiplierTones.ts`) plays the rising arpeggio of `multiplierArpeggio()` – more notes and a higher root the bigger the stack – the way a bounce plays: the next slice while the slicer runs, the hit sample transposed per note in sample mode, otherwise the bounce instrument (a loaded melody roots it on its next note, with the melody voice), snapped to the scale, on the beat grid, ducking the music bed.
- **The Multipliers mode** (`src/lib/physics/modes/multipliers.ts`, id `multipliers`, escape family): `generateBoardLayout()` draws the rows from the seed (2–4 slots, gate kinds weighted by `mpGateMix` – six digits for count, speed, size, damage, reverse, release –, factors from `gateFactor()`, blockers with 3–8 hit points, bumpers, funnels) and `placeBoard()` lays it out in the centred square the recorder crops to, growing downwards (obstacles from `obstacles.ts`, bucketed into one band per row). The board is private to the mode: `onBallStep()` resolves each ball against the side walls and the obstacles of the bands it overlaps with `resolveBallObstacle()`, detects the gate line it crossed (each row once per ball) and the HOME line; `onPostSubStep()` resolves ball-to-ball contacts with the Collision Playground's `SpatialHash` (masses ∝ radius², damped restitution so the piles on the release doors settle); `onPostUpdate()` applies the step's gate passes (count gates clone within `mpMaxBalls` – the clones inherit the velocity with a seeded turn and scale, the multipliers and the row; speed / size / damage gates go through `ctx.getMultipliers()`; ÷2 gates absorb every second ball), removes arrivals in place, nudges a ball that has not got lower for 2.5 s (a wait on a door counts at a quarter; after 15 s a ball is lost, so every run ends), eases the camera (`view.cameraY`, simulation-timed) toward the lowest ball and finishes when the board is empty – with "N Boris made it home", which the page holds for `MULT_FINISH_HOLD_MS` before its end screen (Find Simulation adds the hold to the export length). Release doors open on their own clock and only close once no ball is half-way through. Notes: every hit plays the pentatonic "plinko piano" pitch of its x position (`boardPitch()`), count gates, doors and arrivals their own notes, at most `MAX_SOUNDS_PER_FRAME` per rendered frame (the most energetic, like the Collision Playground) plus one arpeggio for the biggest stat stacked. Settings `mpRows` (URL `mprw`), `mpGateMix` (`mpgm`), `mpStartBalls` (`mpsb`), `mpMaxBalls` (`mpmb`), `mpTarget` (`mptg`); a change restarts the board. With a target the finder (`findByCount()` in `finder.ts`) tests one seed per frame until the final HOME count is within 5 % of it (`countTolerance()`) and the page shows the count; without one it searches by duration like any mode.
- **UI**: `components/simulator/multiplierRenderer.ts` draws the board (gate bands and labels that flash on a pass, pegs, bumpers, funnels, blockers with their hit points and cracks, doors with their countdown, the HOME zone), the balls batched (one path per colour, one stroke for the speed streaks and one for the damage rims), the pickup orbs and the HUD – the stat badges in the top left of the recorded square (they pop and glow on the simulation clock when a value changes; with teams they start below the scoreboard in its default top-left corner, and wrap before it – SLOW-MO moves below it – in the top right: `TeamLayer.scoreboardRect()` says where it will be drawn), SLOW-MO in the top right, the live HOME counter – and mirrors the state into `data-mult-*` attributes (`multSpeed`, `multSize`, `multDamage`, `multBounce`, `multGravity`, `multBalls`, `multPickups`, `multOrbs`, `multSmashes`, `multSlowmo`, `multOutgrew`, and on the board `multHome`, `multActive`, `multClones`, `multGates`, `multDone`). The panel blocks are `sections/MultipliersSection.tsx` (the "Multipliers" group of the Ball section: pickups, rate, kinds, lifetime, unlimited / cap, smash threshold) and `sections/MultipliersModeSection.tsx` (the Mode row of the board: rows, start balls, max balls, gate mix, target count). The stat settings travel in `PhysicsConfig` (`multiplierConfigOf()`, resolved by `resolveMultiplierConfig()` in `setConfig()`), so the finder's headless engines get them with the config; URL keys `mpu`, `mpc`, `wst`, `mpk`, `mpr`, `mpty`, `mpl`.
- **Tests and smoke**: `tests/multipliers.test.ts` covers the stacking maths without and with a cap, the formatting, the planner and the dilation, the ring fit, the smash threshold, the outgrow finish, pickups (seeded spawns, touches, clones within the cap, the arpeggio event), Shatter / Target damage, determinism and the settings; `tests/multipliersMode.test.ts` the layout, the gate maths and cloning caps, the spatial-hash pairs against brute force, arrivals, the finish, the camera, determinism, the count finder and the settings. The smoke test checks that pickups in Classic change the HUD badges, that the board counts arrivals home and holds "made it home" – and a size-orb run its OUTGREW THE ARENA – before the end screen, that the badges of a teams run start below the scoreboard live and in the export (`data-mult-hud-top`, `data-scoreboard-bottom`), that Multiply with speed orbs stays within 200 balls at a steady frame rate and that Glass Smash's gates stack multipliers on the ball; `tests/multipliers.test.ts` also holds Multiply's cap (and the frame budget of the speed-orb run that used to explode), the hashed ball pass against the pair loop and `endsWithMultiplierFinish()`.
- **Add a multiplier type**: add the stat to `MULTIPLIER_STATS`, `unitMultipliers()` and `copyMultipliers()`, apply it in `applyMultiplier()` (if it changes the ball at once) or read `ball.mult.<stat>` where it acts, and keep that path behind a `ball.mult` check so plain balls are untouched; for an orb add a `PICKUP_KINDS` entry with its `PICKUP_FACTORS`, `PICKUP_STATS` and `MULTIPLIER_COLORS`, a word in `MultiplierLabels` (`Simulator.canvasMp<Name>`) and `Controls.pickupKind<Name>` in every messages file; for a gate add it to `GATE_KINDS` (one more digit in `mpGateMix`), `gateFactor()`, `GATE_COLORS` / `gateLabel()` in the renderer, the effect in `MultipliersMode.onPostUpdate()` and `Controls.gate<Name>`; for a HUD badge add it to `BADGES` and the view's summary (`MultiplierRuntime.summarize()`), and cover the maths in `tests/multipliers.test.ts`.

### Obstacle editor
`src/lib/physics/obstacleEditor.ts` holds the editor's model and physics. The `obstacles` setting is a list of `EditorObstacle`s – `kind` (`peg`, `bumper`, `blocker`, `spinner`), centre `x` / `y` in arena radii from the arena centre (1 = the ring of the single-ring modes, `arenaFrameOf()` = `arenaRadius()`), `size` (radius of a peg / bumper or length of a bar, in percent of that radius), `angle` (degrees, bars) and `rpm` (spinners) – validated by `sanitizeObstacle()` / `resolveObstacles()` (clamped to `OBSTACLE_LIMITS`, rounded so the stored value is exactly what the URL reads back, at most `MAX_OBSTACLES` = 24). `serializeObstacles()` / `parseObstacles()` are the URL form (`obs`: `p:x,y,size`, `b:x,y,size`, `k:x,y,length,angle`, `s:x,y,length,angle,rpm`, joined by `;`), read and written by `readObstacleParams()` / `writeObstacleParams()` in settings.ts next to `bumperBoost` (`obb`, 1–2, default 1.3); presets go through `resolveObstacleSettings()`. `addObstacle()` (on `nextObstacleSpot()`, a free spot on rings around the start), `updateObstacle()` and `removeObstacle()` are the list edits the panel and the canvas share.

The list and the boost travel inside the physics config (`editorObstacles`, `bumperBoost` in `PhysicsConfig`; `obstacleConfigOf()`), so `engine.setConfig()` applies them and the seed finder, which copies the page engine's config, replays a found seed with the same obstacles. The engine keeps an `ObstacleField`: `configure()` builds the pixel obstacles (circles and capsule bars of obstacles.ts; bar thickness `barThickness()`) whenever the list or the canvas size changes – a spinner that was only moved keeps its current angle – and `reset()` (every mode init, via `clear()`) turns the spinners back to their start angle. While the current mode is a ring mode (`supportsObstacles()`, `OBSTACLE_EDITOR_MODES`) `update()` turns the spinners every sub-step and resolves every ball against every obstacle after it moved and before the ring walls (`handleEditorObstacles()` → `ObstacleField.collide()`), with the wall-bounciness extra scaling the restitution. The push-out ignores the rings, and a ring judges a ball's side by its centre, so `keepRingSide()` moves a ball whose centre an obstacle pushed across an intact ring back to half a pixel on the side it was on (the innermost ring crossed on the way out, the outermost on the way in) – otherwise a sealed ring would eject it, as a grown Grow ball pressed onto a spinner was. Whatever sped a ball up – a spinner's fling or a bumper's kick – it leaves with at most `obstacleSpeedLimit()`: the larger of its incoming speed and `BUMPER_SPEED_CAP` × the ball speed setting, and never more than `RING_CAPTURE_SHARE` (90 %) of a ring's capture band (`ball.radius + RING_CAPTURE_MARGIN` px, the band `processWallCollisions()` tests) per sub-step, so the next ring still catches it instead of letting it tunnel through. A contact at `OBSTACLE_HIT_SPEED` or more is a hit: it lights the obstacle (`lastHitMs`, simulation time), a bumper sets the ball's speed to its speed before the hit × the boost (never above `BUMPER_SPEED_CAP` × the ball speed setting, never below what the rebound left; the next ring rebound resets it as always) and a `"hit"` `SoundEvent` is queued – pegs and bars play their note of a pentatonic ladder by index (`obstacleNote()`), bumpers carry `bumper: true`, which the page plays as the pinball ding of `src/lib/audio/bumperTone.ts` (`ToneGenerator.playBumper()`: snapped to the scale, on the beat grid, ducking the music bed); at most `MAX_OBSTACLE_SOUNDS_PER_STEP` sounds per step. Nothing here draws random numbers or reads the clock, so a seed replays exactly.

`src/components/simulator/obstacleEditorRenderer.ts` draws them from `engine.getEditorObstacles()` (null outside the ring modes or without a layout) inside the camera transform, under the balls: glowing discs, bumper rings that swell and flash on a kick, bars with a hub on the spinners, hits glowing like the walls. Its `ObstacleEditorLayer` also edits: while `obstacleEditing` is set (Simulator.tsx: a ring mode with a layout, and the run not going – before the start, paused – nor recording or searching) it remembers the transform it drew with, maps pointer events (`clientToCanvas()` → the inverse of that transform → `worldToArena()`) to the obstacle under the pointer (`pickObstacle()`, more slop for touch), drags it live through `engine.setConfig({ editorObstacles })` and commits the list to the settings on release; Backspace / Delete remove the selected one. A press that grabs an obstacle takes the focus off the panel control that had it (a slider just nudged would otherwise keep the keys), and the keys are left alone only while a text field has the focus (`isTextEntryTarget()`). A new layout or boost drops a found seed together with its result (Simulator.tsx), so neither the compact ready bar – which shows the "do not change settings" warning while a found seed stands – nor the finder panel quotes a run length that no longer holds. The canvas mirrors the state into `data-obstacles`, `data-obstacle-editing`, `data-obstacle-selected`, `data-obstacle-hits`, `data-bumper-hits` and `data-spinner-angle`. The panel is `components/simulator/sections/ObstaclesSection.tsx` (its own "obstacles" `ControlSection`, listed in the ring modes). `tests/obstacleEditor.test.ts` covers the URL form, the validation, the coordinate mapping, the list edits, the field (bumper kick and cap, spinners, sound budget, the speed limit), the editing keys, determinism in the engine and the finder, and that the ball stays inside the rings (Grow's sealed ring with the panel's first spinner, a spinner at full speed and length in Lines and Classic, hard bumpers on a small fast ball); the smoke test (section 20) deletes with Backspace right after a slider was used, section 20b moves an obstacle after Find Simulation and section 20c runs Grow with the panel's first spinner at 8× (the grown ball still fills its ring 50 s in) and Lines with a spinner at full speed and length (the ball still hits it 40 s in).

- **Add an obstacle kind**: add it to `OBSTACLE_KINDS` with a URL code (`OBSTACLE_CODES`), a default size and a material, build it in `ObstacleField.configure()` (and give it any special behaviour on a hit in `collide()`), draw it in `obstacleEditorRenderer.ts`, and add its label (`OBSTACLE_KIND_LABELS` in the section, `Controls.obstacleKind<Name>` in every `messages/*.json`).

### Circle Illusion and wobbly walls
`src/lib/physics/modes/illusion.ts` (id `illusion`, family `rhythm`) reuses the owned-playfield mechanism of the other rhythm modes: it activates with the `"none"` ring layout, spawns one ordinary engine ball per body (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`), computes every body once per 60 Hz step in `onPostUpdate()` and pins the balls there in `onBallStep()`; `components/simulator/illusionRenderer.ts` draws the stage, the bodies and the overlay from the mode's view (`engine.getIllusionView()`, the same object every call) in branches of the canvas' passes, like `polyrhythmRenderer.ts` does. No `GameMode` hook was needed; the only interface addition is the optional `ModeContext.recordWallContact()` of the wobbly walls.

- **Lines** (the straight-line / rolling-circle illusion, the Tusi couple): ball *i* of *N* moves on the diameter at angle `linePhase(i, N)` = i·π/N (turned by β = −π/2) with the same phase offset: pᵢ = c + A cos(θ − i·π/N)·u(i·π/N + β), θ = ±2π·t/T. Because cos(θ − α)·u(α) = ½[u(θ) + u(2α − θ)], every ball lies on the circle of radius A/2 around `rollingCircleCentre()` = c + (A/2)·u(θ + β), at the angle 2·i·π/N − θ – evenly spaced on a circle that rolls inside the big one. The rim touches are counted exactly per step: slot m (time m·T/2N) is in step s when u(s) ≤ m < u(s + 1) with u(s) = s·2N / (steps per cycle), divided last so a touch on a step boundary is counted once; `lineTouch(m, N, direction)` names the ball (i ≡ d·m mod N) and its end. Each touch is a `"hit"` `SoundEvent` with the ball's C-major degree from C4 (`pendulumPitch()`) and a rim contact for the wobble; `IllusionView.circleError` (the largest distance of a ball from the hidden circle, 0 up to rounding) is mirrored into `data-illusion-circle-error` for the smoke test.
- **Rings**: K rings between `RING_HOLE_FRACTION` and the arena radius; ring k's ball bounces between its walls along a rail turning K − k times per cycle (`RING_CYCLE_SEC` / speed), `RING_TRAVERSALS` (even) traversals per cycle with the phase staggered by a K-th of a traversal from ring to ring (`ringFraction()` is the triangle wave), so the notes ripple outward and the whole figure – rails and radial phases – is back in line after every cycle (an accented note, `alignCount`, a screen flash). Pitches: the ring's degree, inner rings higher.
- **Nested**: `depth` circles with radii falling geometrically from the arena to the innermost (its size follows the Ball Size), masses ∝ radius, seeded launch velocities; `NESTED_SUBSTEPS` fixed sub-steps per step move every circle and resolve it against its container (outer to inner: position correction by inverse mass, an elastic impulse on the relative normal velocity), so the kinetic energy is conserved (`getNestedEnergy()`, checked in the tests). A collision faster than `NESTED_HIT_SPEED` plays the container's note (C3 G3 C4 E4 G4, louder the harder) and logs two contacts – the container pushed out, the circle inside pushed in; the view's `intrinsicWobble` makes these circles wobble even with Wobbly Walls at 0.
- **White spaces** (`src/lib/physics/illusionPatterns.ts`): `PATTERN_ELEMENTS` designs every picture in arena units out of discs, closed outlines (the balls bounce off the outside and never get in, so the whole inside stays white) and thick strokes, all turned into obstacles of `obstacles.ts` by `buildIllusionPattern()` (seeded offset and scale); `isLegalPosition()` is where a painter may be. `CoverageGrid` (128 × 128 over the arena's square) marks the paintable cells once per run (a disc dilation of the legal cells, half a cell of slack) and paints the capsule a painter swept between two path points; the run is revealed at `WHITESPACE_DONE` (98 %) – or, the safety net, once `WHITESPACE_STALL_COVERAGE` (90 %) is painted and no painter has found a new cell for `WHITESPACE_STALL_SEC` (6 s at speed 1; `whitespaceRevealDue()` counts steps, so the finder and replays agree). Painters move at a constant speed in `PAINTER_SUBSTEPS` sub-steps, resolve the picture with `resolveBallObstacle()`, reflect off the rim with a seeded scatter and, on every bounce – off the rim or the picture (whose normal is the direction the bounce took speed away along) –, turn by up to 0.9 rad toward the direction with the most unpainted cells they can reach (`steerAngle()`; `CoverageGrid.rayScore()` counts along the path only up to the first cell the paint cannot reach, so white behind the picture never lures a painter into it). That keeps the default run at about 20–30 s and lets the biggest balls, or one or two painters, reach every pocket (a single painter takes about two minutes). Every bounce plays the coverage as a degree of C major climbing two octaves (`whitespacePitch()`); the reveal plays C5-E5-G5-C6 accented and throws confetti. The view carries every painter's path (`paths`, `pathLen`, `pathVersion`), which the renderer strokes with `destination-out` into a white offscreen layer (only the points added since the last frame); the reveal fades the specks the painters missed and lights the picture up in the accent colour over `REVEAL_MS`, and `Simulator.tsx` holds the end screen `ILLUSION_REVEAL_HOLD_MS` for it (recordings keep it).
- **Wobbly walls** (`src/lib/physics/wobble.ts`, render-only): the engine logs every ring hit in `processWallCollisions()` – wall, contact angle, strength (the approach speed over the ball speed, positive when a ball inside pushes the wall out) and simulation time – into a `WallContactLog` (a ring of typed arrays, cleared with every run; `engine.getWallContacts()`), and modes that draw their own circles log theirs through `ctx.recordWallContact()` (the Circle Illusion; the Collision Playground its circle container as wall 0, every impact that sounds – an orb resting or pressed against it by the pile does not). `components/simulator/wobbleRenderer.ts`'s `WobbleLayer` copies the new contacts into a `WobbleField` every frame and samples, per wall that is still moving, d(φ, t) = s·e^(−age/τ)·cos(2πf·age)·½[B(φ − φ₀ − c·age) + B(φ − φ₀ + c·age)] at 64 angles (two raised-cosine bumps leaving the contact point both ways, ringing in and out and decaying: |d| ≤ |s|·e^(−age/τ)); the canvas traces a wobbling wall through them – `strokeArc()` / `fillSector()` / `pathArc()` in the ring, Shatter, Color Match, Target and wall-glow drawing, `traceCircle()` in the illusion renderer and `drawCollideArena()` – and keeps the plain arcs for every still wall, so with Wobbly Walls at 0 nothing changes. The amplitude is `WOBBLE_FRACTION` of the wall's radius (at most `WOBBLE_MAX_PX`) × the setting, and nothing moves a wall further: a contact within `WOBBLE_MERGE_MS` and `WOBBLE_MERGE_RAD` of a hit the wall already has (a ball resting or wedged against it – Shatter's rings –, growing into it, a crowd pressing on it) refreshes that hit – the stronger strength, the newer time and angle – instead of stacking another wave on it, and the field passes the sum of a wall's waves through `saturateWobble()` (unchanged up to `WOBBLE_KNEE`, then a tanh easing toward 1). `data-wobble` counts the walls wobbling in the frame; `data-wobble-max-px` and `data-wobble-peak` hold the largest displacement drawn this run (px, and as a share of that wall's amplitude).
- **Settings, finder, UI**: `ilType`, `ilBalls`, `ilRings`, `ilDepth`, `ilPainters`, `ilPattern`, `ilSpeed`, `ilTracks`, `ilReveal`, `ilCycles` and `wallWobble` (URL `ilt`, `ilb`, `ilr`, `ild`, `ilp`, `ilpt`, `ils`, `iltr`, `ilrv`, `ilc`, `wob`) are written and read by `writeIllusionParams()` / `readIllusionParams()` and validated for presets by `resolveIllusionFields()`; a change of the type, the counts, the picture, the speed or the cycles restarts the mode with a fresh seed (the tracks and the reveal follow live; a Ball Size change restarts the nested and white-spaces types). `illusionRunNeverFinishes()` (nested; lines and rings with the cycles at never) hides the finder, `illusionFixedDurationSec()` (cycles × cycle length) makes it explain a fixed length (`Simulator.finderFixedIllusion`), and `createEngineForSettings()` builds the mode from `ModeSettings.illusion`, searching `ILLUSION_FINDER_BATCH` seeds per frame. The panel blocks are `sections/IllusionSection.tsx` (Mode row; its keys join `SECTION_KEYS.ball`) and `sections/WallWobbleSection.tsx` (the Visual section while a circular wall is in play, `wallWobbleOffered()`: the modes of `WOBBLE_MODES`, the Collision Playground only with its circle container and not the lollipop ring). The canvas mirrors `data-illusion-*` (type, bodies, notes, cycles, alignments, collisions, coverage, pattern, finished, circle error, a probe point inside the picture and one on the paint) and `data-wobble`.
- **Tests and smoke**: `tests/illusion.test.ts` covers the settings (URL, presets, ranges), the rolling-circle maths (every ball on the hidden circle and evenly spaced for any N, θ and β; the rim touches), the lines, rings, nested and white-spaces runs in the engine (notes per cycle, exact positions, the outward ripple and the alignment, containment and energy, determinism, the paint never entering a picture, the climbing notes, the reveal, rays that stop at the picture, the stall rule, big painters and one or two painters reaching every pocket, a resize) and the finder; `tests/wobble.test.ts` the wave (a bulge of exactly the strength at the contact point, the decay bound, the bumps travelling both ways), the field against the closed form, the merging of one push's contacts and the saturation, the contact log and its generations, the ring hits logged by Classic and the Collision Playground's circle container (none for the box), the cap in Shatter, Grow and Multiply runs and the setting; `tests/extras.test.ts` holds the mode's fingerprint. The smoke test (section 23) checks the preview and the card, the URL and the controls, the search box, the finder, a lines run on the hidden circle with scale-degree notes, a rings alignment, the nested circles colliding and wobbling, a white-spaces reveal read back from the canvas pixels, two painters on the cross and big painters on the smile revealed, the frame rate of every type, Wobbly Walls in Classic, the cap in Shatter and the Collision Playground's wobbling circle (offered for the circle, not the box).

### Rigged outcomes
Guaranteed results: finder outcomes plus two hard constraints of the cinematic director. Everything is deterministic and, while off, the engine takes exactly its old path (`tests/rigged.test.ts` compares trajectories).

- **The rig** (`src/lib/physics/rigged.ts`, `RigDirector`, owned by the director as `CinematicDirector.rig`): the settings `neverEscape` (URL `ne`) and `forcedWinner` (a team slot, −1 off; URL `fw`) – `RiggedConfig`, `DEFAULT_RIGGED`, `resolveRiggedConfig()`, `RIGGED_RANGES` – travel in `PhysicsConfig` like the physics extras, so the seed finder's headless engines copy them. Once per step `engine.update()` calls `rig.beginStep()` (the rules in effect for the mode – `RIG_ESCAPE_MODES`, `WINNER_MODES` – and the world the steering predicts with); with both off it returns false and nothing else runs. In `engine.ts` (`// --- rigged ---` blocks) `processWallCollisions()` refuses a gap pass through a wall that `rig.closes()` to the ball (counted as a *seal* – the safety net), lets a broken wall hold a ball in (`holdsBroken()`: a forced winner's outermost wall broken open in Shatter or Color Match), steers the rebound after the drama nudge (`director.steerRigged()` → `rig.steer()`), records the chosen team's passes (`notePass()`) and reports bounces right beside a closed gap as near misses (`nearMissAt()` → the camera's near-miss event); `smashWall()` and the multiplier smash leave a closed wall alone; `rig.guide()` bends, every step, a flight heading for a closed gap that no rebound set (a spawn, a deflection); a per-step backstop (`markInside()` before the sub-steps, `holdInside()` after them) puts a ball back that anything else – a push-out, a pair correction – carried across its closed way out; `scanEscapes()` reports escapes (`noteEscape()`: the run's first escape – `engine.getFirstEscapeMs()`, tracked with the rig on or off – and whether the chosen team is out). Modes that break walls themselves ask `ctx.isWallSealed(ball, wallIndex)` first: Shatter does not damage a closed wall, Color Match keeps its last segment. "Never escape" closes the outermost intact wall to every ball; the forced winner closes to the other teams every wall (Classic, where passing breaks a wall and all balls escape in the end, so the walls decide) or the outermost one (elsewhere) until the chosen team has passed it. The way out itself – the outermost wall – is not opened by a pass (the chosen ball enters its gap while still inside) but only once a ball of the chosen team has escaped (the escape scan); in Shatter and Color Match, where that escape ends the run, it stays closed to the others until the end (`EXIT_LOCKED_TO_END` – the scan counts an escape at +10 px, the modes finish at +20 px / +30 px, and a trailing ball slipping out in between would level the escapes and let the walls decide), and in Multiply for good. In Classic the rivals cannot clone themselves on x2 BALLS orbs (`rig.blocksClone()` → `MultiplierRuntime.touch(ball, noClone)`: the orb floats on), so no team out-escapes the chosen one. A merge (ball interaction) that absorbs the chosen team's ball hands the merged ball to that team (`mergeBallPair()`), and should the chosen team still lose its last ball without escaping, `markInside()` releases the locks so the run can end instead of holding the others in forever. With "never escape" on nobody escapes, so the forced winner is off in the modes it wins by escaping (`WINNER_NEEDS_ESCAPE`: Multiply, Shatter, Color Match – `forcedWinnerApplies(mode, balls, team, neverEscape)`, so the rig, the note under the canvas and `data-rig-winner` agree, and the panel says why: `Controls.forcedWinnerNeverEscape`); Classic keeps both – the chosen team breaks every wall while nobody escapes.
- **Steering**: `rig.fly()` integrates a ghost of the ball – gravity with the ball's own weight, wind, air drag, the ring modes' cruising boost; the walls turning as in the engine; gaps passed on walls open to the ball – up to its first bounce. `steer()` keeps the natural angle when that bounce is fine, else tries angles 3° at a time within 80° of the wall's normal until the bounce is clear of every closed gap by a margin that grows with the flight time – the nearest one lands just beside the gap, a near miss – and turns the chosen ball of a forced winner through a passable gap within 12°. `MAX_FLIGHTS_PER_STEP` caps the predictions a step (crowds stay cheap; past it the seal still holds). `engine.getRigView()` exposes the counters (seals, steers, guides, near misses).
- **Finder outcomes** (`src/lib/simulation/outcomes.ts`, pure): a `FinderOutcome` (kind, clip, target second, team) judged on a `RunSummary` (time followed, finished, first escape in real time, team totals) by `outcomeSettled()` (stop early), `outcomeMatches()`, `outcomeMiss()` (the closest run so far) and `outcomeClipSec()` (the recording length of a found run); `availableOutcomes()` lists what a mode can search for (the run length only while the run can end). `finder.ts` sums a seed up in `simulateOutcomeRun()` and `findByOutcome()` searches the seeds in the usual order with a per-frame time budget; `findSimulation()` takes `request.outcome`, and the duration search resolves `endless` when never escape keeps an escape mode from ending (`rigNeverFinishes()`).
- **UI**: `components/simulator/FinderOutcomeFields.tsx` (the Outcome select, the escape-time slider and the team to win, plus the outcome texts of the panel and the canvas overlay), `sections/RiggedSection.tsx` (the Rigged Outcomes group with its storytelling warning; search keys `RIGGED_KEYS`) and `riggedRenderer.ts`, which mirrors `data-rig-never-escape`, `data-rig-winner`, `data-rig-seals`, `data-rig-steers`, `data-rig-guides`, `data-rig-near-misses` and `data-first-escape` onto the canvas – the rig draws nothing, and the page notes it under the canvas where the recording does not see it. Strings: `Controls.rigged*`, `Controls.neverEscape*`, `Controls.forcedWinner*` and the `Rigged` namespace in every messages file.
- **Extending**: for another outcome add a kind to `FINDER_OUTCOMES`, its rules to `outcomeHorizonMs()`, `outcomeSettled()`, `outcomeMatches()`, `outcomeMiss()`, `outcomeFigure()`, `outcomeClipSec()` and `availableOutcomes()`, whatever it needs to `RunSummary` (collected in `simulateOutcomeRun()`), its field and texts to `FinderOutcomeFields.tsx` and the `Rigged` messages, and cases to `tests/rigged.test.ts`. To rig another mode add it to `RIG_ESCAPE_MODES` / `WINNER_MODES` (and `ESCAPE_FINISH_MODES` when an escape ends it); if it breaks walls itself, ask `ctx.isWallSealed()` before breaking one open. The smoke test (section 24) drives the controls, the URL, a rigged 8× run, forced three-team races (Classic; Shatter, where nobody else gets out; merging balls, which still end; x2 BALLS orbs, which do not let the rivals out-escape the chosen team), Never Escape switching the forced winner off in Shatter but not in Classic, and the outcome searches; `tests/rigged.test.ts` runs 20 seeds of Shatter and Color Match races with 2–6 teams each.

### Timeline keyframes
`src/lib/simulation/timeline.ts` holds the model, the maths and the engine side of the automation; `tests/timeline.test.ts` covers the interpolation and the integration, the validation, the URL form, presets and the engine (every step, frame-rate independence, the finder, bases, gaps in place, runs without keyframes unchanged, restarts with breathing walls, the integrated rates, swept amplitude jumps, Ball Size ramps over grown, merged and split balls).

- **Settings and URL**: `keyframes` in `SimulatorSettings` is a list of `Keyframe` – `{ time, key, value }`: seconds of simulation time (0–120 in 0.1 s steps, `TIMELINE_RANGES.keyframeTime`), one of `TIMELINE_KEYS` – the numeric settings the engine takes live without restarting the run: `gravity`, `ballSpeed`, `ballRadius`, `rotationSpeed`, `gapSize`, `airDrag`, `windX`, `windY`, `spinStrength`, `rotatingGravity`, `wallBounciness`, `breathingAmplitude`, `breathingSpeed`, `bumperBoost` (the wall count and the mode blocks rebuild the playfield, so they are left out) – and a value inside the setting's `RANGES` entry, on its step. `sanitizeKeyframe()` / `resolveKeyframes()` validate links and presets (unknown settings dropped, numbers clamped and snapped, one keyframe per setting and time – the later one wins –, at most `MAX_KEYFRAMES` = 40, sorted by time); `timelineKeyOf()` also takes a setting's URL code and the aliases `ballSize`, `wallRotationSpeed`, `wallGap`. `serializeKeyframes()` / `parseKeyframes()` are the `kf` URL form: one group per setting – the setting's own URL key (`TIMELINE_KEY_CODES`: `g`, `s`, `r`, `rs`, `gap`, `drag`, `wx`, `wy`, `spin`, `rg`, `wb`, `bw`, `bws`, `obb`) followed by its time / value pairs, joined by `_` – and the groups joined by `*`, characters a URL keeps as they are: `g_0_300_10_1200*r_0_8_4_20`. settings.ts calls `writeTimelineParams()` / `readTimelineParams()` and, for presets, `resolveTimelineSettings()`; a mode change keeps the keyframes (`timelineCarryOver()`).
- **Interpolation**: `interpolateTrack(times, values, t)` is linear between two keyframes, gives the first value before the first keyframe and the last one from the last keyframe on; `compileTimeline()` groups a list into `TimelineTrack`s (one per setting, ascending distinct times) and `timelineValueAt()` / `timelineValuesAt()` evaluate a list at a second.
- **Engine**: the keyframes travel inside the physics config (`PhysicsConfig.timeline`), so `engine.setConfig()` hands them to the engine and the seed finder – which copies the page engine's config – replays a found seed with them. The engine's `TimelineRuntime` compiles them and applies the values of the simulation second that differ from the config at the start of every fixed step, and at 0 s when a run starts, before its rings and balls are built (`clear()`, which sets the clock back to 0 first: the breathing pulse that `setConfig()` re-applies must be the one of 0 s – at the old run's clock it left a stale pulse scale that the new rings' base radii were divided by, and a restarted or replayed run played on other rings than the finder's), through the normal `setConfig()` path (`patchAt()`); `update()` re-reads the physics extras after it, so a keyframed wind or drag acts in the same step. A breathing change the keyframes make there (a new amplitude) does not move the walls at the start of the step but in its first sub-step, whose collision pass sweeps the whole move (`deferBreathing`, `sweepWalls`) – breathing walls stay collision-safe whatever the keyframes do. Because it is per step on the simulation clock, the automation is the same whatever the frame rate, the playback speed or the camera's slow motion. Nothing is allocated while no value changes, and a run without keyframes takes the old code path. A page patch for an automated setting only becomes its base value (`prepare()`), which the setting gets back once its keyframes are removed – so the automation never writes into the settings and a slider moved meanwhile is not lost. The gap size is special: `setConfig({ gapSize })` rebuilds the rings (and forgets the broken ones), so a keyframed gap resizes the gaps in place instead (`gapAt()`, `resizeGaps()`: every gap keeps its start angle, in the modes whose rings are built from the gap size – Classic, Accumulation, Multiply). `engineTimelineOf()` leaves the rotation speed's keyframes out while the rotation is switched off. The rate settings are special too: the engine turns `rotatingGravity` and `breathingSpeed` (`TIMELINE_RATE_KEYS`) into a phase – gravity's direction, the pulse – so while one is keyframed it integrates the keyframes (`TimelineRuntime.integralAt()` / `integrateTrack()`: the exact trapezoid sum of the piecewise-linear track since 0 s – degrees turned, pulses so far) instead of multiplying the rate by the time, which would move the phase at rate + t · rate′ (gravity turning backwards while its rate falls, walls pulsing faster than the slider's range) and jump with every step's new rate; without keyframes the rate × t path is untouched (`engine.getTimelinePhase()`, `engine.getGravityAngle()`). The Ball Size goes through `setConfig({ ballRadius })`, which sets every ball to `ballRadius × radiusScale`, so every ball whose size a mode or an interaction changes keeps its `radiusScale` up to date – Grow's growing ball, merged and split balls, like the multipliers, Box, Collide, Double Pendulum and Illusion – and a Ball Size ramp scales it instead of resetting it (Grow holds a scaled-up ball to its ring's cap in `onPreUpdate()`).
- **Page**: Simulator.tsx sends `engineTimelineOf(settings)` to the engine (new keyframes drop a found seed, like a new obstacle layout; a preset's go in with it before its run is built) and, through `useTimelineLivePublisher()` (`components/simulator/timelineLive.tsx`), publishes the live values of the automated settings ten times a second on the engine's clock into the `timelineLive` store. `Slider` (ControlPrimitives.tsx) looks its label key up (`TIMELINE_SLIDER_LABELS`) and, for an automated setting, shows the live value in the slider's own format (`formatTimelineValue()`), holds the thumb there, locks it and adds the AUTO badge; the hand-drawn rotation-speed slider uses `TimelineRangeInput` / `TimelineValueText`. The panel is `components/simulator/sections/TimelineSection.tsx` (search keys `TIMELINE_SECTION_KEYS`): the setting picker (the settings the panel shows in the mode – `timelineKeyShown()`), the setting's own value (the value a new keyframe gets), "Add keyframe at … s" (`timelineLive.now()`, the engine's clock, snapped to 0.1 s) and the list (time and value fields that commit on Enter or blur, ✕). `components/simulator/TimelineBar.tsx` is the bar under the canvas: a lane per automated setting with the value curve and the markers (`TIMELINE_KEY_COLORS`), the playhead moved every frame in the DOM, a legend; it mirrors `data-timeline-time`, `data-timeline-live`, `data-timeline-engine` (the values the engine really uses), `data-timeline-phase` (a keyframed rate's integrated phase) and `data-timeline-ball-radius` (the largest ball) for the smoke test (section 25: a link fills the section and the bar, the sliders lock with the AUTO badge, a run at 8× reaches the keyframed values without touching the link's settings, a keyframe added at the current time, an edit and a removal land in the link, the search box and a mode change; a seed found mid-run with breathing walls replays as found, a keyframed gravity rotation never turns backwards, a breathing speed ramp keeps every ball in Lines' ring, a Ball Size ramp scales Grow's growing ball).
- **Add an automatable setting**: it must be a numeric setting the engine takes live through `setConfig()` without rebuilding the playfield. Add it to `TIMELINE_KEYS`, `TIMELINE_KEY_CODES` (its URL key), `TIMELINE_SLIDER_LABELS` (its slider's label key), `formatTimelineValue()` and `TIMELINE_KEY_COLORS`, and – if the panel shows it only in some modes – to `timelineKeyShown()`. A rate the engine turns into a phase (rate × time) also goes into `TIMELINE_RATE_KEYS`, and the engine uses `timeline.integralAt()` for it while it is keyframed.
- **With the rigged outcomes**: both travel in the physics config, so the rig steers and seals with the keyframed values of each step (`rig.beginStep()` runs after the keyframes are applied, with the re-read extras) and the finder's engines copy both. `tests/riggedTimeline.test.ts` checks that Never Escape holds while keyframes open the gaps, speed the balls up and pile on gravity (Classic, Accumulation, Multiply), that a Forced Winner still wins a keyframed race, that the page's engine and the finder's play the same rigged, keyframed run (the outcome search too), and that `ne`, `fw` and `kf` survive links, presets and mode changes together.

### String Battle (oddplayground)
The oddplayground family's first mode ("Tiny random simulations. Seeds, rules, chaos."): `src/lib/physics/modes/stringBattle.ts` holds the settings, the pure geometry and rules and the `StringBattleMode` plugin; `tests/stringBattle.test.ts` covers them (anchors, the cut / touch tests, lives, shields, elimination, the verdict, the finale, the rig, determinism, the finder, the sounds).

- **Playfield**: the mode owns its ring (the `"none"` ring layout, like the rhythm modes) – radius `arenaRadius()`, the obstacle editor's frame. `onBallStep()` reflects a ball off it with a seeded scatter (`SB_SCATTER`, never flatter than `SB_MIN_INCIDENCE`) at its cruising speed (Ball Speed × `SB_SPEED_SCALE` × a seeded 0.9–1.1 drawn afresh at every bounce × the finale factor), so the engine's slow-ball boost is off (`ballsMayRest`) and the balls feel no gravity (`gravityScale` 0); ball-to-ball rebounds stay the engine's pair loop. Every rebound anchors a thread (`SbString`: the ring point on the impact's radius) that follows its ball; beyond `maxStrings` the oldest becomes a fading ghost. A resize (`onConfigChange()`) scales the ring, the anchors, the balls and the effects together: it undoes the engine's stretch of the balls with the canvas (a portrait-to-landscape turn would push them out of the ring) and moves each fighter's previous position with its ball, so the cut rule never mistakes the resize for a slash across the arena.
- **Rules**: after every sub-step `onPostSubStep()` tests every ball against every enemy thread – `cutsThread()` (the cut rule: the ball's own move from its last position crosses the thread's cuttable part, `cuttableSpan()`: all of it – `SB_CUT_SPAN` is 1; the helpers take a smaller anchor-side share as an argument – but never the stub next to its ball, `SB_REACH_GAP` past the two bodies) or `touchesThread()` (the touch rule: overlap) – and `onBallCollision()` compares the pre-collision speeds (the collide rule; the cruising factor is drawn afresh at every ring bounce, so the fastest ball at spawn has no lasting edge). A lost life starts a shield (`SB_INVULN_MS`). A ball at 0 lives is removed, its threads dissolve, its killer scores; the last one standing – or the survivors with the most lives at the clip limit (`timeoutLeaders()`) – win. Sounds are `SoundEvent`s: a bounce note per ball (`bounceFrequency()`, C-major pentatonic), and `sbSound: "pluck" | "shatter"` events the page hands to `ToneGenerator.playStringBattle()` (`src/lib/audio/stringBattleTones.ts`: a Karplus–Strong pluck with a snap, a seeded noise burst with shard tinkles – or the chosen wall-break clip).
- **Scores, finder and rig**: the balls carry their slot as `team`; the mode credits the engine's team stats through new optional `ModeContext` hooks – `creditBounce()`, `ctx.creditWallBreak()` (kills) and `creditEscape()` (the win) – so `teamResult()`, the teams winner banner, `simulateOutcomeRun()` (one team per ball) and the mode's own verdict agree. `BATTLE_WINNER_MODES` (rigged.ts) makes `forcedWinnerApplies()` and `availableOutcomes()` offer the forced winner and the finder's winner outcome – judged at the battle's end, not the clip's (`winnerNeedsEnd()` in outcomes.ts: the run is followed up to the finder's longest run, dropped as soon as the chosen ball is out, and matches only when the finished battle crowned it; the page then records the whole battle plus its banner); `effectiveBallCount()` returns `sbBalls` in this mode. The forced winner is the mode's hard constraint (`rigAbsorbs()`: its chosen ball never loses its last life and never falls behind; under the collide rule it wins such a clash). `noteNearMiss()` (slow motion on the final cut) and `noteImpact()` (a shake per shattered ball) feed the cinematic camera, which draws the balls between steps here too (`SLOW_VIEW_MODES`).
- **Drawing**: `components/simulator/stringBattleRenderer.ts` (`StringBattleLayer`): the ring, the threads (glowing from anchor to ball – all of it cuts and burns; neon: endless lines through `lineThroughRect()` painted into a never-cleared layer), ghosts, halos, bodies with their lives, shatter shards from a seed, the badge, the HUD (`sbHudShown()`: the web style), the banner without a roster and the neon glitch bars (`applyGlitch()`, last in the frame). With a roster `teamsRenderer.ts` pads it to the balls with the palette and hides its scoreboard under the HUD. The panel block is `components/simulator/sections/StringBattleSection.tsx` (search keys `STRING_BATTLE_KEYS`); the settings are `sbBalls`, `sbLives`, `sbMaxStrings`, `sbRule`, `sbStyle`, `sbDuration`, `sbFinaleSpeed`, `sbWobble`, `sbBadge`, `sbHud` (URL `sbn`, `sbl`, `sbm`, `sbr`, `sbst`, `sbd`, `sbf`, `sbw`, `sbb`, `sbh`). The mode cards group it under the new `battle` family (`MODE_CATEGORY_IDS`, heading `Headings.modesBattle`) – the family the other oddplayground duels join. The obstacle editor and the multiplier pickups stay with the ring modes: the thread geometry assumes one clear ring.

### Power Layers
`src/lib/physics/modes/powerLayers.ts` holds the settings (URL keys `pll`, `plq`, `pld`, `plsp`, `plb`, `plp`, read and written by `readPowerLayersParams()` / `writePowerLayersParams()`), the power sequences (`PowerSequence`, `sequencePowers()`), the plan (`buildPowerPlan()`: every hit's power and the layers it destroys, drawn at init), the timing, the flight maths, the notes and the `PowerLayersMode` plugin; `src/components/simulator/powerLayersRenderer.ts` draws it and `sections/PowerLayersSection.tsx` is the "Power layers" block of the Mode row. `tests/powerLayers.test.ts` covers the sequences, the layer accounting, the timing, the notes, the settings and full engine runs (end detection, determinism, sounds, the finder).

- **Timing**: hit k lands at `hitTimeSec(k, T) = T·(k + ½)` with `T = bouncePeriodSec(speed)`; after the last hit the ball leaves the field within T/2 and the run finishes `FREEDOM_HOLD_SEC` later, so a run lasts `runFinishSec(hits, T)` = hits × T + 1.8 s. `powerLayersFixedDurationSec()` gives it for every sequence but chaos (the finder then explains a fixed length), and `getPowerLayersProgress().plannedMs` – known once a chaos seed's plan is drawn – is the finder's duration predicate (`simulateSeed()` returns it without stepping the run).
- **Flight**: the vertical motion is analytic on the mode's own clock: between two hits the ball rises from the old top to the ceiling and falls to the new top, and `ceilingSpeed()` solves the speed it meets the ceiling with so the two legs take exactly T under `arcGravity()` (a fraction of 8·d₀/T², so even the first, shortest bounce can be timed; the Gravity setting picks the fraction). The drift (x) is integrated per sub-step and kicked by `ctx.random()` at every hit. The engine's extras, keyframes and ball size never shift a hit; a resize keeps the run.
- **Add a sequence**: add its id to `PL_SEQUENCES`, its rule to `PowerSequence.advance()` (and its first power to the constructor), its rule text to the renderer's labels (`PowerLayersLabels.rules`, `Simulator.canvasPlRule<Name>` in `messages/*.json`) and its button to `SEQUENCE_OPTIONS` in the section.
- **Sound**: the mode queues ordinary sound events – a `hit` with the level's `frequency` (`levelPitch()`), a `hit` chord plus a `gap` for a big hit (`BIG_HIT_LAYERS`), a chord plus a `multiplier` arpeggio for the empty stack and a `gap` at freedom – so melodies, instruments, hit samples, the slicer, the beat lock and the music bed apply as in every mode.

### Fast export
The ⚡ **Fast export** renders a clip offline instead of recording the screen. The pieces:

- **Planning** – `src/lib/recording/fastRenderPlan.ts` is pure and covered by `tests/fastRender.test.ts`: the time model (the engine and the canvas always advance in 60 Hz frames; simulation frame *j* is drawn at *j*/60 s, its sounds are scheduled there, and a 30 fps export keeps every second frame, so its sounds stay on the 60 Hz grid), frame timestamps and durations that add up exactly, a key frame every 2 s, `offlineCanvasLayout()` (the world is drawn at the scale that makes its centred square exactly the export's shorter side, so frames are copied 1:1), `videoBitrate()` (0.1 bit per pixel and frame, 2–20 Mbit/s), the codec strings with the lowest H.264 / VP9 level that fits the frame (`avc1.42001f` for 720p30, `avc1.42002a` for 1080×1920 at 60 fps) and `selectExportFormat()` – MP4 with H.264 (Baseline, Main, High) and AAC, then WebM with VP9 or VP8 and Opus, then MP4 with H.264 and Opus, each codec probed once through `VideoEncoder` / `AudioEncoder.isConfigSupported()`, null when nothing fits –, the audio chunks, the progress and `ExportEndTracker`, which ends the clip exactly like the page ends a real-time recording: the run's own finish, the page's holds (a finished picture, the Circle Illusion's reveal, then the escape replay the canvas plays, then the winner / multipliers banner), then 0.5 s – or the clip length, with up to 12 s more when the run is already over but still holding.
- **The canvas** – `Canvas.tsx` is exported through `withFastRender()` (`components/simulator/fastRenderCanvas.tsx`): while the page's `FastRenderHost` has a job, a second, hidden instance of the canvas is mounted with every prop the page gives the visible one (frozen when the export starts), on the export's engine and with the `offline` prop. In offline mode the canvas starts no animation loop; its draw routine – the same function – is called once per frame by the export (`OfflineFrameRenderer.renderFrame()`), reads the export's clock instead of `performance.now()`, draws the world at the export's scale and records from its first frame (the Top / Bottom Text is left to the export frame, captions run on the clip's clock). It also hands the export `noteWallBreak()`, `setSongProgress()`, `holdsEndScreen()`, the export-frame background painter and `ready()` (the ball image, background and paint pictures are decoded). A new canvas prop is therefore in the export without further work; a new per-frame value the page pushes through `CanvasHandle` must be added to `OfflineFrameRenderer` and driven in `renderFast()`.
- **The frame loop** – `renderFast()` in `src/lib/recording/fastRender.ts` builds a fresh engine with the page's `createEngine()` (Simulator.tsx: `new PhysicsEngine({ ...page.config })`, the run's seed, the particle style, the Picture Paint options and beat, then `initEngineForMode()` – an engine setter the page applies outside the config and `initEngineForMode()` must be added there too), then per frame: draw, `engine.consumeSoundEvents()` → `playSoundEvent()` (the page's dispatch from the sound loop in Simulator.tsx – a new `SoundEvent` type must be handled in both), the slicer's progress, the end tracker; every exported frame is composed like the real-time recorder composes it (`drawRecordingFrame()` in recorder.ts, shared by both) into a `VideoFrame` and encoded (backpressure keeps at most a few frames queued; the loop yields through a `MessageChannel`, so the page stays responsive and a background tab does not throttle it). Each frame runs in a sandbox where `Math.random` is a generator seeded from the run's seed and `Date.now()` is the export clock, so the engine's visual randomness (confetti), the renderers' (shake, banners) and the hit-glow timestamps replay identically: the same seed gives the same frames, which the export proves with `digest` (FNV-1a over sampled, downscaled frames, mirrored as `data-fast-digest` on the panel for the smoke test).
- **The sound** – `ToneGenerator.createOfflineTwin()` copies the page's sound set-up (volume, instruments, scale, beat lock – its grid starts with the clip –, melody from its first note, hit sample, wall-break clip, song slicer from the start of the song, music bed from its start offset) onto an OfflineAudioContext seen through `clockedAudioContext()` (`src/lib/audio/offlineContext.ts`: `currentTime` is the export clock, the context counts as running), so every sound of the clip is scheduled through exactly the code the page plays live and rendered in one go once the frames are done; the bed stops when the page would show its end screen. `HitSampler` forgets voices that have played out by their end time (an offline clip is scheduled before any `ended` event fires), so only overlapping voices are stolen. A new sound player in the ToneGenerator must be copied in `createOfflineTwin()`. The mix is cut to the video's length, encoded with `AudioEncoder` in 1024-frame chunks and muxed after the video (mp4-muxer with `fastStart: "in-memory"`, webm-muxer interleaves on its own).
- **The page** – Simulator.tsx (`startFastExport()`) pauses the run for the export and resumes it afterwards (the visible canvas keeps its last frame meanwhile, so the export has the main thread to itself), throttles the progress to ~8 updates a second and downloads `jumpingballslive-export.mp4` / `.webm`; `sections/FastExportSection.tsx` has the button (with progress bar, frame count, speed and Cancel) that Controls.tsx renders under Record Video, and the Recording section's frame-rate picker (`fastExportFps`, 30 or 60, URL `xfps`, snapped on the way in). Without WebCodecs (`fastRenderSupported()`) or without a usable codec pair the button explains it and starts Record Video instead; a run played by hand (a Beat Runner without Auto Jump, a Paddle Keep-Up without Auto Platform – `jdmRhythmPlayedByHand()`) has no player in the export's fresh engine, so the button is off for it with a note (`handPlay`, `data-fast-hand-play`) and `startFastExport()` refuses it. The physics of an export is the seed finder's (no audio-reactive gravity), so a found run lasts in the export exactly what the finder promised; the canvas' audio-reactive outer ring is not drawn in it.
- **With the race and the arena games**: their settings reach the export's engine through `initEngineForMode()` and their drawing through the `race` prop and the labels (no new `CanvasHandle` value); `playSoundEvent()` plays a race event's chime or fanfare (`playRaceArpeggio()`, copied with the rest of the synth by `createOfflineTwin()`), and `fastExportEndHolds()` holds a Battle Royale / Capture the Flag winner banner for `ARENA_WIN_HOLD_SEC` like the page. The cup table drawn in an export adds the exported race to the cup kept in this browser without storing it, under the page's run key of that race (`FastRenderJob.raceKey` → `CanvasRaceOptions.runKey`, see `exportRaceOptions()`): the export's engine is new and counts its races from 1, so a race the page has already scored is shown as scored, not added a second time.
- **With String Battle and Power Layers**: their settings reach the export's engine through `initEngineForMode()` (`stringBattleSettingsOf()`, `powerLayersSettingsOf()` – the level notes follow the Sound section's scale and root) and their drawing through the labels; `playSoundEvent()` plays a String Battle pluck or shatter (`playStringBattle()`; the offline twin builds its own noise burst for the offline context), and `fastExportEndHolds()` holds the last shatter, the ring flash and the winner banner for `STRING_BATTLE_FINISH_HOLD_MS` like the page. Power Layers needs nothing more: its freedom celebration is part of the run (`FREEDOM_HOLD_SEC`) and its sounds are ordinary events.
### Project files and share codes
`src/lib/project.ts` (the file format) and `src/lib/shareCode.ts` (the codec) are pure and covered by `tests/project.test.ts` and `tests/shareCode.test.ts` (round trips, validation, versions, size limits, damaged and oversized input); `src/lib/base64.ts` holds the chunked base64 / base64url helpers both use.

- **The file**: `{ format: "jumpingballslive-project", version, name, app, createdAt, settings, extras, assets }`. `settings` is the whole `SimulatorSettings` object, so a new setting – and every list setting such as `obstacles`, `keyframes`, `captions` or `teams` – travels without any change here. `extras` holds page state that is not a setting (`ballEmoji`, the built-in `melody` id). `assets` maps a `ProjectAssetKind` (`PROJECT_ASSET_KINDS`) to `{ name, type, size, data }` with `data` in base64; `size` is checked against the decoded bytes on import, pictures (`IMAGE_ASSET_KINDS`) must have an image MIME type, unknown kinds (from a later version) are ignored and damaged ones left out (`skipped`, reported in the panel). An uploaded wall-break sound's `blob:` URL is stored as none; its medium selects the upload again.
- **Validation**: `parseProject()` refuses non-JSON, other formats and newer versions, lifts older ones through `MIGRATIONS` (bump `PROJECT_VERSION` and add a step there when the layout changes), then `resolveProjectSettings()` keeps only known fields of the right type, clamps numbers to their `RANGES` and runs `presetToSettings()`; a custom hit sample stays selected only with its medium, a picture background without its picture falls back to the theme's, and the wall-break sound can only be a built-in clip. `projectSizeCheck()` warns above `PROJECT_WARN_BYTES` (25 MB) and refuses above `PROJECT_MAX_BYTES` (100 MB).
- **Page**: `components/simulator/useProjectFiles.ts` lists the loaded media (the original files of the audio uploads are remembered in `projectUploadsRef` by the upload handlers in Simulator.tsx; pictures are data: URLs already), builds and downloads the file, and imports one: `loadPresetSettings()` (the preset loader, shared with presets and share codes), then each medium through the same handlers the upload buttons use, then `projectMediaPatch()` so the project's own switches (hit sound mode, slicer on/off, background type) win over what loading the media switched on. `sections/ProjectSection.tsx` is the panel block (search keys `PROJECT_KEYS`), `ProjectDropZone.tsx` wraps the panel for drag-and-drop – a project file is caught in the capture phase (`onDragOverCapture` / `onDropCapture`), so it opens as a project even when it is dropped on one of the panel's own drop zones (none of them takes JSON); every other file goes through to them. To add a medium: a kind in `PROJECT_ASSET_KINDS` (plus `IMAGE_ASSET_KINDS` for a picture), a line in `listMedia()` and in `applyProject()`, a `projectMedium…` label in `messages/*.json`.
- **Share codes**: `encodeShareCode(settingsToSearchParams(settings))` → `base64url(deflate-raw(JSON))`, where the JSON maps the long link's parameter names to their values (canonical numbers as numbers), so any setting with a URL key is shareable by code too. `components/simulator/shareLinks.tsx` keeps the short link of the current settings ready (so the clipboard write happens inside the click), decodes a `?c=` link once on load – `mergeShareParams()` puts the link's other parameters over the code's – and shows a notice under the canvas when a code cannot be read. Decoding is capped (`SHARE_CODE_MAX_LENGTH`, `SHARE_PAYLOAD_MAX_BYTES` against deflate bombs) and accepts only a flat object of plain values.
- **With the fast export**: its frame rate (`fastExportFps`, `xfps`) is an ordinary setting, so a project file and a share code carry it and snap a foreign value onto 30 / 60 (`tests/fastExportProject.test.ts`); the ⚡ Fast export button waits while a project is being opened, whose settings and media arrive over several renders.
### Square Racing Grand Prix
`src/lib/physics/modes/race.ts` (id `race`, family `rhythm`) owns its playfield like Ball Drop and Glass Smash: it activates with the `"none"` ring layout, the racers are ordinary engine balls (`gravityScale` 0, `ballsMayRest`, `ballsPassThrough`), so drag, wind, pause, the playback speed and the recorder work unchanged, and the mode does the rest itself on the simulation clock. `components/simulator/raceRenderer.ts` draws it (Canvas.tsx scrolls the world by the race camera like Glass Smash and calls the layer in world and screen space); the panel block is `sections/RaceSection.tsx` (Mode row; its keys are searched with the Ball section).

- **Track** (`src/lib/physics/raceTrack.ts`, pure): `buildRaceTrack(width, height, settings, ballRadius, random)` lays out a corridor (`TRACK_X0`–`TRACK_X1` of the centred square the recorder crops to, whose side S is the layout unit, "one screen"; the left of the square is kept for the standings, the right for the mini-map) with the start grid above the gate (a seeded shuffle of the racers), then row after row picked by `pickRowKind()` from `ROW_WEIGHTS` (a featured kind weighs `FEATURED_WEIGHT` times more, a kind that just came `REPEAT_DAMPING` less) and built by its builder: staggered **pegs** (none closer to a wall than a racer can pass), a **funnel** (two arms down to one opening), one or two **spinners** (bars turning at 1.4–3.2 rad/s, their angle analytic – `setSpinnerAngles()` – so any step size gives the same angle), a **swap zone**, one or two **turbo pads**, two or three pinball **bumpers** and a shallow **gate** with one or two openings barely wider than a racer. Rows are at least `MIN_ROW_GAP` apart; every lap ends in the final sector (a swap zone `FINAL_ZONE_BEFORE` and a full-width turbo strip `FINAL_STRIP_BEFORE` screens before the lap line); more laps copy the lap's rows below it, each copy with its own pad and zone state (the loop is one long descent the same rows come round on); the finish closes the last lap and a run-off floor catches the finishers. The racer radius is the Ball Size scaled with the field (`racerRadius()`, the Ball Size itself on a 400 px field, at most 2.8 % of it), so the whole race is scale-free: the same seed runs the same race on any canvas size. Random numbers are drawn in a fixed order and recorded, so a resize before the first step lays the same track out afresh; later `rescale()` maps the track, the racers and the camera onto the new field.
- **Physics**: `onBallStep()` resolves the racer against the obstacles of the rows around it (`firstRowFrom()`, a binary search – only a row or two per racer) with the obstacle layer's maths (`resolveBallObstacle()`; a bumper kicks at `BUMPER_KICK`), clamps it to the walls, the ceiling and the run-off floor, applies the mode's gravity and a linear drag that caps the fall (`raceMotion()`: `RACE_GRAVITY` field sizes/s² and `RACE_VMAX` field sizes/s at the defaults; the Gravity setting scales both, the Ball Speed runs the whole race faster), fires the sensors – a pad boosts a racer once (`TURBO_BOOST`), a racer's centre crossing a zone's line arms or triggers it, the finish line is timed within the sub-step – and rolls the square (visual). `onPostSubStep()` bumps the racers into each other (equal masses, `RACER_RESTITUTION`) and places the sub-step's finishers in crossing order. `onPostUpdate()` updates progress and laps, kicks a racer that has not gained `STUCK_PROGRESS` in `STUCK_MS` (seeded), ranks the field (`rankRacers()` in `src/lib/physics/raceStandings.ts`: finishers by place, the pack by progress with a hysteresis of a racer radius, DNFs last; every overtake reported), times the gaps (`LeaderClock`: when the front reached each stretch, so a gap is the time since the leader was where the racer is), calls out passes (`CALLOUT_GAP_MS` apart, a lead change always), the final lap, a swap and the winner, eases the camera (`CAMERA_TAU`) toward the leader at `LEADER_VIEW` of the view – or the middle of the pack, keeping the leader in view – and runs the phases: countdown (`COUNTDOWN_MS`, the racers held on the grid), racing, podium (`PODIUM_MS`, confetti) once everybody is home or the stragglers are DNF (`dnfGraceMs()` after the winner) or at the time limit (`raceTimeLimitMs()`, kept in `RaceView.timeLimitMs`: `RACE_MS_PER_SCREEN` per screen of track – the track length × the laps – divided by the tempo and the gravity factor, never under `MAX_RACE_MS`, so even 20 screens × 5 laps at the slowest Ball Speed and Gravity finish; should nobody be home by then, the racers still racing are placed where they are – the favourite first – so there is always a winner, a podium and a fanfare, and a race nobody finished is never scored into the cup), the cup table (`CUP_MS`, with the cup on), done. Everything random comes from `ctx.random()`, so a seed replays exactly and Find Simulation times races (`RACE_FINDER_BATCH` seeds a frame).
- **Sound**: an obstacle hit queues a `"hit"` at `racerNote(i)` – a C-major pentatonic ladder from C4, one note per racer – with a level from the impact (a bumper plays the pinball ding an octave up, a pad a soft octave), at most `MAX_RACE_SOUNDS_PER_STEP` a step and one per racer per `SOUND_COOLDOWN_MS`; the countdown beeps A4 three times and GO an accented A5; a swap plays both racers' notes as one accented chord. A pass, second and third place and the final lap queue a `"hit"` with `race: "chime"`, the winner one with `race: "fanfare"`: the page hands those to `ToneGenerator.playRaceArpeggio()` (`src/lib/audio/raceTones.ts`: a rising root–third–fifth–octave chime rooted on the racer's note, a "ta-ta-ta-taaa, ta-TAAA" C-major fanfare), which goes the way a bounce goes – instrument (or the melody voice rooted on its next note), hit samples, the song slicer, scale snap, beat grid, music-bed ducking.
- **Staged winner** (`rcWinner`): the favoured racer never arms a swap zone (it would be pulled back), a zone it has not reached waits for it (only it can trigger the swap, jumping to wherever the arming racer is by then), turbo pads boost it `RIG_TURBO_FACTOR` harder, the last lap's final swap zone hands it the place of the first racer to reach it, and that lap's final turbo strip boosts it and drags everybody else (`RIG_STRIP_DRAG`). `tests/race.test.ts` checks the staged racer wins every seed it tries (8, 16 and two-lap races); the page says the race is staged under the canvas, never in the recording.
- **Roster and cup**: `src/lib/raceRoster.ts` names the racers – team i of the Teams roster (name, colour, emoji) for the first six, then `RACE_COLORS` and the translated colour names (`Controls.rcName1`–`16`). `src/lib/raceCup.ts` scores a race's finishing order into the cup (`addRaceToCup()`: F1 points, a count of every place for countback, a new cup when the grid size changes, a run key so a race counts once), ranks it (`rankCup()`: points, then countback, then racer number), validates what comes back from localStorage (`parseCup()`) and keeps the page's cup in `raceCupStore` (useSyncExternalStore-friendly). Simulator.tsx scores a race once it reaches its podium (the run key is a page prefix plus the mode's `runSerial`); the canvas draws the table with the race in it exactly once whether or not the store has caught up; the panel shows the cup's leader and a reset button. The title is `rcCupTitle` or, empty, the mix's name (`CUP_TITLE_KEYS`).
- **Drawing**: `RaceLayer.drawWorld()` draws only the rows in view (pegs in the wall colour flashing the hitter's colour, arms, spinners with their hubs, bumpers that swell, pads with running chevrons, zones with running stripes that show the armed racer), the gate with its countdown lights, the lap lines and the checkered finish; `drawRacers()` draws back to front (the leader on top) the trails, glow, rolling squares or circles with emoji or the racer's place, boost and swap flashes, the leader's crown and the front runners' names; faces from the Character group go on them too. `drawOverlay()` – in the square the recorder crops to, below the page's buttons live – draws the standings (rows eased toward their places), the mini-map (swap zones, pads, lap lines, the view window, a dot per racer), the newest callout, the countdown, the podium and the cup table. Text widths and truncations, emoji and glow sprites are cached. The canvas mirrors `data-race-racers`, `-phase`, `-leader`, `-winner`, `-finished`, `-passes`, `-swaps`, `-boosts`, `-hits`, `-lap`, `-camera`, `-order` and `-callouts`.
- **Settings and UI**: `rcRacers` (URL `rcn`), `rcShape` (`rcs`), `rcTrackLength` (`rcl`), `rcLaps` (`rclp`), `rcFeature` (`rcf`), `rcCamera` (`rccam`), `rcCup` (`rccup`), `rcCupTitle` (`rcct`), `rcWinner` (`rcw`), `rcStandings` (`rcst`), `rcMiniMap` (`rcmm`), written and read by `writeRaceParams()` / `readRaceParams()` and validated by `resolveRaceFields()` for URLs and presets alike. A new track (racers, length, laps, mix, favourite) or Ball Size restarts the race and drops a found seed; the camera, the shape and the cup follow live (the cup only lengthens the run, so it drops the seed too). `tests/race.test.ts` covers the settings, the track generator (determinism, row spacing, obstacles inside the corridor and passable, the final sector, laps, the featured mix, the grid, scaling), the standings and gaps, F1 points and the cup, the roster, the notes and tunes, whole races (phases, placings, sounds, determinism across frame sizes, swaps, pads, the camera, the cup phase, the staged winner, stragglers, tempo, resizes, live settings) and the finder; `tests/extras.test.ts` holds its fingerprint; the smoke test (section 26) checks the preview and the card, the URL and the controls, the search box, the Teams note, a default race at 30+ fps with the racers' notes, a short race at 8× through its podium and cup table into localStorage twice, a staged winner and the finder.

### Beat Runner and Paddle Keep-Up (rhythm runner)
Feature jdm-rhythm-runner: two modes without rings that own their playfields (the `"none"` ring layout; each moves one ordinary engine ball – `gravityScale` 0, `ballsMayRest`, `ballsPassThrough` – so pause, playback speed, restart, the recorder and the fast export work unchanged; only a run played by hand – a Beat Runner without Auto Jump, a Paddle Keep-Up without Auto Platform, `jdmRhythmPlayedByHand()` – is left to Record Video, since the export's fresh engine has no player: the ⚡ Fast export is off for it with a note (`FastExport.handPlayNote`) and a batch job of one fails as "played by hand" (`BatchRender.errorHandPlay`)) and draw their own entities through a small renderer module and a few `Canvas.tsx` hooks, like the race and the arena games. `src/lib/physics/modes/jdmRhythm.ts` holds what they share (`isJdmRhythmMode()`, the scale-degree notes `rhythmPitch()` / `rhythmChord()`); `jdmRhythmFields.ts` glues their SimulatorSettings fields, ranges, URL keys and validation into `settings.ts` and their finder settings into `finder.ts`.

- **Beat schedule** – `src/lib/simulation/beatSchedule.ts` inverts the beat clock of Picture Paint (`lib/simulation/beatClock.ts`): `beatTimeSec(config, i)` is the simulation time of beat `i`, numbered exactly like `BeatClock.sample().index` (a song grid mapped through the music bed's start offset and loop, past a non-looping song's end extrapolated at its tempo; the manual BPM from 0), and `firstBeatAtOrAfter(config, t)` the first beat at or after a time. `tests/runner.test.ts` checks both against `BeatClock` for several offsets, looping or not.
- **Jump-timing solver** (`runner.ts`) – `runnerPhysics()`: gravity `RUNNER_GRAVITY` cube lengths/s² × the Gravity setting (0.5×–2×), take-off speed √(2·g·H) from the Jump Height H. `jumpFlightTime(v0, g, rise)` is the descending root of v0·t − g·t²/2 = rise (onto a block `rise` 1 or 2, flat 0), `takeOffSec(land, …)` = land − flight time, `ascendTime()` when the rising jump passes a height (the block's corner), `dropTime(g, depth)` the free fall off an edge.
- **Course** – `buildRunnerCourse(settings, gravity, random)` (pure; four draws per obstacle whatever it becomes) walks the beats: for each obstacle a kind from the mix and the level (`pickKind()`), the earliest beat the jump fits (`LEAD_IN_SEC` before the first, `MIN_RUN_SEC` of running after every landing; below Density 1 a beat or two is skipped now and then), the take-off from the solver, and the geometry from the times (x = speed × time): a row of spikes centred under the apex, as many as the arc clears with the hitbox margins (`runnerMaxSpikes()`), a pit between the take-off and the landing (`GAP_MARGIN`), a block face the rising square clears by `FACE_MARGIN` (`runnerCanStepUp()`), an edge placed so the fall lands on the beat; floors and blocks are disjoint spans, a closing drop brings the square back to the floor, checkpoints every `SECTION_EVENTS` obstacles, the finish a second after the last landing. `courseIsClear()` in the tests flies every planned arc against the hitboxes.
- **Runner physics** – `RunnerMode.advance()` moves the square event by event inside every engine sub-step, on its own track clock (simulation time minus a shift): take-offs (the plan's times with Auto Jump, a buffered Space press – `requestJump()`, `JUMP_BUFFER_SEC` – without), running off an edge, landings (the descending crossing of a surface top with ground under it, solved analytically) and crashes (a block face or spikes ahead, `runnerFrontHitSec()`; the inset hitbox against blocks, pit walls and spikes, `runnerCollides()`; falling below `PIT_DEATH_Y`). A crash waits `RESPAWN_SEC`, rounded up to whole beats, and restarts the section at its checkpoint (the shift grows by whole beats, so the course stays on the music's beat). The rotation turns a whole number of quarter turns over a planned flight (half a turn per flat flight otherwise, snapped on landing). A landing queues a `"hit"` with the event's scale degree (`runnerDegree()`, a contour lifted by the level), the finish a chord and the `"multiplier"` arpeggio, a crash the wall-break sound and a low note that only accompanies the tune (`SoundEvent.melody` false: a loaded melody or slicer song moves on with the landings alone); dust, debris and finish sparks are analytic particles from the mode's own generator.
- **Paddle** (`paddle.ts`) – the field is in field heights (a portrait column, `PD_ASPECT`, the ceiling at `PD_CEILING`, the platform at `PD_PLATFORM`), so a seed plays the same on any canvas. `PaddleMode.step()` runs `PADDLE_SUBSTEPS` fixed sub-steps per 60 Hz step: the platform moves (the controller, or the hand input of `setInput()`), then the ball flies with walls, ceiling and the platform line met at their exact times. A catch launches it with `launchOf()` (the apex from `APEX_EDGE` to `APEX_CENTRE` of the room by how central the hit was, sideways `VX_KEEP` of its speed + `KICK` × spin × offset + `PLATFORM_CARRY` of the platform's) and speeds the tempo up (`paddleTempo()`: gravity × k², speeds × k, at most `MAX_TEMPO`); a ball past the platform is a miss, served again after `RESPAWN_SEC`, or GAME OVER with `GAME_OVER_HOLD_SEC` of banner. A catch is the next note of the tune (a loaded melody's next note); the walls, the ceiling, the streak chime, a miss and the game over only accompany it (`SoundEvent.melody` false – the ToneGenerator plays them with the bounce instrument and lets them use up no melody note, slicer slice, melody cooldown or beat-lock slot), so the song advances on the catches alone. The controller (`planCatch()`, pure): `predictLanding()` solves the flight to the platform line exactly (ceiling bounce, walls folded in with `foldBetween()`), a drawn sideways speed to send the ball off with sets the off-centre hit it aims for, and below skill 1 a timing error (±`TIMING_ERROR_SEC` × (1 − skill): it plans early or late), a heavy-tailed aim error (`AIM_JITTER`: P(error > d) = 1/(1 + (d/scale)²), so the miss rate grows with (1 − skill)²), a reaction delay and a slower platform (`controllerTopSpeed()`). The serves and the plans draw from the game's own generator seeded from the engine's at init – the engine's stream is shared with the cinematic director – so `runLengthMs()`, the finder's fast path, replays a game exactly without the engine loop (`tests/paddle.test.ts` compares it with engine runs).
- **Page** – `Simulator.tsx` hands the runner the song's beat grid (`rhythmBeatRef`, the same grid Picture Paint follows) and re-plans the Beat Runner only when what its run is planned from changes (`runnerPlanOf()` / `sameRunnerPlan()`: the course settings, Auto Jump, the Gravity's factor and the beat the course follows, compared by `sameBeatSchedule()` – so the BPM of a run on a song's grid, or a song finishing its analysis under a run on the BPM, changes nothing). The course lands on the music bed's beats, so a re-plan restarts the whole run (`restartRun(true)`, the R key's restart: the bed from its start offset, the melody, the slicer and the beat grid with the course – a paused run stays paused and its bed starts over when it resumes); a change of the beat it follows drops a found seed there, and neither the BPM nor a song touches a seed in any other mode (the runner's and the paddle's own settings drop it whatever the mode, like every mode's). Paddle Keep-Up restarts when its game (or the Gravity, the Ball Size) changes; while a runner or a paddle is played by hand, a capture-phase key listener turns Space / ↑ / W into jumps (instead of pausing; Escape pauses) and ← → / A / D and the pointer over the canvas into the platform's input. `components/simulator/jdmRhythmRenderer.ts` (`RunnerLayer`, `PaddleLayer`) draws both and writes `data-rr-*` / `data-pd-*` onto the canvas; `sections/JdmRhythmSection.tsx` is the Mode-row block of each (search keys `JDM_RHYTHM_KEYS`); the canvas words live in the `JdmRhythm` namespace of `messages/*.json`.
- **Tests and checks** – `tests/runner.test.ts` (the solver, the schedule, the course, settings, whole runs: every landing on the beat and a note in its step, song grids, determinism and resizes, crashes and beat-aligned restarts, a perfect hand-played run, the finder, a loaded melody that only the landings advance – two crashes use up no note –, `sameBeatSchedule()` and when the page re-plans, `jdmRhythmPlayedByHand()`) and `tests/paddle.test.ts` (the predictor against brute force, the controller, the launch, skill 1 never missing, deterministic misses and GAME OVER, sounds, only the catches as notes of the tune – also through a real ToneGenerator with a melody on a fake audio graph (`tests/fakeAudio.ts`) –, bounds, hand input, the fast path and the finder); `tests/toneGenerator.test.ts` covers accompaniment hits (`melody` false) under a melody, the slicer, the beat lock and a hit sample; `tests/extras.test.ts` holds both fingerprints; the smoke test (section 31: also the melody on a paddle's catches, a runner that re-plans on a song's beat only when it follows the song – bed and course restarted together, landings on the song's clicks –, the BPM leaving a found seed in Classic, the Fast export off for hand play) and `scripts/generate-mode-previews.mjs` (`public/modes/runner.webp`, `paddle.webp`).

### Batch render

- **ZIP** – `src/lib/recording/zip.ts` (covered by `tests/zip.test.ts`, which reads the archive back header by header): `crc32()` (table-driven, chainable over chunks), `dosDateTime()`, `zipHeaders()` (the local headers, central directory and end record from each file's name, size and CRC-32 alone: method 0, UTF-8 names via flag bit 11, no ZIP64 – `ZipTooLargeError` above 65 535 files or 4 GiB), `zipArchiveSize()` (that check from the names and sizes), `zipStore()` (byte arrays between the headers, referenced, not copied) and, for the clips, `zipBlobs()` / `zipBlobParts()`: the archive's size is checked from `blob.size` before anything is read, each clip is read once, one `ZIP_READ_CHUNK_BYTES` (4 MiB) slice at a time, for its CRC (`blobCrc32()`), and the archive is a Blob of the headers and the clips' own Blobs – referenced, not copied, so a ZIP of any size needs one slice of memory beyond the clips the page already holds.
- **Page** – `components/simulator/useBatchRender.ts` runs a batch. The fast export renders what the page shows (the hidden canvas copies the page's props, the export engine the page engine's config), so each job first puts its settings on the page – a link's or a swept value through `loadPresetSettings()` (which keeps the page's live uploads selected: `presetToLiveSettings()` in `settings.ts` puts back the uploaded wall-break sound and the custom hit sample that `presetToSettings()` drops), a mode through `changeMode()` (the mode card's change, so the carry-overs of a new feature apply without work here; the batch's clip length is put back afterwards, as a new mode starts from its defaults) – and waits for the page to commit them (an effect after every commit resolves the waiters, plus `SETTLE_MS` for asynchronous set-up such as a sample decoding); then it hands `startFastExport()` a `BatchExportRequest` through `batchExportRef` in Simulator.tsx: the export renders the job's seed instead of the page run's, scores a race under a key of its own, and gives its result to `settle()` instead of downloading `jumpingballslive-export.*`. A job whose export did not start (a recording or a search was running) fails as "busy", one whose run is played by hand (a Beat Runner or Paddle Keep-Up without its auto player: nobody would play it) as "played by hand" (`handPlay`); one without an encoder for its format stops the batch before the page would fall back to Record Video.
- **UI** – `components/simulator/sections/BatchSection.tsx` (search key `BATCH_KEYS`, rendered by Controls.tsx at the end of the Recording section): source and variant pickers, the list with its read-out, the mode chips, the sweep's setting / from / to / steps and its values, the summary (clips × resolution × fps), **Render batch**, the queue (`data-batch`, `data-batch-done`, `data-batch-total` on the block, `data-batch-job` / `data-batch-file` / `data-batch-seed` per row, a progress bar on the clip being rendered), **Stop after this clip**, **Download all as ZIP** and **Clear list**. The smoke test renders a two-seed list (names, both downloads, the ZIP read back entry by entry against them, the definition after a reload), a mode variant stopped after its first clip (the rest skipped, the page back in its own mode), an uploaded wall-break sound through a sweep of a seed and of a share link and through a mode variant (the select's value while every clip renders, the upload played in every clip, still selected afterwards) and a found run through a gravity sweep (the Found panel, the clip length, the fast export's digest and the page run's first escape are the same afterwards).

Feature boris-vortex: a Boris-family mode without rings that owns its playfield and its motion like Pendulum Wave (the `"none"` ring layout, `ballsMayRest` + `ballsPassThrough`, balls with `gravityScale` 0 whose positions the mode overwrites in `onBallStep()`), so pause, playback speed, restart, the recorder, fast export, faces, emoji and trails work unchanged; the physics extras, the obstacle layer and the ring walls do not apply (the funnel is the mode's own).

- **Physics** – `src/lib/physics/modes/vortex.ts`: `buildVortexField()` lays the funnel out in the centred square the recorder crops to (rim `RIM_AT`, entry `ENTRY_AT` × rim, hole `HOLE_AT` × rim) and `ringRadii()` spaces the rings geometrically between the entry and the hole. Every ball is integrated in polar coordinates by `stepSpiral()` – L′ = −k·L (exact), r″ = L²/r³ − v_c²/r − k·r′, θ′ = ±L/r², semi-implicit Euler cut into turns of at most `MAX_TURN_PER_STEP` – under the attraction v_c²/r (it grows toward the centre; a circular orbit has the same speed v_c = rim · `BASE_OMEGA` · √pull everywhere, so the whirl speeds up as the ball sinks). A ball entering on v_c with r′ = −k·r follows r₀·e^(−k·t) exactly, so `dragRate()` = ln(entry / hole) / duration brings it to the hole on time and crosses the geometric rings at a steady tempo. The seed draws the whirl direction, the first entry angle, the run tempo (1 ± `TEMPO_SPREAD` / 2, scaling the drag) and per ball an entry speed of `ENTRY_SPEED_MIN`–1 × v_c (the weave); the entry angles step by the golden angle. `crossRings()` advances a ball's next ring past every ring it is inside (inward, once); the step's distinct rings become one `"hit"` event – a chord of at most `MAX_RING_NOTES_PER_STEP` when several – pitched by `ringPitch()` (degree i of the scale, a diatonic major while chromatic, starting at C4 and an octave lower while the innermost would pass C7). Reaching the hole records a splash, queues a `"hit"` with `pew: true` and `frequency = pewPitch()` (an octave above the innermost ring) and removes the ball at the end of the step; with `loop` it re-enters `RESPAWN_DELAY_SEC` later. The run finishes `SWALLOW_HOLD_SEC` after the last swallow (never with the loop: `runNeverFinishes()`); `vortexNominalRunSec()` / `vortexRunRangeSec()` give its length and the band the seed's tempo spreads it over, which is why the finder searches it. A resize before the first step places the entered balls from their seeded draws exactly as an init at the new size would (the finder builds its engine at the page's size); later it scales every ball's state with the funnel. `depthRadiusScale()` shrinks a ball with its depth (`radiusScale`, so a Ball Size change keeps it).
- **Sound** – `src/lib/audio/pewTone.ts`: `schedulePewTone()` glides a main oscillator (`pewWaveform()` of the bounce instrument) and a sine sub an octave below exponentially down `PEW_TONE.drop` times over `PEW_TONE.duration`; `ToneGenerator.playPew()` snaps the start to the scale, places it on the beat grid without taking a bounce's slot, ducks the music bed, and plays the chosen wall-break clip instead when there is one. The page's sound loop and the fast export's `playSoundEvent()` route `ev.pew` to it; the ring notes are ordinary hits (melody, instrument, hit sample, beat lock, slicer).
- **UI** – `components/simulator/vortexRenderer.ts` (`VortexLayer`): the funnel's depth gradient, four logarithmic whirlpool arms turning with the balls (their dashes flow inward), the rings (cyan at the rim to magenta by the hole with the rainbow walls, else the wall colour; a ring flashes and glows when a ball sinks past), the rim and the hole's lime lip under the balls; the throat's shade, note pulses and splashes (a ripple and droplets in the ball's colour, analytic on the simulation clock) over them; the title and the swallowed / pew counter at the top of the square, and a "PEW!" banner from the last swallow (`allSwallowed`) through the `SWALLOW_HOLD_SEC` hold before the end screen, so a recording ends on it. The canvas mirrors `data-vortex-*` (balls, entered, swallowed, in flight, notes, chords, rings, deepest ring, loop, tempo, depth, all swallowed, finished) for the smoke test. The panel block is `sections/VortexSection.tsx` (balls, stagger, rings, spiral time, pull, depth cue, loop and a run summary – or the endless note); a change of the funnel or the flight restarts the run and drops a found seed, the depth cue and the scale follow live. Settings `vxBalls` (URL `vxn`), `vxStagger` (`vxs`), `vxRings` (`vxr`), `vxDuration` (`vxd`), `vxGravity` (`vxg`), `vxLoop` (`vxl`), `vxDepthScale` (`vxds`), validated by `resolveVortexFields()`; the canvas words live in the `Vortex` namespace of `messages/*.json`.
- **Tests** – `tests/vortex.test.ts`: settings / URL / presets, the funnel geometry, the matched spiral and the integrator's determinism, ring-crossing detection, the notes rising with depth, the pew's place in the event stream, its synthesis and the ToneGenerator's dispatch (scale, waveform, beat grid, wall-break clip), the banner flag and the hold before the end, the loop, resizes and the finder landing a 30 s seed; `tests/extras.test.ts` holds the fingerprint of the default run. The smoke test checks the card, the URL ↔ panel round trip, a run's notes and pews and its banner hold, the finder and the frame rate at 1080×1920.

### Viral video bot
Feature viral-bot: the owner asked for "a bot that makes videos like project.jdm and the other accounts that go viral". The
research is [docs/virality-playbook.md](docs/virality-playbook.md); the bot is that playbook as code, in three layers around
one planner. Everything is client-side or runs on your own machine / runner – there is no server.

- **Playbook** – `src/lib/bot/playbook.ts` turns the playbook's recipe (§3) into data: the families (`escape`, `rhythm`,
  `battle`), platforms and their length buckets (short 8–15 s, standard 15–30 s – the Reels default –, long 60–90 s), the safe
  zone (`SAFE_ZONE`: clear of the bottom 20 % and the right 12 % of the 1080×1920 frame), the payoff band (80–90 % of the clip,
  accepted up to 97 % for runs that end a second after their payoff; a cut clip ends 0.5–1 s before it), the look (the Neon
  theme on black, glow, trails), the voices (piano: triangle bounces + plucked melody on a major scale; xylophone: marimba on a
  pentatonic one), the climbing public-domain melodies, the recurring cast (`SERIES_ROSTER`: Blaze, Wave, Volt, Moss, Nova,
  Tang; `MASCOT` Pip, the ball with a face), the checklist the score reads (`CHECKLIST`, 100 points) and the **recipes**:

  | Recipe | Family | Mode | Countdown | Payoff | Where it comes from (playbook) |
  | --- | --- | --- | --- | --- | --- |
  | `ring-escape` – “Can it escape in 24 seconds?” | escape | Classic / Portal / Accumulation | wall counter | escape | the rule-in-one-second + countdown pattern (§1, §3.2–3.3) |
  | `pip-escape` – “Pip always escapes. Day 12.” | escape | Portal / Classic, face + name | wall counter | escape | borisbounces' character and daily struggle |
  | `grow-fill` – “It grows every bounce…” | escape | Grow | percentage bar | fill | oddplayground's “It starts tiny and gets out of control” |
  | `clone-per-pass` – “Every escape spawns 3 more balls.” | escape | Multiply | timer | fill | the multiply / retention loop (§1) |
  | `multipliers-board` – “x2 x4 x8… until it breaks.” | escape | Multipliers board | percentage bar | fill | borisbounces' multipliers |
  | `power-layers` – “Every hit doubles the power.” (the rule of the clip's sequence: `ViralBot.plRules`) | escape | Power Layers | the stack itself | escape | oddplayground's doubling layer breakers |
  | `pendulum-wave` – “20 pendulums. Wait for the chord.” | rhythm | Pendulum Wave | percentage bar | flip (back in line) | project.jdm's pendulum waves (music-first) |
  | `polyrhythm` – “12 rhythms. When do they all meet?” | rhythm | Polyrhythm | percentage bar | flip (all meet) | project.jdm's “Rhythm Theory” formats |
  | `drop-symphony` – “18 balls. Every peg is a note.” | rhythm | Ball Drop | timer | fill | project.jdm's sound-first drops |
  | `glass-smash` – “Pip vs 4 floors of glass.” | rhythm | Glass Smash, face + name | timer | shatter | borisbounces' “smash all of the glass” |
  | `string-battle` – “4 lives each. Cut a string, cost a life.” | battle | String Battle | lives (HUD) | winner | oddplayground's Web Dominion hit |
  | `territory` – “Pick a side: which colour takes the board?” | battle | Capture the Flag | timer | flip | oddplayground's pong-wars territory battles |
  | `battle-royale` – “10 squares, one survivor. Pick yours now.” | battle | Battle Royale | hit points (HUD) | winner | project.jdm's square deathmatch (1,099 comments) |
  | `square-race` – “6 squares. Which one finishes first?” | battle | Square Race | standings (HUD) | winner | project.jdm's races and recurring contestants |
  | `maze-race` – “Which one finds the exit first?” | battle | Classic with 3–4 team balls | wall counter | winner | oddplayground's maze escapes |

  Territory and the maze play in the closest existing modes (Capture the Flag, a Classic ring maze); when dedicated modes
  land, point the recipe's `modes` and `settings()` at them.
- **Planner** – `src/lib/bot/planner.ts`, pure and deterministic (seeded generators keyed by the inputs; the only date is the
  one passed in). `planClip(recipe, planSeed, platform, options)` builds the settings (the mode's defaults, the look, the
  voices, 1080×1920 at 60 fps, the recipe's seeded numbers, the series label – the Top Text, or the Bottom Text in the modes
  whose own scoreboard band covers the top of the square, `TOP_HUD_MODES`: battle royale and capture the flag, where the canvas
  also starts the top captions below that band), then searches physics seeds with the
  seed finder's engine (`createEngineForSettings()` – `finderRequest.ts` rebuilds the page's physics config and mode settings
  from the settings and the page canvas's world size, so a planned seed replays exactly in the fast export) and its
  predicates (`outcomes.ts`: escapes-at for a resolved escape inside the last 20 %, never-escapes + escapes-at for a cut
  0.5–1 s before it, winner for the races; the finder's duration search for the modes that end on their own – a square race's
  payoff is its first finisher, when the mode names the winner, and a resolved race is cut at 85 % instead of at the podium; the fixed length of
  Power Layers; the analytic cycle of the Pendulum Wave and Polyrhythm; a measured fill for Grow and Multiply). It models the
  clip's real end (the run's own finish, the page's banner holds, the recorder's 0.5 s), fills the captions (the hook split into
  one-line pills that fit the safe zone, the countdown, the payoff text or the closing question; a recipe's `copyVars` fill
  words from the copy, e.g. Power Layers' `{rule}` names the sequence the clip plays by), the share link (with `seed=`, which
  the page reads in its first render and pins on its first run) and the post (`copy.ts`: caption, specific question, keywords, 5–10 hashtags, posting note, in the
  locale's `ViralBot` messages). Every accepted candidate is scored by `scoreClip()` (motion in the first second, hook present
  and safe, visible countdown, payoff timing, length bucket vs platform, sound, ending, series, look – each with a reason) and
  the best is kept. `planDay(date, platform, count)` rotates the leading family daily and splits every family into two halves
  that alternate by day, so no recipe runs two days in a row whatever the count; endings alternate clip by clip. The search is a
  generator (`planClipSteps`, `planDaySteps`) so the page runs it in slices.
- **Bot section** – `components/simulator/sections/BotSection.tsx` (search key `BOT_KEYS`, after the Batch block) and
  `components/simulator/useViralBot.ts`: platform, count 1–20, series, length and ending; **Plan clips** (a fresh set with these
  filters) and **Today's plan** (the day's own, the one the CLI and the job make); per clip the recipe, hook, mode, seed, length,
  ending, score and **why this clip**, **Open in simulator** (the settings through the preset loader, the melody, the seed pinned
  like a found simulation), **Re-roll** and **Copy caption**; **Render all** hands the plan to the batch renderer
  (`useBatchRender`'s `runJobs()` – a small hook: jobs with their own settings, seed, name and a `prepare()` that loads the
  melody) and downloads `jumpingballslive-bot-<date>.zip` with the videos (`<episode>-<recipe>-<seed>.mp4|webm`), a caption
  `.txt` each, `manifest.json` and `posting-schedule.md` (`output.ts`). The last plan is kept in localStorage (`store.ts`,
  `jumpingballslive_viral_bot`). Plans are timed for the canvas size they were made in: after a resize the block asks to plan again.
- **CLI** – `node scripts/viral-bot.mjs --count 5 --platform reels --out bot-output [--date YYYY-MM-DD] [--family escape]
  [--bucket standard] [--ending resolved] [--locale pl] [--dry-run] [--post | --post-only]` (also `npm run bot -- …`). With the
  exported site served (`BASE_URL`), it opens the simulator in headless Chromium, plans through `window.__jumpingBallsBot` in
  the page's world, renders every clip with the fast export and saves the videos, caption files, `manifest.json` and
  `posting-schedule.md`. `--dry-run` plans in Node instead (the same planner bundled from `src/lib/bot/node.ts` with esbuild)
  and writes only the text files. It never posts without `--post` (render and post) or `--post-only` (post what `--out` holds,
  after you uploaded it); both need `IG_USER_ID`, `IG_ACCESS_TOKEN` (a long-lived token with `instagram_basic` and
  `instagram_content_publish`) and `BOT_VIDEO_BASE_URL` (the public HTTPS folder Instagram downloads the MP4s from), optionally
  `IG_GRAPH_VERSION` / `IG_GRAPH_HOST` – see `.env.example`; keep them in `.env.local` or secrets, never in the repository.
  Publishing (`src/lib/bot/instagram.ts`, pure request builders and a flow with an injected `fetch`) creates a `REELS` media
  container from the video URL, polls its `status_code` until `FINISHED` and publishes it; a failure names its step, hides the
  token and prints the manual upload steps. Instagram takes MP4 (H.264 + AAC): a Chromium without H.264 + AAC encoders renders
  WebM (Playwright's Chromium on Linux has neither; Google Chrome on Linux has no AAC encoder), so after rendering the CLI
  converts every WebM clip with ffmpeg (on `PATH`, or `FFMPEG_PATH`: `-c:v libx264 -pix_fmt yuv420p -r 60 -c:a aac -b:a 192k
  -movflags +faststart`), removes the WebM and points `manifest.json` and `posting-schedule.md` at the `.mp4`; without ffmpeg
  the WebM stays, with a warning, and is never posted.
- **Scheduled job** – `.github/workflows/bot.yml`: every day at 05:47 UTC and by hand (inputs `count`, `platform`, `post`) it
  installs (with ffmpeg, when the runner lacks it, checked for its libx264 and aac encoders), builds with the Pages base path,
  serves `out/`, runs the CLI (which converts the WebM clips to MP4) and uploads `bot-output` as an artifact kept 14 days.
  It posts only when run by hand with `post` ticked and the `IG_USER_ID`, `IG_ACCESS_TOKEN` and `BOT_VIDEO_BASE_URL` secrets
  plus a `BOT_UPLOAD_COMMAND` repository variable (the command that uploads `bot-output` to that public folder, e.g.
  `aws s3 sync bot-output s3://my-bucket/bot --acl public-read` with `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets) exist;
  otherwise it warns and the clips wait in the artifact with their posting schedule.
- **Add a recipe** – append a `BotRecipe` to `RECIPES` in `playbook.ts`: `id`, `copyKey`, `family`, `modes`, `payoff`,
  `countdown` (`caption` or the mode's `hud`), `strategy` (how the payoff is timed), optionally `teams`, `character`,
  `musicFirst`, `endings` and `buckets` (what the mode can fill), a `settings(ctx)` generator that keeps every value on its
  `RANGES` step (use `ctx.rng`, `ctx.bucket` and `ctx.payoffTarget`), `hookVars()` and, for words that depend on the settings,
  `copyVars()` (variable → path under `ViralBot`); a mode whose own HUD covers the top of the square goes in `TOP_HUD_MODES`;
  then add its copy under
  `ViralBot.recipes.<copyKey>` in the three messages files (`name`, `series`, `hook`, `payoff`, `cliffQuestion`, `postQuestion`,
  `cliffPostQuestion`, `keywords`, `hashtags`, optionally `cliffHook`). `tests/bot.test.ts` checks every recipe against `RANGES`
  for many seeds, the copy in three languages and the safe zone; update the recipe table above and the playbook's §5.
- **Tests and checks** – `tests/bot.test.ts` (recipes vs RANGES, determinism of planClip / planDay, the square race cut
  before its first finisher, Power Layers' hook vs its sequence, the series label and the arena scoreboard, the daily rotation,
  the score item by item, the safe zone, captions and hashtags per locale, the manifest, caption files and schedule),
  `tests/instagram.test.ts` (the request builders and the publishing flow with a mocked `fetch`), `tests/botCli.test.ts` (the
  options, a real `--dry-run` in Node and the WebM → MP4 conversion with a stand-in ffmpeg); the smoke test plans three clips
  in the Bot block, opens their share links (the canvas' `data-seed` is the planned seed), reloads, opens one, keeps an arena
  game's captions below its scoreboard band, and renders a one-clip short plan into a ZIP it reads back.

### Split-screen races
Feature split-screen: 2 or 4 arenas on one canvas and one recording, without touching the single-arena code paths.

- **Settings** – `src/lib/splitScreen.ts` (pure): the fields `arenaCount` (1 | 2 | 4, URL `ac`), `arenaLayout` (row | grid, `al`), `soundArena` (first | all, `sa`) and `arenas` (per-arena `{ label, seed?, gravity?, ballSpeed?, ballColor?, mode? }`, the compact URL key `ar` – arenas split by `|`, fields by `~`: `s` seed, `g` gravity, `v` ball speed, `c` colour, `m` mode) with defaults, `SPLIT_SCREEN_RANGES`, validation (`resolveSplitScreenFields()`, URLs, presets and project files alike) and `splitScreenCarryOver()` for a mode change; the override merge (`mergeArenaSettings()`: the shared settings with an arena's gravity, speed, colour and – not for the first arena, which always plays the Mode picker's mode – its mode on top; `resolvedArenas()` fills labels and missing arenas; `patchArena()` / `withArenaSeeds()` edit them); the viewport maths (`arenaViewports()`: the arenas tile the centred square the recorder crops, in reading order; each arena's engine simulates a world of its viewport's shape whose shorter side is that square's side – a single arena's world – drawn scaled by `scale`); `splitRestartKey()` (a new count, seed or mode restarts every arena; gravity, speed and colour follow live) and the race (`raceStandings()`: each arena timed by its first escape, else its finish, on its own simulation clock; ties on the same step).
- **Engines** – `src/lib/simulation/multi.ts` (`MultiArenaRunner`): the first arena is the page's own engine (Simulator.tsx lays the first arena's gravity / speed / colour / seed over the settings); the runner keeps one more `PhysicsEngine` per arena, set up through the page's hooks exactly like the page's engine and the fast export's (`arenaPhysicsConfig()` + `initEngineForMode()`), follows every settings change (from scratch before the run starts, only what changed during it), notices the page's engine restarting (its clock going back or another mode) and restarts the others on the same frame, shares the particle budget out (`engine.setParticleBudget()`, `arenaParticleBudget()`), drains the other arenas' sound queues every frame (played through `playArenaSound()` like the page plays its own – bounces at `EXTRA_ARENA_LEVEL`, `melody: false` accompaniment kept – only with "every arena"; their wall breaks are counted either way for the faces, `takeWallBreaks()`), marks each arena's first escape (`engine.getFirstEscapeMs()`) and finish (`engine.getFinishedAtMs()`: the step the run finished on, which the engine records in `update()` – exactly the finder's run length, however many steps an 8× frame runs) and holds the finished race `SPLIT_FINISH_HOLD_MS` before the end screen. The page's hooks (`ArenaHooks` in Simulator.tsx) let the other arenas play a hand-played Beat Runner / Paddle Keep-Up by themselves (the player's keys and pointer drive the first arena). `findArenaSeeds()` wraps the finder: the first arena is searched as always, then every other arena with its overrides and world (`arenaFinderRequest()`); the seeds go into `arenas[i].seed`, the clip lasts the longest run.
- **Canvas** – `src/components/simulator/splitScreenCanvas.tsx` wraps the canvas component (`withSplitScreen()`, around `withFastRender()` in `Canvas.tsx`): with one arena it renders the canvas as before; in a race every arena is drawn by its own hidden instance of the canvas – the unchanged single-arena draw routine, with every prop the page gives the canvas – in the fast export's offline mode (a driver with the arena's world, its viewport's scale in device px and a clock from its first frame), and one animation loop composes them into the visible canvas (`drawImage()` into each viewport) with borders, the arena labels (time and medal once an arena is done), the race banner, the watermark, the Top / Bottom Text and the captions (on the first arena's run); the Grand Prix cup table is left to the first arena, whose race the page scores. It implements the canvas handle (recording, end-screen holds, background of the export's letterbox) and mirrors `data-split-*` for the smoke test.
- **Panel** – `src/components/simulator/sections/ArenasSection.tsx` (the "Arenas & Split Screen" section: count, layout, sound, one editor per arena); messages under `Controls.split*` and the `SplitScreen` namespace (the banner).
- **Tests** – `tests/splitScreen.test.ts` (viewport maths, the override merge, URL / presets, the standings, the runner with real engines – an arena replays the finder's run of its seed exactly and its finish mark is the finder's run length at 8× –, the sounds and wall breaks of the other arenas, and the finder wrapper); the smoke test races four arenas, records a race and finds seeds for two.

## Browser support

Chrome, Edge and Safari export MP4; Firefox exports WebM. Recording uses `canvas.captureStream()` and
`MediaRecorder`, so it needs a recent desktop browser. The fast export uses WebCodecs (`VideoEncoder`, `AudioEncoder`) and an
`OfflineAudioContext`: MP4 (H.264 + AAC) in Chrome, Edge and Safari, WebM (VP9 + Opus) in Firefox and in Chromium builds without
an H.264 / AAC encoder; where it is missing, the button falls back to the real-time recorder. The simulator itself runs anywhere `<canvas>` and
Web Audio are available.

## Notes

- The tool is free of external runtime dependencies beyond Next.js, React, next-intl and the two MIT muxers of the fast export (mp4-muxer, webm-muxer).
- Uploaded images, MIDI files and sounds never leave the browser.
- Melodies shipped in `public/notes` are short public-domain themes generated from note lists in `scripts/generate-midi.py`.

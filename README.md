# ViralBalls clone – satisfying ball physics simulator

A full-featured, editable re-creation of [viralballs.com](https://viralballs.com/en): a free, browser-based
bouncing-ball physics simulator that exports vertical MP4 clips for TikTok, Reels and Shorts.

Built with **Next.js 15 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · next-intl**.
Everything runs client-side: physics, rendering, audio and video encoding happen in the visitor's browser.
The site is exported as plain static files, so it deploys to **GitHub Pages** (workflow included) or any
static host – no server required.

Settings in the Mode row: ball count, size spread, gravity spread, peg rows, release interval, rain (`dbc`, `dsv`, `dgv`, `drows`, `dsi`, `dloop`); deterministic, so seeds and Find Simulation include it. Built on a generic obstacle layer (`src/lib/physics/obstacles.ts`: circles and optionally spinning bars with restitution, friction and swept collision maths) that any mode – or an obstacle editor – can reuse; the canvas draws obstacles in the wall colour with the wall glow |
| **Bouncing Shapes & DVD polyrhythms** | A rectangular box (portrait by default, `boxAspect`) instead of rings, with 1–12 axis-aligned squares, circles or rounded DVD-style logos (`boxShape`) flying in straight lines at constant speed with perfect reflections (mirror reflection, so the bounce period never drifts; gravity optional via `boxGravity`). Every wall hit plays the next note of the loaded melody or, without one, one of four notes – one per wall (C5 E5 G5 C6, snapped to the scale, on the beat grid). A big number on each shape counts down by one per hit (`boxCountdown`, 0–99; the run ends when every shape reached zero, never at 0), the shape flashes, grows a little (`boxGrowPerHit`, 0–3 %) and cycles its colour. Shapes at speeds in small whole-number ratios (`boxSpeedRatio` 1:1 / 2:3 / 3:4:5 / 4:5:6) hit the walls in those ratios – the polyrhythm – and a DVD logo that reaches a corner plays an accent (louder, longer note plus a full-screen flash). Deterministic: the seed picks the axis ratios, the launch directions and the run's tempo (±15 % on every speed, the ratios intact), so run lengths vary continuously and Find Simulation works while the countdown is on (with it off the finder says the run never ends instead of searching); a DVD logo always gets an odd axis ratio and a corner lock re-aims it by a hair at every bounce, so it reaches a corner exactly every 3–13 hits even while it grows. In the "Box arena" block of the Mode row, shared via the URL (`bxn`, `bxs`, `bxa`, `bxg`, `bxc`, `bxgr`, `bxr`) |
| **Pendulum Wave** | The project.jdm pendulum-wave / phasing format: 5–60 pendulums tuned like the classic Harvard wave (pendulum *i* completes K + *i* swings per cycle of T seconds, default 51 + *i* in 60 s), so the row starts in line, drifts into travelling waves, splits into two and three groups and snaps back in line at the end of every cycle – analytic motion θᵢ(t) = A cos(2π fᵢ t) from the simulation clock, so it is exactly deterministic and replays frame for frame. Six layouts: **row** (pivots on a bar, strings ∝ 1/f²), **arc** (pivots on a ring, swinging toward the centre – "Pendulum Wave in a Circle"), **circle** (bobs on radii from the centre, optionally mapped onto a rotating **polygon** of 3–8 sides), **galaxy** (the radial layout on a slowly turning frame – spiral arms in the trails), **sliding** (bobs on rails) and **bouncing** (balls on a floor with a rectified free-fall arc, so every ball hits the floor at its own frequency and the slow ones bounce highest); **phasing** swaps the harmonic series for an arithmetic series of swing times (a Reich-style tempo phase shift that never quite realigns); fading **trails** 0–1; rainbow colours by index. Sound: a note when a bob crosses the centre, reaches an extreme or both (the floor hit / apex when bouncing), pitched by the pendulum's index as a major-scale degree from C4 (low → high or high → low), through the ToneGenerator like every other hit (instrument, scale snap, beat lock, hit sample, melody); the **wave chord** option plays bobs whose events fall within 20 ms as one chord (`SoundEvent.chord`: one grid slot, the level shared out, a flash when most of the row aligns). Finishes after N full cycles (default 1) or never; the finder knows the run length is fixed by the settings and says so. In the "Pendulum wave" block of the Mode row, shared via the URL (`pwn`, `pwk`, `pwt`, `pwa`, `pwl`, `pwp`, `pwph`, `pwtr`, `pws`, `pwpd`, `pwch`, `pwc`) |

## Getting started

```bash
npm install
npm run dev        # http://localhost:3000 (plus the base path, if set) → redirects to your browser's language, /en by default
npm run build      # static export into ./out (+ 404.html and .nojekyll for GitHub Pages)
npm start          # serves ./out the way GitHub Pages does (base path, 404 page, trailing slashes)
```

Copy `.env.example` to `.env.local` to configure the build. Everything is optional for local development:

- `NEXT_PUBLIC_BASE_PATH` – sub-folder the site is served from (`/Balls` on `https://user.github.io/Balls`, empty for a root deployment).
- `NEXT_PUBLIC_SITE_URL` – public URL used for canonical links, hreflang, sitemap and Open Graph, including the base path. Defaults to `http://localhost:3000` plus the base path.
- Feedback channel, first one set wins: `NEXT_PUBLIC_FEEDBACK_ENDPOINT` (an endpoint that accepts a cross-origin JSON POST, e.g. Formspree, Basin or your own worker with CORS enabled), `NEXT_PUBLIC_FEEDBACK_EMAIL` (opens the visitor's email app) or `NEXT_PUBLIC_GITHUB_REPO` (opens a prefilled GitHub issue; needs a public repository with Issues on, and visitors need a GitHub account).
- `NEXT_PUBLIC_ANALYTICS_SCRIPT_URL` / `NEXT_PUBLIC_ANALYTICS_SITE_ID` – load a privacy-friendly analytics script (Plausible, Umami, Rybbit…).

`next build` reads `.env.local`; so do `npm start`, `npm run smoke` and `npm run previews` (for `NEXT_PUBLIC_BASE_PATH`),
so a base-path build previews correctly at `http://localhost:3000/<base path>/`. You can also pass it explicitly:
`npm start -- --base /Balls` and `BASE_URL=http://localhost:3000/Balls npm run smoke`.

Other scripts:

```bash
npm run typecheck                          # tsc --noEmit
npm run lint                               # eslint
npm test                                   # vitest unit tests (engine, physics extras, ball interactions, obstacles, Ball Drop, Bouncing Shapes, MIDI parser, settings, hit samples, song slicer, scales, instruments, music bed, beat detection, beat clock, Picture Paint)
npm run smoke                              # headless-browser end-to-end checks; build and `npm start` first (see scripts/smoke-test.mjs)
npm run previews                           # regenerate public/modes/*.webp from the real simulator (build and `npm start` first); MODES=drop npm run previews renders one mode
python3 scripts/generate-midi.py           # regenerate the built-in melodies in public/notes
python3 scripts/generate-sounds.py         # regenerate the wall-break and hit sound effects
```

## Deploying to GitHub Pages

The repository ships with `.github/workflows/deploy.yml`:

1. **Enable Pages once**: repository *Settings → Pages → Build and deployment → Source: GitHub Actions*.
   The workflow cannot do this for you; until it is done the *deploy* job stops with a message saying so.
   Private repositories need a paid GitHub plan (Pro, Team or Enterprise) for Pages; public repositories work on
   the free plan.
2. **Push to the default branch** (or run the workflow manually from the *Actions* tab). Every push is linted,
   type-checked, unit-tested and built; pushes to the default branch are then published.
3. The site appears at `https://<user>.github.io/<repo>/` – for this repository
   `https://cronusaztec.github.io/Balls/`. The workflow reads the site URL from the repository's Pages settings
   on every run (falling back to that conventional URL while Pages is off) and builds with the matching base path.

**Feedback form**: on a public repository with Issues enabled the deployed form opens a prefilled GitHub issue
(visitors need a GitHub account). On a private repository, or to use another channel, set a repository
*Variable* (Settings → Secrets and variables → Actions → Variables): `FEEDBACK_ENDPOINT` (a form endpoint that
accepts a cross-origin JSON POST, e.g. Formspree) or `FEEDBACK_EMAIL`. Until one of these applies the form
tells visitors that no channel is configured. `ANALYTICS_SCRIPT_URL` and `ANALYTICS_SITE_ID` variables are passed
to the build the same way.

**Custom domain**: set it under *Settings → Pages → Custom domain* and point its DNS at GitHub Pages. For
Actions-based deployments GitHub ignores a `CNAME` file; the workflow picks the domain up from the Pages settings
and builds for the domain root (no base path) on the next run.

**Other static hosts** (Netlify, Cloudflare Pages, S3, nginx…): run `npm run build` with `NEXT_PUBLIC_SITE_URL`
set and upload `out/`. Point the host's "not found" page at `404.html`.

`.github/workflows/smoke.yml` builds the site under a base path and runs the browser smoke test on pull
requests and on demand.

### How the static export works

- `next.config.ts` sets `output: "export"`, `trailingSlash: true` (every page is `route/index.html`) and
  `basePath` from `NEXT_PUBLIC_BASE_PATH`.
- There is no middleware: `src/app/(static)/page.tsx` is the root page and redirects to the visitor's language
  in the browser (with a `<meta refresh>` fallback), `src/app/(static)/404/` is the localised not-found page
  and `scripts/postexport.mjs` copies it to `out/404.html`.
- `src/lib/site.ts` exposes `assetPath()` for `/public` files referenced from plain `<img>`/`fetch()` calls (Next's
  `Link`/`Image` add the base path on their own) and `pageUrl()`/`absoluteUrl()` for canonical, Open Graph and
  sitemap URLs.
- The feedback form talks to its channel directly from the browser (`src/components/site/FeedbackForm.tsx`).

## How to extend it

### Add a setting
1. Add the field and its default to `SimulatorSettings` / `defaultSettings()` in `src/lib/settings.ts` (and a range in `RANGES` if it is numeric).
2. Optionally give it a short URL key in the `*_URL_KEYS` maps so it is shareable.
3. Render a control in `src/components/simulator/Controls.tsx` (use the `Slider`, `Toggle`, `ColorPicker` helpers from `ControlPrimitives.tsx` and wrap it in `Searchable` with a label key so the search box finds it; add the key to `SECTION_KEYS`). A bigger feature gets its own component in `src/components/simulator/sections/` that Controls.tsx renders inside the right section (see `SongSlicerSection.tsx`, which also exports its search keys).
4. Add the label + tooltip to every `messages/*.json` under `Controls`.
5. Apply it: either read it in `Canvas.tsx` (visual) or forward it to the engine in an effect in `Simulator.tsx` (physics).

### Add a game mode
1. Create `src/lib/physics/modes/<name>.ts` implementing `GameMode` (see `types.ts`; `classic.ts` is the minimal example, `portal.ts` a complete one, `drop.ts` a mode without rings built out of obstacles, `box.ts` a mode that owns its playfield entirely and folds the balls back in `onBallStep()`, `pendulum.ts` one whose motion is analytic – it overwrites every ball's position from the simulation clock in `onBallStep()` and solves its sound events inside each step). Use `ctx.random()` for randomness so the seed finder stays deterministic. Optional flags: `ballsMayRest` (no slow-ball boost), `ballsPassThrough` (no ball-to-ball collisions).
2. Register it: add the id to `MODE_IDS` in `types.ts`, instantiate it in `engine.ts` and add a case to `initMode()` (`activateMode()` takes the ring layout: `"classic"`, `"single-gap"`, `"solid"`, or `"none"` for a mode that builds its own playfield).
3. Draw anything mode-specific in `Canvas.tsx` (segments, overlays, HUD counters); obstacles are drawn for every mode. A mode that draws its own entities gets a small module next to the canvas (see `boxRenderer.ts`) and a branch in the ball pass.
4. Add the card order and the family (`MODE_CARD_ORDER`, `MODE_CATEGORIES`: `escape` or `rhythm`; the mode cards are grouped under a heading per family) in `src/lib/modes.ts`, names/descriptions in `messages/*.json` (`Modes`, `Controls.mode<Name>`, `Editorial.mode<Name>`), and a preview image in `public/modes/<name>.webp` (add the mode to `scripts/generate-mode-previews.mjs` and run `MODES=<name> npm run previews` against the served build).
5. Mode settings that the finder needs go into `ModeSettings` in `src/lib/simulation/finder.ts` and `createEngineForSettings()`, and a fingerprint of the new mode's default run into `tests/extras.test.ts`, so the physics extras are proven not to disturb it. A mode whose run cannot finish with some settings says so in `runNeverFinishes()` (the page then hides the finder and `findSimulation()` resolves with `endless` instead of searching); a mode whose run length is fixed by its settings whatever the seed (Pendulum Wave: cycles × cycle length) reports it in `fixedRunDurationSec()`, so the finder resolves with `fixedDuration` and the page explains what to change instead of testing seeds.

### Physics extras
`src/lib/physics/extras.ts` holds the optional forces and wall behaviours: `airDrag` (fraction of the velocity lost per 60 Hz step), `windX` / `windY` (acceleration as a fraction of the ball speed per second), `spinStrength` (wall contact spins the ball by the no-slip condition against the – possibly rotating – wall, `contactSpin()`, and a Magnus-style force `spinStrength × MAGNUS_COEFFICIENT × spin × (−vy, vx)` curves the flight; the integrated angle rotates custom ball images and emoji in `Canvas.tsx`), `wallBounciness` (restitution multiplied into every rebound speed, also the ones a mode sets itself), `breathingAmplitude` / `breathingSpeed` (wall radii pulse as `base × (1 + amplitude · sin(2π · speed · t))`) and `rotatingGravity` (degrees per second the gravity vector turns, starting straight down). They are part of `PhysicsConfig` (`PhysicsExtras` in `types.ts`), so they reach the engine through `engine.setConfig()` and the finder through `createEngineForSettings()` like every other physics value; `resolvePhysicsExtras()` fills in the defaults and clamps to `PHYSICS_EXTRA_RANGES`, which `RANGES` in settings.ts spreads for the sliders and the URL/preset validation.

The engine applies them in `update()`: drag once per fixed step, the gravity direction, wind and spin terms per sub-step, the contact spin and the restitution in `processWallCollisions()`. Each extra is skipped entirely at its default, so a run without extras takes the original code path and `tests/extras.test.ts` checks every mode against a trajectory recorded before the extras existed, plus determinism with all of them on. Breathing walls mutate `wall.radius` in place around the base radii the engine keeps in `wallBaseRadii` (`syncWallBaseRadii()` runs after every wall (re)assignment, including `ctx.setCircularWalls()`, and `setConfig()` restores the base radii before a mode rebuilds its walls), so gaps, modes and the renderer follow the pulse without knowing about it. The pulse is applied once per **sub-step** (the last sub-step lands exactly on the step's end time, so frames and `setConfig()` see the same radii as a per-step pulse would give) and the engine remembers where every wall was before the move in `wallPrevRadii`; the first collision pass of each sub-step then *sweeps* each wall over that move – the ball's side is judged against the previous radius and the hit test is one-sided (`outer >= radius` for a ball that was inside, `inner <= radius` for one that was outside), so a wall that jumped across the ball is still a hit, pushed back to the side it came from, and a gap that swept past the ball's centre counts as a pass. At the widest and fastest pulse the outer wall moves up to ~24 px per step in an 800×600 arena, more than the ±(ballRadius + 2) hit window, which is why both are needed; later passes of the collision loop use the plain current-radius test so push-outs and portal teleports are never re-judged against a stale sweep. Modes can read the unpulsed radii and the resolved extras through `ctx.getWallBaseRadii()` / `ctx.getPhysicsExtras()`: Grow caps the ball at the trough of the pulse (`base × (1 − amplitude) − 2`) instead of the live radius, so the ring never shrinks under a ball that outgrew it. To add another extra: add the field to `PhysicsExtras`, `DEFAULT_PHYSICS_EXTRAS` and `PHYSICS_EXTRA_RANGES`, apply it in the engine behind an "is it at its default?" check, give it a URL key in `NUMERIC_URL_KEYS`, a slider in `components/simulator/sections/PhysicsExtrasSection.tsx` (with its search key in `BALL_PHYSICS_EXTRA_KEYS` / `WALL_PHYSICS_EXTRA_KEYS` and the section defaults in `sectionDefaults()`), the label + tooltip in every `messages/*.json`, and add it to the finder-invalidation dependency list in `Simulator.tsx`.

### Ball interactions (merge, split, pass)
`src/lib/physics/interactions.ts` holds the "what balls do to each other" setting and its pure maths. `ballInteraction` is `bounce` (the classic equal-mass rebound), `merge`, `split` or `pass`; `splitMinRadius` (4–20 px) and `maxBalls` (2–64) limit the splitting. Like the physics extras, the three values travel inside `PhysicsConfig` (`BallInteractionConfig` in `types.ts`), so they reach the engine through `engine.setConfig()` and the finder through the copied config; `resolveBallInteraction()` fills in the defaults and clamps, `ballInteractionOf()` picks them out of the settings, and `RANGES` spreads `BALL_INTERACTION_RANGES`. With the default the engine takes exactly its old code path, so existing seeds and links behave as before.

- **Merge**: `handleBallCollisions()` runs the pair loop; in merge mode `mergeBallPair()` fuses two balls that overlap while approaching each other (balls that merely drift apart – e.g. freshly spawned at the same point – are left alone, as a bounce would leave them). `mergeBalls()` gives the result: mass ∝ area, so the merged ball has radius √(r₁² + r₂²), sits at the mass-weighted centre, keeps the total momentum and wears the mass-weighted blend of both colours (`blendColors()`; a non-hex colour wins by weight). The first ball of the pair becomes the merged one (keeping its id, trail and lifetime), the second is removed; a `merge` sound event and a burst of `burst` particles (glowing dots in the ball's colour, drawn by `Canvas.tsx`) follow.
- **Split**: whoever breaks a wall reports it with `ctx.reportWallBreak(ball, wallIndex)` next to its `gap` sound event – the engine's own gap pass (Classic), Multiply's escape detection and Shatter's segment breaks do. In split mode the ball is queued and `flushSplits()` runs at the end of the step, after the rebound / escape bookkeeping and outside every loop over the balls (one split per ball per step). `canSplit()` checks the limits (both halves at least `splitMinRadius`, fewer than `maxBalls` balls) and `splitBall()` computes the halves: radius r/√2 each, side by side across the flight direction, each with the parent's velocity plus an equal and opposite sideways push, so the pair keeps the parent's momentum while diverging by 40–72° (the only random number, drawn from `engine.random()`). The parent becomes one half (keeping id, trail, lifetime and spin), the other is a new ball; a mode copies per-ball state to it in the optional `onBallSplit()` hook – Multiply marks the half of an escaped ball as escaped too, so it flies out with its parent instead of counting as a new escape and spawning another wave. A `split` sound event and a spark burst follow.
- **Pass**: the pair loop is skipped.

The sounds live in `src/lib/audio/interactionTones.ts` (`ToneGenerator.playInteraction("merge" | "split")`: a low sinking sine and a high rising triangle, on the beat grid and snapped to the scale like every other sound, ducking the music bed). The panel block – the bounce / merge / split / pass switch and the two split sliders, shown in the two-ball modes – is `components/simulator/sections/BallInteractionSection.tsx`, which exports its search keys; the settings are `ballInteraction` (URL `bi`), `splitMinRadius` (`smr`) and `maxBalls` (`mb`), and a mode change resets them like the physics extras. `tests/interactions.test.ts` covers the maths (radius, momentum, colour, caps), the engine behaviour in every mode that reports breaks and determinism. To let another mode split its ball, call `ctx.reportWallBreak()` where it breaks a wall and, if it keeps per-ball state, implement `onBallSplit()`.

### Obstacles and Ball Drop
`src/lib/physics/obstacles.ts` is a generic obstacle layer: an `Obstacle` is a `circle` (a peg: centre, radius) or a `segment` (a bar: centre, half-length, angle, optional `angularVelocity` in rad/s around its centre, optional `thickness`), each with a `restitution` (fraction of the approach speed kept) and a `friction` (fraction of the sliding speed lost per contact). Factories: `circleObstacle()`, `segmentObstacle()`, `segmentBetween(x1, y1, x2, y2)` for walls and floors; `segmentEndpoints()` writes a bar's ends into a caller-owned object so the renderer never allocates. The maths is pure and deterministic: `resolveBallObstacle()` pushes the ball out, reflects the normal component of its velocity (relative to the surface velocity of a spinning bar, so a bar can fling a ball) with the restitution, applies the friction and returns the approach speed of the contact (−1 when there is none). Both resolvers look at where the ball came from (`position − velocity × dt`): a fast ball that crossed a thin bar or passed a peg's centre within one sub-step is bounced back to the side it came from instead of popping out on the far side.

The engine keeps the list (`ctx.setObstacles()` / `engine.getObstacles()`, cleared with every mode init) and, in every sub-step after moving a ball, resolves it against every obstacle before the ring walls (`handleObstacleCollisions()`); `advanceObstacles()` turns spinning bars first. The wall-bounciness extra scales the obstacle restitution like every other rebound. A contact whose approach speed is at least `OBSTACLE_HIT_SPEED` (40 px/s, raised under heavy gravity to three times the speed one sub-step of gravity adds, so a resting ball never "hits" its support) is reported to the mode through the optional `GameMode.onObstacleHit(ctx, ball, obstacle, index, impactSpeed)` hook, which may return `{ frequency, suppressSound, suppressGlow }`; the engine then queues a `"hit"` `SoundEvent` carrying that `frequency` (without a hook or frequency the innermost-wall tone plays) and remembers the contact in `getObstacleHits()` for the glow. `ToneGenerator.playWallHit(wallIndex, frequency?)` plays a pitched hit like any other: snapped to the scale, on the beat grid, a hit sample transposed to it (`hitSamplePlaybackRate(wallIndex, pitchByWall, frequency)`), a loaded melody still taking precedence. `Canvas.tsx` draws every obstacle in the wall colour (per-obstacle hue in rainbow-gradient mode) with the `GLOW_LAYERS` halo on recent hits, and the reactive background flashes on obstacle hits too. Two small per-ball fields support all this: `Ball.gravityScale` (a per-ball gravity multiplier, 1 when absent – the engine multiplies it into the gravity term, which leaves every other mode's numbers bit-identical) and `Ball.radiusScale` (the ball's size relative to the configured radius, so `setConfig({ ballRadius })` keeps a size spread). A mode whose balls may come to rest sets `readonly ballsMayRest = true`; the engine then skips the slow-ball boost that keeps a ball moving in the ring modes.

**Ball Drop** (`src/lib/physics/modes/drop.ts`, id `drop`) is built entirely out of obstacles: `buildDropLayout(width, height, rows, ballRadius, loop)` lays out a portrait playfield that uses the full canvas height and fits the centred square the recorder crops to, closed by a left, a right and (unless raining) a bottom wall – the side walls continue `WALL_EXTENSION` (one) canvas height above the top, clipped by the canvas edge, so a pile that outgrows the board stays between them – with `rows` staggered rows between the top and the floor – every third row bars instead of pegs – spaced so the biggest ball of the size spread fits between two pegs and past the ends of a bar. `init()` sets the obstacles and releases the first ball; `onPreUpdate()` releases ball *k* at *k × spawnInterval* seconds at a random x along the top (a spot still taken by another ball waits for the next step, so balls never spawn inside each other), each with its own `radiusScale` (±75 % of the ball size at full size variation, never below 3 px) and `gravityScale` (½×–2× at full gravity variation, log-uniform). `onObstacleHit()` returns `dropHitFrequency(ball.radius)` – 5280 / radius Hz, i.e. the 8 px default ball plays E5 and bigger balls play lower, clamped to A2–A6 – and caps the queued sounds at `MAX_HIT_SOUNDS_PER_STEP` per step. The run is finished when every ball has been released and none has moved more than `REST_DISTANCE` (3 px) during a `REST_TIME_MS` (1 s) window (positions rather than speeds, because a resting ball still jitters by one sub-step of gravity; where a ball rests does not matter, a pile may reach above the top). A board that cannot hold every ball (40 balls of size 30, say) is not left waiting forever: `releaseDue()` reports a due release that found no free spot at the top, `onPreUpdate()` times how long that has been going on (`blockedMs`) and once it has lasted `REST_TIME_MS` while the pile is at rest, the board counts as full – the run finishes with the balls it holds and `getProgress().total` (the SETTLED! banner, the finder) reports that number instead of the setting; with **rain** (`loop`) the floor is left out, a ball that fell below the canvas re-enters at the top (fresh trail, spread over a band above the top) and the run never finishes, so the seed finder is hidden. Ball-to-ball collisions are damped to `BALL_TO_BALL_RESTITUTION` (0.6) in `onBallCollision()`, right after the engine's elastic pair rebound, so a pile settles instead of a cradled ball rocking forever. Safety net: a ball whose centre was shoved across a wall or floor line by another ball is put back inside in `onPostSubStep()`, so the run can still finish. A live change of the ball size re-spaces the board on the next step; a canvas resize rebuilds it in `onConfigChange()`. The settings are `dropBallCount` (URL `dbc`, 1–40), `dropSizeVariation` (`dsv`), `dropGravityVariation` (`dgv`), `dropRows` (`drows`, 3–12), `dropSpawnInterval` (`dsi`, 0–2 s) and `dropLoop` (`dloop`); `resolveDropSettings()` clamps them (URL parameters and presets alike), `engine.setDropSettings()` applies them on the next `initDrop()`, `Simulator.tsx` restarts the board when one of them changes (like Target does), the finder receives them in `ModeSettings.drop`, and the panel block is `components/simulator/sections/BallDropSection.tsx` (rendered in the Mode row, and in the Ball section while the settings search is in use, so the search box finds it). `tests/obstacles.test.ts` covers the collision maths (push-out, restitution, friction, end caps, thickness, tunnelling, spinning bars, the restitution cap and scale) and `tests/drop.test.ts` the settings, the pitch mapping, the layout counts, the release schedule, the per-ball sizes and weights, the sound events, settling (default, heavy-gravity, big-ball and overfull boards, including that a slow schedule or a burst is never mistaken for a full board), rain, the rescues, live changes and determinism; the smoke test drives the controls, the URL and a run with size-pitched sounds in the served export. To use obstacles in another mode, build them with the factories, hand them to `ctx.setObstacles()` in `init()` (and again in `onConfigChange()` when the size changed) and, if the mode wants its own pitches or silence, implement `onObstacleHit()`.

### Bouncing Shapes (box arena)
`src/lib/physics/modes/box.ts` (id `box`) is the project.jdm "DVD logo / count down from 60" format and the template for a mode that owns its playfield: it activates with the `"none"` ring layout, lays a box out with `buildBoxField(width, height, aspect)` (a rectangle of the given aspect fitted into the centred square the recorder crops to), spawns its shapes as ordinary engine balls (the engine integrates them, so gravity, drag, wind and the recorder work unchanged) and, in `onBallStep()`, folds every ball that crossed a wall back inside with `reflectAxis()` – a mirror reflection of the overshoot, so the motion is exactly the straight line a perfect reflection gives and the bounce period `(box − size) / speed` never drifts, whatever the step size. `ballsMayRest` switches the slow-ball boost off and `ballsPassThrough` the pair loop, so the shapes fly through each other and nothing disturbs their rhythm.

- **Rhythm and tempo**: `speedFactors(ratio, count)` cycles the ratio's numbers over the shapes and normalises the fastest to the Ball Speed, so shapes at 2:3 hit the walls 2:3 times; every speed is then multiplied by the run's **tempo**, drawn from the seed within 1 ± `TEMPO_SPREAD` / 2 (0.85–1.15, exposed as `BoxView.tempo`). The ratios between the shapes stay exact, but the run length becomes a continuous function of the seed instead of one of five values (one per axis ratio), which is what lets Find Simulation land inside its ±0.5 s tolerance – with the default box a 30 s target is met by roughly one seed in eight; when the target is out of the band, the finder's "closest" message says by how much to change the countdown or the Ball Speed. A live Ball Speed change scales the velocities, so the tempo survives it. `launchAngle(innerW, innerH, p / q)` picks the direction so a shape's vertical and horizontal bounce periods are in the ratio `p : q` (an `AxisPeriodRatio`, drawn per run with `ctx.random()`; shared by every shape unless the speeds are equal, when each shape draws its own).
- **Corners**: a shape launched from the centre reaches a corner only when its axis ratio is odd/odd. Squares and circles draw from `AXIS_PERIOD_RATIOS` (2:1, 3:2, 4:3, 5:3, 5:2 – mostly even, so two notes rarely land on one hit); DVD logos draw from `DVD_AXIS_PERIOD_RATIOS` (5:3, 7:5, 3:1, 7:3, 9:5), so the accent is on the schedule of every seed: the first corner is the ((p + 1) / 2)-th side-wall hit and then there is one corner every `hitsPerCornerCycle()` = p + q − 1 hits (3 to 13). Growth would detune that within a cycle or two (each hit takes a little more room across than down), so the **corner lock** (`lockCorner()`, DVD logos without gravity) counts the hits into the cycle (`BoxShapeState.cycleX` / `cycleY`) and, after every hit, re-aims the logo with `cornerAimAngle()` – the one direction whose unfolded paths to the scheduled corner take the same time in both axes – keeping its speed. The correction is a fraction of a degree per hit; a schedule that would need a grazing angle (`MIN_AIM_ANGLE`, e.g. after a live change) restarts its cycle from where the logo is.
- **Sound**: every hit queues a `"hit"` `SoundEvent` with `frequency = BOX_WALL_NOTES[wall]` (top E5, right G5, bottom C6, left C5); the ToneGenerator plays a loaded melody's next note instead when there is one, snaps the pitch to the scale, transposes a hit sample to it and places it on the beat grid like any other hit. A DVD logo reaching a corner (both walls in one sub-step, or the second wall within `CORNER_REACH_SUBSTEPS` – predicted at the first hit, so the pair counts as one hit) sets `accent: true`, which `playWallHit()` turns into a louder, longer note (`ACCENT_GAIN`, `ACCENT_LENGTH`; hit samples get the gain) and the canvas into a full-screen flash.
- **Countdown, growth, colour**: each shape's `BoxShapeState` (hue, count, hits, last hit tick, growth scale) lives in the mode and is exposed through `engine.getBoxView()` (the same object every call; hit ages are sub-step ticks × `tickMs`, so flashes freeze with a pause and replay in recordings). A hit advances the hue by `HUE_STEP`, grows the shape by `growPerHit` % up to `MAX_SHAPE_FRACTION` of the box, and decrements the countdown; at zero the shape freezes (`frozen`, zero velocity and gravity) and the run finishes once every shape is done. `ball.radiusScale` keeps the shape's size right across `setConfig({ ballRadius })`, and `onConfigChange()` re-lays the box out on a canvas resize.
- **UI**: `components/simulator/boxRenderer.ts` draws the box (each wall glowing after its hit), the shapes (rounded squares, circles or a stylised DVD-style plate – a rounded rectangle with a disc motif, no trademark artwork – with the countdown number, hit flash, glow and trail) and the corner flash; the canvas mirrors `data-box-hits`, `data-box-corners` and `data-box-done` onto the element for the smoke test. The panel block is `sections/BoxArenaSection.tsx` (shape, count, speed ratio, countdown, growth, gravity, aspect). Settings: `boxShapeCount` (URL `bxn`), `boxShape` (`bxs`), `boxAspect` (`bxa`), `boxGravity` (`bxg`), `boxCountdown` (`bxc`), `boxGrowPerHit` (`bxgr`), `boxSpeedRatio` (`bxr`); `resolveBoxSettings()` clamps them for URLs and presets alike, and a change restarts the box like a Ball Drop change does. `tests/box.test.ts` covers the reflection, ratio and layout maths, the notes and accents, the countdown, determinism, the seeded tempo and the continuous run lengths the finder needs, the corner schedule of every DVD seed under growth (and the size of the lock's turns), the finder and the settings; the smoke test checks a DVD corner and a found 30 s seed in the served export.

### Pendulum Wave
`src/lib/physics/modes/pendulum.ts` (id `pendulum`) is the project.jdm pendulum-wave / phasing format and the template for a mode with **analytic motion**: it activates with the `"none"` ring layout, spawns one ordinary engine ball per bob (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`, so nothing in the engine moves them) and in `onBallStep()` overwrites every ball's position with the closed-form swing at that sub-step's time – no integration, no drift, bit-identical replays. The clock is the mode's own step counter (`steps × stepSec`, so consecutive steps share their boundary exactly) rather than the accumulated `elapsedMs`.

- **Tuning** (`pendulumFrequency()`): classic, fᵢ = (K + i) / T – pendulum *i* completes `baseOscillations` + *i* swings per `cycleSeconds`, the frequencies are 1 / T apart and the whole row is back in phase after exactly T (at T / 2 the odd and even bobs are on opposite sides – two groups; at T / 4 half the row crosses the centre together). **Phasing** keeps the same range of tempi but makes the swing *times* an arithmetic series (each bob's swing lasts a fixed bit longer than the next one's), so neighbours drift apart by a constant time lag per swing and the row never snaps back as a whole. `relativeLengths()` gives every bob L ∝ 1 / f² (the row's strings, the bouncers' heights) and `pendulumAngle()` is θ(t) = A cos(2π f t), the seed picking the side the row starts on and the direction the frame / polygon turns.
- **Layouts** (`buildPendulumField()` – the centred square the recorder crops to – and `buildPendulumRig()`, both pure): `row` hangs the bobs from a bar across the middle 40 % of the field and shortens the longest string so the outermost bob still fits at full swing ((0.3 S − r) / sin A, capped by the height); `arc` puts the pivots on a ring with every string hanging toward the centre; `circle` / `galaxy` move each bob along its own radius between ρ₀ ± ρ_A (the travel follows the amplitude up to ~30° and is capped at the rim and above the centre), `polygon` 3–8 maps the radius onto a polygon outline (`polygonRadius()`) that turns once per cycle and `galaxy` turns the whole frame once per cycle too; `sliding` stacks rails; `bouncing` stands the balls on a floor and lifts each by the rectified free-fall arc `bounceHeight()` = 4 H u (1 − u) of its own period, so every ball hits the floor at its frequency and the slow ones bounce highest. `placeBob()` is the one hot-loop function (no allocation) and the bob radius follows the Ball Size (`radiusScale`, capped by the spacing of each layout); a live size change or a canvas resize rebuilds the rig in place.
- **Sound**: `eventPhases()` says at which fractions of a swing a bob sounds (¼ and ¾ for the centre crossings, 0 and ½ for the extremes; the floor hit at 0 and the apex at ½ when bouncing) and `crossingTimes()` solves the exact event times inside each 60 Hz step (starting one index early and comparing strictly against the shared step boundary, so an event is never missed or doubled). Every event becomes a `"hit"` `SoundEvent` with `frequency = pendulumPitch(index)` – the bob's rank as a degree of C major from C4 over at most three octaves, low → high or high → low – which the ToneGenerator snaps to the chosen scale, plays with the instrument or the hit sample, places on the beat grid and lets a loaded melody override, like any other hit. With **wave chord** on, `groupChords()` merges events within `CHORD_WINDOW_SEC` (20 ms) into one event carrying `chord` (its distinct pitches, at most `MAX_CHORD_NOTES`) – a chord is only flushed once its window has closed, so one straddling two steps is still one chord – and a chord of at least `ACCENT_CHORD_FRACTION` of the row is `accent`ed. `ToneGenerator.playWallHit(wall, frequency, accent, chord)` voices every pitch of a chord at once (`hitPitches()`, `chordGain()` = 1 / √n, at most `MAX_CHORD_VOICES`; the sampler plays the clip once per pitch), in one beat-grid slot with one duck, while a melody still plays a single note. At most `MAX_PENDULUM_SOUNDS_PER_STEP` events leave one step; every note still flashes its bob.
- **Run, finder, UI**: the run finishes at `cycles × cycleSeconds` (the events of that instant are still queued, so the final alignment is heard; then the clock stops, so the row holds that alignment in silence under the end screen instead of swinging and sounding on) or never with `cycles` 0, which `runNeverFinishes()` reports; because the length is the same for every seed, `fixedRunDurationSec()` tells `findSimulation()` to resolve at once with `fixedDuration` when it misses the target and the page explains what to change (`Simulator.finderFixed`). `PendulumView` (`engine.getPendulumView()`, the same object every call) carries the field, the rig, the per-bob states (hue, frequency, pitch, last-note tick), the clock, the rotations and the counters; `components/simulator/pendulumRenderer.ts` draws the rig of the layout, the strings / radius lines / floor shadows, the bobs (rainbow by index, brightened for `NOTE_FLASH_MS` after a note, glow on request), the **trails** – `drawPendulumTrails()` samples every bob's path from the analytic swing (`placeBobAt()`, the same placement the mode writes into the balls) over the last `trailWindowSec()` of simulation time and strokes it in `TRAIL_BANDS` bands of falling opacity (a time constant of 0.12 + 3 · trails² s, drawn back to 2 %, within `MAX_TRAIL_POINTS` for the whole rig), so a trail is exactly the path taken whatever the frame rate or speed, fades out completely (an offscreen layer faded with `destination-out` would keep an 8-bit residue of every path forever), freezes with a pause and starts empty on a restart – and the screen flash of a big chord; the canvas mirrors `data-pendulum-notes`, `data-pendulum-chords` and `data-pendulum-cycles` onto the element. The panel block is `sections/PendulumWaveSection.tsx` (layout, polygon, count, base swings, cycle length, swing, phasing, trails, where a note plays, pitch direction, wave chord, cycles). Settings: `pwCount` (URL `pwn`), `pwBaseOscillations` (`pwk`), `pwCycleSeconds` (`pwt`), `pwAmplitude` (`pwa`), `pwLayout` (`pwl`), `pwPolygon` (`pwp`), `pwPhasing` (`pwph`), `pwTrails` (`pwtr`), `pwSoundOn` (`pws`), `pwPitchDirection` (`pwpd`), `pwWaveChord` (`pwch`), `pwCycles` (`pwc`); `resolvePendulumSettings()` clamps them for URLs and presets alike (a polygon of 1–2 sides is the circle) and a change restarts the rig like a Ball Drop change does – except the trails, which only change the drawing and follow live (`PendulumMode.setSettings()` applies them to `PendulumView.settings` at once; the mode itself always runs on the settings of its last init). `tests/pendulum.test.ts` covers the tuning maths, the crossing detection and chord grouping (including across step boundaries), the pitches, every layout staying inside the field for every count, amplitude and ball size, the mode in the engine (analytic positions, notes and chords, bouncing, cycles and the finish, the silent hold after it, live changes and the live trails, determinism, the per-step cap), the trails (window, sampling budget, the exact path, no residue), the finder and the settings; `tests/toneGenerator.test.ts` the chord dispatch (a hit sample that is not pitched by wall plays a chord once); the smoke test drives the controls, the URL, the fixed-length finder message, a run with scale-degree notes, a trails change mid-run and the silent finish in the served export.

### Metronomes & Polyrhythms
`src/lib/physics/modes/polyrhythm.ts` (id `polyrhythm`, family `rhythm`) reuses the Pendulum Wave mechanism for a mode that owns its playfield with analytic motion: it activates with the `"none"` ring layout, spawns one ordinary engine ball per voice (zero velocity, `gravityScale` 0, `ballsMayRest` + `ballsPassThrough`), computes every voice's position once per 60 Hz step in `onPostUpdate()` and pins the balls there in `onBallStep()`; `components/simulator/polyrhythmRenderer.ts` draws the stage and the voices from the mode's view in a branch of the canvas' ball pass, like `pendulumRenderer.ts` does.

- **Exact tempo arithmetic** (`buildTempoSeries()`): voice *i* ticks `a[i] / D` times per second with whole numbers `a` and `D` – harmonic: `a = 10 (i + 1)`, `D` = the cycle length in tenths of a second; custom: `a = 10 × ratio`; BPM steps: `a` = the tempo in tenths of a BPM, `D = 600`. The ticks of a voice inside step *s* are the whole numbers in [⌈s·a / 60D⌉, ⌈(s+1)·a / 60D⌉) (`ticksInStep()`, with the exact `ceilDiv()` / `floorDiv()`), its position the remainder of `s·a` modulo `2·60D` (`tickPhaseMod2()`), so nothing accumulates, however long the run or large the count. Every voice ticks together exactly at the multiples of `D / gcd(a)` (`alignmentsInStep()`) – that is the alignment, detected analytically, never by comparing floating-point times; a cycle is the cycle length (harmonic, custom) or the alignment period (BPM steps), and the run's last step is `finalStep()`.
- **Sound**: all ticks of a step become one `"hit"` `SoundEvent` – a note, or a `chord` of the ticking voices' distinct pitches (at most `MAX_STEP_PITCHES`, `MAX_ALIGN_PITCHES` on an alignment, spread evenly by `spreadPitches()`) – `accent`ed on an alignment or when a voice's k-th tick is a multiple of `accentEvery`. The ToneGenerator plays it like any other hit (instrument, scale snap, beat lock – one grid slot per step –, hit samples, melody, music-bed ducking). `polyrhythmPitch()` gives a voice the Pendulum Wave's scale degree by index, or its tempo ratio as a harmonic of C3 folded into four octaves – a harmonic or custom voice its own ratio (ticks per cycle, so `3,4,5` plays G4–C5–E5), a BPM-steps voice its tempo relative to the slowest voice.
- **Layouts** (`buildPolyGeometry()`, `placeVoice()`; pure, inside the centred square the recorder crops to, dot size from the Ball Size capped by the spacing): rings (polygons via `polygonRadius()` of the Pendulum Wave, turning once per cycle so a corner meets the dot at every tick), chords / semicircles (a triangle wave of the tick phase, `tickTriangle()`), metronomes (θ = A cos(π·ticks)) and the spiral (tick points on a one-turn spiral). The layout, arc style, polygons, accents, pitch mapping and numbers change live (`setSettings()` rebuilds the geometry and re-places the voices at the current step); the tempo settings and the cycles restart the run (`Simulator.tsx`). The seed only picks the direction the dots turn / the side they start on.
- **Finder, UI, tests**: `runNeverFinishes()` is true with the cycles at 0 and `fixedRunDurationSec()` returns cycles × cycle length, so the page says what to change (`Simulator.finderFixedPolyrhythm`) instead of testing seeds. The panel block is `sections/PolyrhythmSection.tsx` (Mode row; its keys are pushed into `SECTION_KEYS.ball` for the search box); the canvas mirrors `data-poly-voices`, `data-poly-ticks`, `data-poly-alignments`, `data-poly-cycles` and `data-poly-layout`. Settings: `prCount`, `prLayout`, `prArcStyle`, `prTempos`, `prCustom` (sanitised to digits and separators, parsed by `parseCustomRatios()`), `prCycleSeconds`, `prBaseBpm`, `prBpmStep`, `prPolygon`, `prAccentEvery`, `prPitchBy`, `prNumbers`, `prCycles`, resolved by `resolvePolyrhythmSettings()` for URLs and presets alike. `tests/polyrhythm.test.ts` covers the exact arithmetic, the three tempo series, tick and alignment detection against brute force, the pitches, every layout staying inside the field, the mode in the engine (positions, notes, chords, accents, the finish, live changes, determinism, 400 voices), the finder and the settings; the smoke test drives the controls, the URL, the fixed-length finder message, a run with alignments and scale-degree notes, a live layout switch, a pitch-by-ratio run (3:4:5 sounds G4–C5–E5) and 400 voices.

### Collision Playground
`src/lib/physics/modes/collide.ts` (id `collide`) is the template for a mode with **many interacting bodies**: it activates with the `"none"` ring layout, spawns its orbs as ordinary engine balls (so the engine integrates them – gravity via `Ball.gravityScale` = the playground's gravity, drag and wind apply – and pause, playback speed and the recorder work unchanged), opts out of the engine's O(n²) pair loop with `ballsPassThrough` and resolves the collisions itself:

- **Broad phase**: `src/lib/physics/spatialHash.ts` – a uniform grid (counting sort into typed arrays, reused every build, so it allocates nothing once warm) with a cell as wide as the largest contact distance; `collectContacts()` visits each cell and its four "forward" neighbours, so every pair of touching discs is found exactly once (`tests/collide.test.ts` checks it against brute force). `onPostSubStep()` rebuilds it every sub-step from the orbs' positions.
- **Narrow phase**: `COLLISION_ITERATIONS` (3) passes over the candidate pairs, alternating direction: overlap beyond `POSITION_SLOP` is pushed apart by inverse mass (`POSITION_CORRECTION`), approaching pairs exchange an impulse with the restitution; after each pass the orbs are put back inside the container, so a heavy pile pushes its neighbours rather than the wall. The container itself (circle or square, `buildCollideField()` in the centred square the recorder crops to) is resolved per ball in `onBallStep()`, with the restitution × the wall-bounciness extra. Masses are radius²; sizes are log-uniform (`sizeFactor()`, 1/3×…3× at full spread) and scaled so the orbs cover `COLLIDE_FILL` (30 %) of the container at the default Ball Size, capped at `COLLIDE_MAX_FILL`. A speed cap (`MAX_SPEED_FACTOR` × the ball speed) is only a safety net: an elastic gas keeps its energy exactly.
- **Sound**: every impact faster than a resting contact is offered to a per-frame budget of `MAX_SOUNDS_PER_FRAME` (12) slots that keeps the most energetic (½ μ v²) across every 60 Hz step the frame runs (one at 1×, up to eight and more at 8× or on a late frame); `flushPendingSounds()` – the optional `GameMode` hook `engine.consumeSoundEvents()` calls once per batch, i.e. once per rendered frame – queues them strongest first as `"hit"` events with `frequency = collidePitch(smaller radius)` – the run's size range mapped onto a C major pentatonic ladder from C3 (bigger = lower) – and `level = collideLevel(impact speed)`. `SoundEvent.level` / `ToneGenerator.playWallHit(…, level)` scale the loudness of one hit (voice, melody note or hit sample; `hitLevel()` clamps it), so the notes are soft and the texture stays musical under the scale snap, beat lock and music bed.
- **Variants**: squishy orbs store their last impact per body (`CollideView.impactTick / impactNx / impactNy / impactAmount`) and the renderer flattens them with `squashAt()` over `SQUASH_MS`; sync start places them with `syncGridPitch()` / `syncGridCells()` (the widest lattice that fits) and releases them together; the anti-collision switch (`onPostUpdate()` at `antiCollisionAt` seconds of simulation time) stops the pair solver, recolours the orbs and queues an accented chord; the ring variant keeps its bodies in `src/lib/physics/ringTrack.ts` – arc positions and velocities on a circular track, 1-D collisions between neighbours in a fixed cyclic order (they cannot overtake), contact at the chord distance (`contactArc()`), optional tangential gravity – and places the balls from it every sub-step.
- **UI**: `components/simulator/collideRenderer.ts` batches the orbs by hue bucket (one path per colour, `HUE_BUCKETS`), draws short motion streaks, the glow, impact sparkles, squashed orbs as ellipses, lollipop sticks, the container glow and the anti-collision flash and caption; the canvas mirrors `data-collide-bodies`, `data-collide-collisions`, `data-collide-notes` and `data-collide-anti`. The panel block is `sections/CollisionPlaygroundSection.tsx`. Settings: `cpCount` (URL `cpn`), `cpSizeSpread` (`cpsz`), `cpContainer` (`cpc`), `cpGravity` (`cpg`), `cpRestitution` (`cpe`), `cpSquishy` (`cpsq`), `cpSyncStart` (`cpsy`), `cpAntiCollisionAt` (`cpac`), `cpRing` (`cpr`); `resolveCollideSettings()` clamps them, a change restarts the playground, `runNeverFinishes()` reports the mode as endless and `createEngineForSettings()` builds it from `ModeSettings.collide`. `tests/collide.test.ts` covers the spatial hash, the ring collisions, the helpers, the mode in the engine (energy, piles, sound budget, pitch, squash, sync start, anti-collision, ring, live changes, determinism, finder) and the settings; the smoke test runs 300 orbs for 5 s at 30+ fps in headless Chromium and checks that 8× playback still starts at most 12 notes per frame.

### Glass Smash
`src/lib/physics/modes/glass.ts` (id `glass`) is the first mode of the Boris family (the borisbounces formats) and combines the owned-playfield pattern of Bouncing Shapes with the obstacle layer of Ball Drop and a camera of its own:

- **Level** (`buildGlassLevel(width, height, settings, ballRadius, random)`, pure): a portrait shaft (`buildGlassField()`, `SHAFT_ASPECT` 0.62) filling the height of the centred square the recorder crops to; its height is the layout unit ("view height"). The stages are stacked below each other in world pixels – stage 0 starts at the top of the field, the rest continue below the canvas – each with a top pad for the ball to fall in (and the banner), `stageRows(rows, s)` panes (the setting plus a third of it per stage, at most 30) spread over `PANE_ZONE` view heights (never closer than the ball needs) and `stageHp(hp, s)` hit points (one more every other stage, at most two more; `paneThickness()` grows with them). From stage 1 on a pane may get a hole (`stageHoleChance()`, wide enough for the ball, away from the walls), from stage 2 on it may slide (`stageMoveChance()`: 62 % of the shaft wide, a sine of 2.2–3.6 s on the simulation clock); the first pane of a stage is always whole. Below the last stage lies the HOME area: the ground and a doorway on a seeded side. `random` is the engine's generator; every pane draws the same three numbers whatever its kind, so one pane never shifts the next one's.
- **Physics**: the ball is an ordinary engine ball with `gravityScale` 0 – the mode integrates `glassGravity()` (3.2 view heights/s² × the Gravity setting, 0.3×–3×) itself in `onBallStep()`, so the audio-reactive engine gravity never touches it – and resolves the panes there with the obstacle layer's capsule maths (`resolveBallSegment()`; a pane is one segment, two around a hole, moved in `onPreUpdate()` when it slides). The shaft walls and the ground are ordinary engine obstacles (`buildGlassObstacles()`), drawn by the canvas in the wall colour with the wall glow; `onObstacleHit()` keeps the walls silent and lets the ground thud (C3). Any contact from above is a landing, however slow – a graze on the end of a hole's glass, a sliding pane lifting the ball onto its top – so the ball never comes to rest on unbroken glass (the capsule maths alone would only damp its bounce there and the run would never end); a knock from below needs `HIT_SPEED`. A landing cracks the pane and re-launches the ball to the stage's hop height (`GlassStage.bounceHeight`: 0.8 × the pane spacing within 0.06–0.15 view heights, × the seeded tempo², so the pulse quickens as the panes get denser and the run length varies continuously with the seed) with a small seeded sideways kick; a knock from below cracks it too. The last hit point shatters the pane: `makeCrack()` / the shards are drawn from `ctx.random()`, the ball keeps `SHATTER_KEEP` of its speed and crashes through. Falling through a hole or past a sliding pane skips that pane (`cleared` without `shattered`); a pane above the ball can still be cracked from below. Once the ball lands on the ground it rolls to the door; in the doorway the run celebrates for `CELEBRATION_MS` (three confetti bursts) and then finishes.
- **Camera and stages**: `GlassView.cameraY` (world offset: screen y = world y − cameraY) eases toward `cameraTarget()` – the top of the stage the ball is in, following the ball down a stage taller than the view, or the ground at HOME – with `CAMERA_TAU` on the simulation clock and is clamped so the ball never leaves the field. Entering a stage sets `bannerStage` / `bannerAtMs`. Everything is advanced per 60 Hz step, so a pause freezes it and a recording replays it.
- **Sound**: a crack queues a `"hit"` with `frequency = glassPitch(stage, row)` (the row as a C-major degree from C4, each stage two degrees higher, folded into two octaves), which the ToneGenerator plays as the next melody note, the instrument voice or the transposed hit sample, snapped to the scale and on the beat grid like every other hit; a shatter queues the same note with `accent: true` (louder and longer – the hit-sample accent path) plus a `"gap"`, i.e. the wall-break sound, and the page wide-eyes the ball characters on it. `modeWallBreakSound()` (`src/lib/audio/songs.ts`, `MODE_WALL_BREAK_SOUNDS`) makes the new `glass` clip – synthesised by `scripts/generate-sounds.py` (`glass()`: a high-passed noise crash, a thump and a shower of inharmonic tinkles) and listed in `WALL_BREAK_SOUNDS` so any mode can pick it – the wall-break sound of this mode while none is chosen; `Simulator.tsx` applies it and the Sound section names it ("Mode default (Glass)"). HOME plays an accented C-major chord. At most `MAX_GLASS_SOUNDS_PER_STEP` notes leave one step.
- **Drawing** (`components/simulator/glassRenderer.ts`): `applyGlassCamera()` scrolls the canvas' camera transform (the mode's camera owns the view: Camera Follow and the cinematic camera's zoom and shake step aside), so the obstacle walls, the ball with its face and name, the trails and the particles scroll with the level; `drawGlassWorld()` draws the stage markers, the rails of sliding panes, the panes (tinted per stage, bright top edge, glints, a frost that thickens with the damage, a flash per hit), the cracks (one path, each grown over `CRACK_GROW_MS`) and the doorway with its roof and HOME sign (warm light once the ball is home); `drawGlassShards()` the shards (a fixed pool in typed arrays, bouncing off the shaft walls); `drawGlassOverlay()` the stage dots and the "STAGE n" banner in screen space. Only what is in view is drawn and the colours are cached per hue. The canvas mirrors `data-glass-stage`, `data-glass-stages`, `data-glass-hits`, `data-glass-shattered`, `data-glass-panes`, `data-glass-home` and `data-glass-camera`; the HUD shows "HOME!" with the pane count at the end.
- **Settings and UI**: `glassRows` (URL `glr`, 3–30), `glassHp` (`glhp`, 1–5), `glassStages` (`gls`, 1–10), `glassMoving` (`glm`), `glassHoles` (`glh`) and `glassGates` (`glg`, see below); `resolveGlassSettings()` clamps them for URLs and presets alike, a change restarts the shaft (`Simulator.tsx`), the finder builds it from `ModeSettings.glass`. The panel block is `sections/GlassSection.tsx` (Mode row; its keys are pushed into `SECTION_KEYS.ball` for the search box) with a line that sums the run up. A canvas resize rescales the whole level, the ball, the cracks, the shards and the camera onto the new field (`rescale()`).
- **Multipliers** (boris-multipliers, `src/lib/physics/multipliers.ts`): the ball's stat multipliers act on the glass too – `hitDamage()` takes that many hit points off a pane per hit (clamped at 0; `paneDamage()` – the hit points lost – sizes the cracks and the frost), a speed multiplier k runs the whole flight k× faster (`glassTempo()`: the mode's gravity × k², the hops, kicks and the walk to the door × k, so the ball flies the same arcs faster and the notes come quicker) and size grows the ball. With **Multiplier Gates** on (`glassGates`, URL `glg`, off by default) `buildGlassGates()` lays a row of three gates – x2 DMG, x1.5 SPEED, x1.25 SIZE (`GLASS_GATE_FACTORS`), in a seeded order drawn after everything else, so the glass is the same with or without them – across the shaft `GATE_Y` view heights below the top of every stage, under its banner and over its first pane. The ball's centre falling through a row picks the slot under it (`gateSlotAt()`, once per row, in `onPostSubStep()`); the multiplier is stacked at the end of the step through `ctx.getMultipliers().apply()` – the run's cap, the HUD badges, the adaptive sub-steps, which `markTouched()` switches on from the first step when the level has gates – with the rising arpeggio; a size gate never grows the ball beyond the room the panes and holes of the stages left leave (`glassMaxBallRadius()`, at most `MAX_BALL_OF_SHAFT` of the shaft). `drawGlassGates()` draws the rows (a tinted band and the label per slot; the slot taken flashes and stays lit, the others dim), the canvas mirrors `data-glass-gates`, and the Ball section's Multipliers group (the cap) shows in Glass Smash while the gates are on.
- **Tests**: `tests/glass.test.ts` covers the settings (URL, presets, ranges), the progression helpers, the pitches, the shard counts, the level (determinism, stacking, holes and slides only where they belong, everything inside the shaft), the cracks (determinism, inside the glass, never across a hole, longer with damage), the mode in the engine (gravity, crack/shatter state and its sounds, the hop height, a run through every stage to HOME with its banners and camera, the ball kept in the shaft and in view, sliding panes, exact replays, a resize mid-run), the finder, the default wall-break clip, a slow touch from above counting as a landing (and the seeds that used to come to rest on a pane reaching HOME) and the multipliers (a x2 DMG ball breaks a 2-hit pane in one landing, a x2 SPEED hop takes half the time for the same height, the gate rows: layout, seeded order, each slot's multiplier at the end of the step with the arpeggio, the whole run deterministic, the size limit, the cap, a resize); `tests/extras.test.ts` holds its fingerprint. The smoke test (section 17) checks the preview and the clip, the URL and the controls, the search box, the finder, the Sound section's default, a default run at 30+ fps with scale-degree notes and the glass clip, a short run to HOME at 8× and a run with the gates on whose rows stack multipliers on the ball on its way HOME.

### How a wall hit becomes sound
`ToneGenerator.scheduleHit()` dispatches every bounce in this order: the **song slicer** while it has a song to play, then the **hit sample** in `sample` mode once the clip is decoded, otherwise a **synthesised voice** – the next melody note (played with `melodyInstrument`, sine by default) or the wall tone (played with `instrument`), snapped to the chosen scale. A `SoundEvent` may carry its own `frequency` (Ball Drop pitches every hit by the ball's size); it replaces the wall tone's pitch and transposes the hit sample, and is snapped and beat-locked like any other hit. With the beat lock on, voices and hit samples alike are scheduled on the BPM grid and extra hits inside an occupied grid slot are dropped. Whatever path a hit takes, the sound that actually plays ducks the background music bed at its own scheduled time (see below). The Sound section of the panel follows the same order (bounce sound: mode, instrument or sample; melody; scale, root note and beat lock; song slicer; background music; wall-break sound), and controls that only apply in one mode – the sample picker, the melody instrument, the root note, the grid, the music mix sliders – are still rendered while the settings search is in use, so the search box finds them whatever the current mode is.

### Song slicer
The "each bounce plays the next bit of a song" format. `src/lib/audio/slicer.ts` holds the pure cursor arithmetic (`planSlice` picks the next slice, shortens the last one, wraps or stops at the end; `positionAt`, `sliceProgress`, `sliceCount`, `formatSongTime`) and is covered by `tests/slicer.test.ts`, which also drives a `SlicePlayer` through a fake `AudioContext` (next-bounce cut, pause/resume, switching off, reset); the smoke test checks the pause/resume position in the served export. `slicePlayer.ts` is the Web Audio side: it keeps the decoded `AudioBuffer` and the cursor, plays each slice through an `AudioBufferSourceNode` + `GainNode` with linear fades into the ToneGenerator's master gain (so recordings include it), fades out a slice that is still sounding whenever it is cut short (`stop()`: the next bounce, a pause, slicing switched off, restart, new song) and moves the cursor to the point where it was cut, so the song always continues from there and the HUD bar never jumps to the end of the cut slice. `ToneGenerator.getSlicer()` / `decodeAudio()` expose it and `scheduleHit()` hands every wall hit to the slicer first (a bounce falls back to the hit sample, tone or melody note when the slicer has nothing to play, e.g. a finished non-looping song). `Simulator.tsx` decodes the upload, mirrors the settings into the player, rewinds it on restart / mode change / preset load and pushes the song position to the canvas each frame (`CanvasHandle.setSongProgress`), where `Canvas.tsx` draws the thin progress bar along the bottom edge. The panel block lives in `components/simulator/sections/SongSlicerSection.tsx`. Settings: `sliceSong` (URL `slice`), `sliceMs` (`slms`, 80–1000 ms), `sliceLoop` (`sloop`) and `sliceFadeMs` (`slfade`); the song itself stays in memory and is not part of links or presets.

### Background music with ducking
The music bed mixes an uploaded track under the bounce sounds so an export is ready to post. `src/lib/audio/musicBed.ts` plays it through `AudioBufferSourceNode → fade GainNode → duck GainNode → volume GainNode → ToneGenerator master gain`; the master gain already feeds the speakers and the recorder's `MediaStreamDestination`, so the bed ends up in every export without touching `recorder.ts`. The ToneGenerator owns the bed (`getMusicBed()`, attached in `initAudioGraph()`, detached in `stop()`) and every bounce, gap pass or wall-break clip it schedules calls `duck(time)` at that sound's audio time – so beat-locked sounds and their ducks line up, and a hit that plays nothing (melody cooldown, occupied grid slot) does not duck. A duck drops the gain to `1 - ducking` instantly and ramps it back to 1 with `exponentialRampToValueAtTime` over the release time (`cancelAndHoldAtTime` where available, so a running recovery is held rather than dropped); several hits in one frame share one duck. The pure helpers (`duckedLevel`, `duckEnvelope`, `scheduleDuck`, `resolveOffset`, `playbackPosition`, `normalizeMusicOptions`) and the player itself (through a fake `AudioContext`) are covered by `tests/musicBed.test.ts`; the smoke test instruments `AudioBufferSourceNode.start` to check that the bed starts with the run, pauses, resumes from the pause position, restarts and – after Loop is switched off on a track that has already wrapped – still resumes from the wrapped position in the served export.

`Simulator.tsx` decodes the upload with `ToneGenerator.decodeAudio()`, hands the buffer to `MusicBed.setBuffer()`, pushes the settings with `setOptions()` and drives the transport from the run state: `play()` while the simulation runs, `pause()` (keeping the position) while it is paused, `stop()` when it finishes or a mode / preset change resets it, and `restart()` from the Restart button / R key (a non-looping track that reached its end stays silent until then). The position of the sounding source is tracked with the loop state that source actually had (a `looped` flag on the voice, set when it starts looping or is switched to loop mid-run): a source that has wrapped keeps sounding from `(start + elapsed) % duration` after Loop is switched off, so a pause/resume then continues from that wrapped position instead of treating the track as finished, while a source that never looped clamps at the end. The panel block – drop zone, track row with a live duck-level meter, volume, ducking, release, loop and start offset – is `components/simulator/sections/MusicSection.tsx`, which also exports its search keys. Settings: `musicVolume` (URL `mv`), `musicDucking` (`md`), `musicDuckRelease` (`mdr`, 50–1000 ms), `musicLoop` (`mloop`) and `musicStartOffset` (`mso`, seconds); the track itself stays in memory and is not part of links or presets. To route any other source into the recording, connect it to the ToneGenerator's master gain the same way.

### Picture Paint
Paint mode can reveal an uploaded picture instead of leaving a rainbow trail, in rhythm with a song. Three cooperating parts, all deterministic (no `Math.random`, no wall-clock time), so a run replays identically for the recorder:

- **Reveal** (`components/simulator/Canvas.tsx`): the picture (a `data:` URL kept in the page state like the custom ball image) is cover-fitted into the arena circle once, into a `source` layer the size of the arena in *device* pixels, plus a greyscale `ghost` of it. Every sub-step `PaintMode.onBallStep()` records a `PaintPoint` with its dab radius `r` (the ball radius in classic Paint; `ballRadius × paintBrush × paceScale × beatEnvelope` with a picture) and the canvas stamps only the points recorded since the last frame into a `mask` layer (one path, one fill – the mask is never redrawn from scratch), re-composites the `reveal` layer (`source` with `destination-in` the mask) only when new dabs arrived, and draws the ghost at `paintGhost` opacity under the reveal. `PicturePaintState.generation` (incremented by `PaintMode.init()`) tells the canvas to clear the mask on a restart; a resize rebuilds the layers and re-stamps every point. The coverage that finishes the run (≥ 95 %) still comes from the mode's 100×100 grid, which now marks the dab radius and counts painted cells incrementally, so the HUD percentage matches the mask; the finished picture is drawn crisp and `Simulator.tsx` holds the end screen back for `PAINT_FINISH_HOLD_MS` so it is seen (and recorded). The canvas mirrors the HUD state onto the element (`data-paint-coverage`, `data-paint-picture`, `data-paint-pace`, `data-paint-beat`), which the smoke test reads.
- **Beat sync** (`lib/audio/beats.ts`, `lib/simulation/beatClock.ts`): whenever a song is decoded for the music bed or the song slicer, `Simulator.tsx` runs `analyzeBeatsAsync()` – an onset envelope (Hann-windowed FFT frames every 512 samples, log-compressed spectral flux), adaptive-threshold onset picking, tempo by autocorrelation of the smoothed envelope over the 60–200 BPM range (three-harmonic comb score minus the half-lag peak, so the beat beats its half-tempo alias, times a gentle 120 BPM prior), the grid phase that collects the most envelope energy, and a least-squares refinement of period and phase on the onsets – in slices of a few milliseconds between idle callbacks, so a three-minute song never freezes the page. The result (`{ bpm, beatTimes, onsets, confidence }`) is shown in the section and handed to the engine through `engine.setPaintBeat()`, together with the music bed's start offset and loop flag (song time = offset + simulation time, wrapped at the track length), or the manual `bpm` setting when the source is "bpm". `BeatClock.sample(t)` maps simulation seconds to `{ index, sinceBeat, pulse }` with `pulse = exp(−decay · sinceBeat / period)` (1 on a beat, ~5 % before the next). `PaintMode.onPreUpdate()` scales every ball's velocity to `1 + paintBeatPulse × pulse`, undoing the previous step's scale first (and resetting it at a wall hit, where the engine assigns a fresh rebound), so the ball kicks on each beat and glides between while gravity and the rebounds act on the unscaled motion; the dab radius and the glow use the same envelope and the canvas draws a pulse ring. When the beat sync ends – switched off, no tempo to follow, or the picture removed mid-run – `releaseBeat()` undoes the scale still applied and clears the beat state on the very next step (also on the classic code path, where it is otherwise a no-op), so the ball resumes its natural speed at once, the pulse ring and the tempo hint disappear, and a picture loaded again starts from an unscaled ball. No sound is added: hits still play through the normal bounce path only when the ball actually hits.
- **Meticulous coverage** (`lib/physics/picturePaint.ts`): `summarizeCoverage()` reduces the 100×100 grid to a 24×24 map of painted fractions (blocks outside the circle read 1), `largestUnrevealedCluster()` flood-fills the blocks below 50 % and returns the weighted centroid of the heaviest cluster, and `steerAngle()` turns a rebound toward it by at most 18° – the same clamp as the cinematic director. The engine calls the new optional `GameMode.adjustRebound(ctx, ball, wallIndex, outAngle)` hook right after the director's nudge (Paint's wall has no gaps, so the director leaves the angle alone), which is where `PaintMode` steers with `paintGuided` on. Pacing: `paceBrushScale()` nudges the brush every second (`PACE_INTERVAL_MS`, simulation time) by the ratio of the expected coverage (`0.95 × elapsed / target`, linear) to the actual one, at most ×1.2 / ×0.85 per step and clamped to 0.7–2.5, and `paceStatus()` gives the HUD its "on schedule / behind / ahead" hint; `paintTargetSeconds()` picks the schedule – the loaded song's first pass from its start offset or the clip length, whichever ends first.

The settings are `paintBrush` (URL `pbr`), `paintGhost` (`pgh`), `paintBeatSync` (`pbeat`), `paintBeatSource` (`pbs`, `song` | `bpm`), `paintBeatPulse` (`pbp`), `paintGuided` (`pgd`) and `paintPaceToSong` (`pps`); `resolvePicturePaintSettings()` clamps them for URLs and presets alike; the picture itself never travels in links or presets. Everything is gated on `PaintModeOptions.picture`, so without a picture the Paint mode takes exactly its old code path (`tests/extras.test.ts` keeps its recorded fingerprint) and the finder is unaffected. The panel block is `components/simulator/sections/PicturePaintSection.tsx` (upload drop zone, ghost, brush, beat sync with its source switch, detected-BPM readout and pulse strength, guided and pace toggles), rendered in the Mode row of Paint mode and in the Visual section while the search box is in use. `tests/beats.test.ts` runs the detector on synthetic click tracks (90 / 120 / 150 BPM with an offset, stereo, accented, silence, the async slicing), `tests/beatClock.test.ts` the clock (manual and grid sources, offset, loop wrap, decay), `tests/picturePaint.test.ts` the coverage summary, the cluster centroid, the steering clamp, the pacing maths, the settings round trip and the engine behaviour (classic run untouched, brush and dabs, beat envelope, guidance, pacing, restarts); the smoke test generates a PNG in the page, uploads it, detects the tempo of a click-track music bed and checks that the reveal grows.

### Ball characters (faces, expressions and the Boris persona)
The borisbounces format – a ball with a face and a name that always escapes – as a visual layer over every mode. Nothing of it reaches the physics engine: the settings are read by the canvas only, so seeds, "rigged" outcomes and the finder are untouched (`tests/character.test.ts` runs a seeded engine with and without the tracker and compares the trajectories). The pure side lives in `src/lib/character/`, the drawing in `components/simulator/faceRenderer.ts`:

- **Settings** (`character.ts`): `ballFace` (URL `face`: `none` | `dot` | `cute` | `cool` | `cat` | `angry`), `ballName` (`bn`, trimmed to `MAX_NAME_LENGTH`), `nameLabel` (`nl`), `ballSquash` (`sq`, 0–1), `faceOverImage` (`fimg`) and `faceSounds` (`fsnd`) – all off by default; `resolveCharacterSettings()` validates URLs and presets alike, `borisPersonaPatch()` is the **Meet Boris** button (`BORIS_PERSONA`, and the ball grows to at least `BORIS_MIN_RADIUS` so the face reads on a phone), `characterRenderOptions()` turns the settings into what the canvas needs. `faceGeometry(style, r)` places the eyes, pupils, reach and mouth proportionally to the radius (a face scales with the ball size and with Ball Drop's size spread); below `TINY_FACE_RADIUS` every face becomes two dots.
- **Expressions** (`expression.ts`): a small, allocation-free state machine per ball, advanced once per frame on the **simulation clock** (`engine.getElapsedMs()`, so a pause freezes the face and a recording of a seed shows the faces of its run). Priority: `grin` (the ball is outside every intact wall, or the run is finished; lingers `GRIN_HOLD_MS`) > `shock` (a wall broke, `SHOCK_MS`; a running shock is never re-armed and the next one waits `SHOCK_COOLDOWN_MS`, so Shatter's burst of segment breaks startles the face now and then instead of freezing it wide-eyed) > `ouch` (a hard hit – a relative impact ≥ `OUCH_IMPACT`, i.e. a near head-on rebound – for `OUCH_MS`, then no new ouch for `OUCH_COOLDOWN_MS`) > `happy` (still for `REST_MS`) > `neutral`. `stepExpression()` returns the expression it *triggered*, which is what the cat chirps on.
- **Eyes, blink, squash** (`eyes.ts`): `lookTarget()` points the pupils along the velocity with a reach of `1 − e^(−speed / LOOK_REF_SPEED)` and `smoothToward()` eases it frame-rate independently; `BlinkClock` walks a Mulberry32 sequence seeded by `blinkSeed(runSeed, ballId)` – a blink every 1.8–5 s, sometimes a double one, never at the start – so blinks depend only on the seed, not on the frame rate or the playback speed (`blinkSchedule()` lists them); `squashAmount()` is a damped squash-then-stretch after an impact, `squashScales()` the area-preserving scale pair.
- **Tracker** (`tracker.ts`): `CharacterTracker.update(balls, frame)` derives per ball the impact (the change of velocity since the last frame beyond what gravity, wind and drag explain – rebounds off rings, pegs, box walls and other balls alike, no engine hook needed): the squash takes its strength relative to the Ball Speed, the ouch relative to the ball's own speed before the hit (at least `OUCH_SPEED_FLOOR` of the Ball Speed), so a mirror rebound scores 2·cos(angle to the normal) whatever the ball's speed and only near head-on ones hurt; its normal (for the squash), whether it rests or escaped (`escapeRadius`: the outermost intact ring), steps the expression, the eased look (for balls a mode moves by hand, like the Pendulum Wave bobs, from their movement) and the blink. It keeps up to `MAX_CHARACTER_BALLS` balls, starts over when the seed changes or the time goes back (a restart) and drops balls it no longer sees.
- **Drawing** (`faceRenderer.ts`): `FaceLayer` is created with the canvas loop. `beginFrame()` runs once per frame (the page forwards every `"gap"` sound event through `CanvasHandle.noteWallBreak()`, so every character is shocked when a wall breaks); around each ball's body `pushSquash()` applies the squash transform (pivoting on the side that hit), `drawBehind()` the cat's ears, `drawFront()` the face and `drawLabel()` the name under the first ball (white text, dark outline). Bouncing Shapes, Pendulum Wave, Metronomes & Polyrhythms and the Collision Playground draw their own bodies, so `drawOverlays()` puts the faces on them afterwards (two eyes above a countdown number; a DVD plate with a number stays plain). A custom image or emoji keeps its own look unless `faceOverImage` is on. The canvas mirrors `data-face`, `data-face-expression`, `data-face-count` and `data-name-label` for tools and the smoke test; the recorder copies the canvas, so exports have the faces and the label.
- **Sound** (`lib/audio/characterVoice.ts`): the cat's chirps are recipes (a sawtooth through a gliding band-pass formant – "mew!", "mrrp?", "meow~") scheduled by `ToneGenerator.playCharacterChirp()` like every other sound: on the beat grid, snapped to the scale (the contour follows its peak), ducking the music bed, into the recording. They play only with the cat face, `faceSounds` on and the bounce sound not an audio sample (`characterSoundsOn()`), at most one per `CHIRP_MIN_GAP_MS` (a second), so the cat comments on a minority of the bounces and never drowns the notes.
- **UI**: `sections/CharacterSection.tsx` is the "Character" group at the top of the Ball section (the face picker with a live preview that acts out every expression, Meet Boris, name, label, squash, face over image, cat sounds), exporting its search keys; a mode change keeps the character, the Ball section's reset clears it.
- **Extending**: a new face style is an id in `FACE_STYLES`, its proportions in `faceGeometry()`, its features in `drawFace()` (the `drawEye()` / `drawMouth()` branches), an icon and label key in `FACE_OPTIONS` (CharacterSection) and `Controls.face<Name>` in every messages file; a new expression is an entry in `EXPRESSIONS` with a rank and a trigger in `stepExpression()`, drawn in `drawEye()` / `drawMouth()` / `drawDotFace()`. `tests/character.test.ts` covers the settings, the geometry, the state machine, the eye-tracking maths, the blink schedule's determinism, the squash maths, the tracker (also on a real run), seeded Classic and Shatter runs through the `FaceLayer` (how often the face winces, is shocked and blinks, and how often the cat chirps) and the chirp; the smoke test checks the panel, the URL, the face and the label on the canvas, the emoji overlay option, the Bouncing Shapes bodies, the expression mix in Classic (mostly neutral, a minority of ouch) and Shatter (not stuck in shock) and the chirp (fewer than the bounce notes) in the served export.
### Themes and backgrounds
One-click looks, kept out of the physics entirely (nothing here changes a seeded run):

- **Data and merge** (`src/lib/themes.ts`): `THEMES` holds the curated looks – `id` (part of shared links, never rename one), `nameKey` (`Controls.theme<Name>` in every message file), `circleColor`, `ballColor`, `ballColor2`, `lineColor`, `background: { type: "solid" | "gradient", colors: [top, bottom] }`, `trailColors` and `particleStyle`. `applyTheme(settings, id)` is a pure merge – `{ ...settings, ...themePatch(theme, settings) }` – that also switches the rainbow walls / ball / lines off (so the colours show) and keeps an uploaded picture as the background; nothing else is touched, so every colour stays editable. `isThemeIntact()` tells whether the look still matches its theme (the card shows "edited" otherwise), `plainLookPatch()` is the Default card (the look fields of the mode's defaults), `themeCarryOver()` is what a mode change keeps (the background, particle style and trail colours, plus a picked theme's colours) and `particlePalette()` gives the bursts the scene's colours while a theme is picked. To add a theme, append an entry to `THEMES` and its name to every `messages/*.json`; `tests/themes.test.ts` checks its colours and names.
- **Settings**: `themeId` (URL `theme`), `backgroundType` (`bgt`: `solid` | `gradient` | `image`), `backgroundColors` (`bg1`, `bg2`), `backgroundDim` (`bgd`, 0–1), `particleStyle` (`ps`) and `trailColors` (`trc`, two colours or empty for the rainbow). `defaultThemeSettings()` reproduces the old canvas exactly (solid `#0a0a0a`, confetti, rainbow trail), `writeThemeParams()` / `readThemeParams()` are called from `settingsToSearchParams()` / `settingsFromSearchParams()` and `resolveThemeSettings()` from `presetToSettings()`. The picture itself stays in the page state as a `data:` URL: links never carry `bgt=image` (the reader only accepts solid / gradient), presets keep the type and fall back to the solid colour until a picture is loaded again.
- **Drawing** (`components/simulator/themeRenderer.ts`): the canvas still fills its solid colour first (`backgroundColor` = the first background colour); `BackgroundPainter.paint()` then draws the gradient (cached per size and colours) or the picture (cover-fitted into a device-pixel layer with the dim baked in, rebuilt only when the picture, the size or the dim changes), before the reactive-background flashes, so those still land on top. For exports, `CanvasHandle.paintRecordingBackground()` is handed to the recorder as its `drawBackground` option: `paintExport()` maps the canvas background through the crop, so the gradient meets the cropped square seamlessly and the letterbox bars take its end colours, and a picture fills the bars with a blurred, darker copy of itself. `trailColorTable()` turns the two trail colours into a 64-step cosine cycle of ready-made `rgb()` strings that replaces the rainbow hues of the colour trail (`drawThemedTrail()`), and `drawStyledParticle()` draws the styled particles – no allocation per frame.

### Team balls with scoreboard
The "which one wins" format – several balls, each one a team, a live scoreboard and a winner. Only the ball count reaches the physics (as "two balls" did before it); everything else is counted or drawn beside it, so a seeded run replays exactly with or without teams (the trajectories recorded in `tests/extras.test.ts` still match, and `tests/teams.test.ts` checks that a ball count of one and two replays the one-ball and the old two-ball runs exactly).

- **Several balls** (`src/lib/physics/ballStats.ts`): `MULTI_BALL_MODES` (Classic, Multiply, Lines, Grow, Shatter and Color Match – whose balls share the colour to match) start `startBallCount(config, mode)` balls: `PhysicsConfig.ballCount` (1 – `modeBallCap(mode)`) when the page sets it, else two with the old `twoBalls`. The cap is six (`MAX_TEAMS`) except where `MODE_MAX_BALLS` says otherwise: Grow grows every ball to about the radius of its sealed ring, so three or more balls crush each other through it (and the rest jam), and it keeps its old limit of two – one- and two-ball Grow runs replay exactly as before. `activateMode()` spawns them from the centre, the first one in the seeded random direction and the others spread evenly around it (`startBallAngle()`: the second of two flies straight back, exactly as before; no extra random draws), coloured by slot (`startBallColor()`: the ball colour, the second ball colour, then `EXTRA_BALL_COLORS`). Every starting ball carries its slot in `Ball.team`; Multiply's new balls and the halves of a split inherit it, and `setConfig()` recolours only slot 0 with the ball colour (slot 1 with the second colour), so the other slots keep theirs. `engine.setBallCount(n)` is the live change the page makes when the slider or the roster changes: it removes the balls of the slots beyond `n` (down to one: only the first ball, as the switch did) and adds the missing slots at the first ball, flying off in their start directions.
- **Per-ball stats**: the engine owns a `BallStatsBook` and records into it where things already happen – a rebound in the wall collision (a bounce), `reportWallBreak()` (the engine's own gap pass, Multiply's escapes and Shatter's segment breaks: a wall), the optional `ModeContext.creditWallBreak()` (Color Match's matching segments, which must not split balls) and `scanEscapes()` once per step after the mode's `onPostUpdate()` (a ball beyond the outermost wall's live radius – with breathing walls, where the pulse has it in that step – plus its radius and `ESCAPE_MARGIN`, has escaped; each ball once, and the half of an escaped ball inherits that). The live radius is what Multiply (+ `ESCAPE_MARGIN`), Shatter (+ 20 px) and Color Match (+ 30 px) test in their `onPostUpdate()` just before the scan, so the escape that ends a run is always counted in the step that ends it or earlier, and the frozen scoreboard and the winner never miss it. `getBallStats(id)`, `getTeamStats()` (six totals, reused objects), `hasBallEscaped(id)` and `getStatsGeneration()` (bumped by every restart) read them; nothing here draws a random number or moves a ball.
- **Settings** (`src/lib/teams.ts`): `ballCount` (URL `nb` above two; two is still `two=1`), `teams` (the roster: `{ name, color, emoji }[]`, at most six, URL `teams=name*rrggbb*emoji,…` with `%`, `*` and `,` percent-escaped inside a field), `showBallNames` (`tn`), `showScoreboard` (`tsb`) and `scoreboardPosition` (`tsp`: `top-left` | `top-right`). `writeTeamParams()` / `readTeamParams()` are called from `settingsToSearchParams()` / `settingsFromSearchParams()` and `resolveTeamSettings()` from `presetToSettings()` (a preset from before the ball count keeps its two balls). A roster sets the ball count to its size (`effectiveBallCount()`, capped by the mode's `modeBallCap()`, is what the engine and the finder get; a bigger roster than Grow takes keeps its teams, and the first two play there), `ballCountPatch()` / `rosterPatch()` keep the count, `twoBalls` and the roster in step, and `teamCarryOver()` takes the roster (and its balls) along when the mode changes.
- **Ranking**: `compareTeamStats()` – most escapes, then most walls broken, then most bounces, then the earlier first escape; `rankTeams()` sorts without allocating (the scoreboard ranks every frame) and `teamResult()` names the winner or the teams tied for first place.
- **Drawing** (`components/simulator/teamsRenderer.ts`): `TeamLayer` gives team balls their colour and emoji sprite in the ball pass of `Canvas.tsx`, rings a ball whose body does not show its colour and writes each team's name above its first ball; after the HUD it draws the scoreboard (layout, fonts and fitted names cached per size) in a corner of the centred square the recorder crops – below the page's Restart / Pause buttons on a square canvas, flush in a recording – and, once `isSimulationFinished()`, freezes the stats, pops up the banner (lower when the mode shows its own banner) and throws screen-space confetti from typed arrays. `Simulator.tsx` holds the end screen back for `WINNER_HOLD_MS` (3 s) while teams play, which also keeps a recording running through the celebration: an export whose length (`recordingDuration`) runs out after the run finished waits for that hold (and the escape replay) instead of stopping – the stop is left to the `finished` effect, with `END_HOLD_FALLBACK_MS` as a backstop – and Find Simulation sets the length to the found run plus the 3 s. The canvas mirrors `data-teams`, `data-team-stats` (`bounces/walls/escapes` per team), `data-team-winner`, `data-team-labels`, `data-scoreboard` and `data-scoreboard-bottom` (where the scoreboard ends) for tools and the smoke test.
- **Panel** (`components/simulator/sections/TeamsSection.tsx`, search keys `TEAM_KEYS`): the "Teams & Scoreboard" section – the Teams switch (default teams with translated names, at least two), a row per team (colour, emoji field with a datalist of suggestions, name, remove), Add Team (up to `maxTeamsIn(mode)`: two in Grow, with a note that the first two teams play there), Ball Names, Scoreboard and its corner; `BallCountControl` is the Ball Count slider of the Ball & Physics section (its maximum is the mode's cap). Its reset clears the roster and keeps the balls.
- **Extending**: to let another mode start with several balls, check that its logic copes with them (shared state like Color Match's colour is fine; a mode whose balls fill the arena, like Grow, needs a cap in `MODE_MAX_BALLS`), add it to `MULTI_BALL_MODES` and report its wall breaks through `ctx.reportWallBreak()` (or `ctx.creditWallBreak()` when a split would be wrong there). `tests/teams.test.ts` covers the URL form, the validation, the settings and preset round trips, the ranking, the stats book and seeded runs of every multi-ball mode; the smoke test (section 14) loads a roster from a link, edits it, runs three teams to a winner at 8× and records the banner, checks that a breathing Shatter run ends with its escape on the scoreboard, that Grow plays two of four teams without an escape, and that Find + Record at 1× keeps the banner in the export.

### Cinematic camera
A rendering layer over every mode; nothing of it reaches the physics (`tests/camera.test.ts` drives seeded runs through the camera with everything on and compares every step with the plain run):

- **Settings and maths** (`src/lib/simulation/camera.ts`, pure): `CameraSettings` – `cameraZoom` (URL `cz`), `screenShake` (`shake`), `slowMoOnNearMiss` (`slow`), `slowMoFactor` (`slowf`), `slowMoMs` (`slowms`), `replayOnEscape` (`replay`); `DEFAULT_CAMERA_SETTINGS` is all off, `CAMERA_RANGES` is spread into `RANGES` and `resolveCameraSettings()` validates URLs and presets alike. The view is a `CameraView` (focus offset + scale): `stepCameraView()` eases the focus toward the first ball with the classic follow's 0.08 inside `followLimit()` (half the arena at 1×, more when zoomed, so a ball at the outer wall stays in frame) and the scale toward `zoomScale()` (1 → `MAX_CAMERA_SCALE` 2.2), reduced by `fitScale()` so a second ball stays in frame – with zoom 0 it is exactly the old camera follow – and `cameraTransform()` turns it into the canvas translate + scale. The shake is `shakeEnvelope()` (quadratic decay over `SHAKE_DECAY_MS`) × `shakeOffset()` (a deterministic ~13 Hz wobble whose direction turns by the golden angle from one break to the next), at most `MAX_SHAKE_FRACTION` of the shorter canvas side. The slow motion is `slowMoTimeScale()` (eases in over 60 ms, holds the factor, eases out over 250 ms) driven by `SlowMotion` (a window per near miss, extended by another one inside it, then `SLOW_MO_COOLDOWN_MS` before the next, so a run is never slow throughout). The replay constants are `REPLAY_WINDOW_MS` (2 s), `REPLAY_SPEED` (½), `REPLAY_POST_ROLL_MS` and `REPLAY_MODES` (the modes whose run ends with an escape).
- **Events** (engine): `engine.getWallBreakSerial()` counts every `"gap"` sound event – the engine's gap passes and the modes' breaks, teleports and segment breaks – and `engine.getNearMissSerial()` the director's near misses (`CinematicDirector.getNearMissSerial()`: a gap pass within four ball widths of a gap edge, counted by the same geometric test whether the director is on or off, without drawing a random number). Both only ever grow; the camera polls them once per frame, however many steps the frame ran.
- **Replay buffer** (`src/lib/simulation/replay.ts`): `ReplayBuffer` keeps ~2.5 s of steps in typed arrays allocated once – position, radius, id, sprite angle, team slot and colour of up to 24 balls, rotation and radius of up to 32 walls, the broken-wall mask and the wall-break count – and `sample(t)` rebuilds the scene at any moment into pooled objects (balls matched by id and interpolated between two steps, rotations the short way round, a trail per ball from its recorded positions), so neither recording nor replaying allocates per frame. It freezes `REPLAY_POST_ROLL_MS` after every ball got outside the outer wall, so Classic – whose run only ends once the ball is far off-screen – replays the escape, not the flight.
- **Canvas** (`components/simulator/cameraRenderer.ts`, `CinematicCamera`, one per draw loop): `timeScale()` multiplies the time the canvas feeds the fixed-step engine – the engine still runs the same 60 Hz steps, so a slowed run is the same run, and the recorder, which copies real-time frames, exports the slow motion; `afterStep()` records each step (and, while the slow motion is switched on in a ring mode, keeps the step before it in a `StepInterpolator`, `src/lib/simulation/stepInterpolation.ts`); `slowView(engine, alpha)` hands the draw pass the balls (by id, with their live look and a trail whose newest point follows them), walls and rotations `alpha` – the canvas' leftover accumulator ÷ one step – of the way between the last two steps, from typed arrays and pooled objects like the replay: at 0.2× a step comes only every fifth frame, and the raw positions would stand still for four frames and jump (a 12 fps stop-motion in the export too). It draws one step behind the engine all the time the switch is on, so opening or closing a window never jumps the view by a step; a ball that moved more than `INTERP_SNAP_PX` in one step (a teleport) is drawn where it is, and the rhythm modes, which draw their own bodies, keep the engine's positions (`SLOW_VIEW_MODES`); `frame()` kicks the shake on new wall breaks, starts the slow motion on new near misses and, when a replay mode finishes, holds on for the post-roll (`postroll`) and plays the window at half speed (`playing`; a wall that breaks inside it shakes the view and bursts its particles again through `spawnWallBreakByStyle` – visual only, particles never use the seeded generator); `replayView()` hands the recorded walls, rotations, broken set and balls to the draw pass instead of the live ones (mode overlays such as Shatter segments or portals keep their live state, the mode banners wait); `applyView()` replaces the classic follow whenever zoom, shake or the replay need the view and hands back to it without a jump; `drawOverlay()` draws the REPLAY badge (blinking dot, label, speed, progress) in screen space, centred at the top of the square the recorder exports – at its bottom when a top text is set or the teams' scoreboard is shown (below the scoreboard when a bottom text is set as well) – so exports have it. `CanvasHandle.holdsEndScreen()` lets `Simulator.tsx` hold `finished` back – the end screen and the recording's stop – until the replay is over; with teams the winner banner (`TeamLayer.drawOverlay()`'s `holdBanner`) and its 3 s hold only start after it. The canvas mirrors `data-camera-replay` (idle / postroll / playing / done), `data-camera-scale`, `data-camera-time-scale`, `data-camera-shakes`, `data-camera-slow-mo`, `data-camera-replays`, `data-camera-slow-frames` and `data-camera-slow-still` (slow-motion frames drawn, and those that drew the first ball where the frame before did) for tools and the smoke test.
- **UI**: `sections/CameraSection.tsx` is the "Camera" group of the Visual section, under Camera Follow (zoom, shake, the slow-motion switch with its speed and length, the replay switch with a note outside the escape modes), exporting its search keys (`CAMERA_KEYS`); the Visual section's reset turns it all off and a mode change resets it like Camera Follow. The badge text is `Simulator.canvasReplay`, the labels live under `Controls` in every `messages/*.json`.
- **Tests**: `tests/camera.test.ts` covers the settings (defaults, clamping, URL and preset round trips), the zoom and follow maths (zoom 0 equals the classic follow frame for frame), the shake, the slow motion, the replay buffer (interpolation, ring wrap, trails, ids, walls, freezing, no allocation), the slow motion drawn between steps (`StepInterpolator`: interpolation, ids, teleports, the ball cap, walls, no allocation; and a seeded Classic run at 0.2× and 0.4× in which the drawn ball moves in every slowed frame while the engine's positions stand still in most of them), the engine events, determinism (Classic, Shatter and Portal) and the replay of real Classic and Accumulation escapes; the smoke test (section 15) drives the controls, the URL and the search, a zoomed, shaken and slowed run (whose ball moves in every slowed frame), and a recorded 8× escape whose replay plays before the export and the end screen; section 16 runs three teams with the replay (team names on the replayed balls, the winner banner after it).
### Multipliers
Stackable stat boosts for every mode, pickups in the ring modes and a board mode built on them. Everything that touches the physics draws from the engine's seeded RNG and runs in the fixed steps, so seeds, recordings and the finder replay exactly; with the settings at their defaults nothing changes (`tests/extras.test.ts` still reproduces every mode's recorded trajectory).

- **The stats** (`src/lib/physics/multipliers.ts`): `Ball.mult` (optional – absent is a plain ×1 ball) holds `speed`, `size`, `damage`, `bounce` and `gravity`. `applyMultiplier(ball, stat, factor, cap)` stacks a factor multiplicatively (`stackMultiplier()`, clamped to [1/cap, cap] – Infinity unless `mpUnlimited` is off and `mpCap` > 0 – and to a float-safety ceiling of 10¹⁵) and applies it: speed scales the velocity, size the radius and `radiusScale` (so a Ball Size change keeps it), gravity the ball's `gravityScale`. Where the others act: `cruiseSpeed()` is the ring modes' cruising speed (the engine's rebound speed, the slow-ball boost, Grow's and Accumulation's re-normalisation, Multiply's children – who also inherit the multipliers; while multipliers are in play Multiply stops spawning them at `MULTIPLY_MAX_BALLS_WITH_MULTIPLIERS` (200) balls, since inherited speed makes every escape come sooner and the count would explode), `hitDamage()` is what one hit takes off anything with hit points (Shatter's `segment.hp`, Target clears that many numbers per correct hit, the board's blockers, Glass Smash's panes), `effectiveBounce()` multiplies the restitution of the engine's rebounds and of obstacles (capped at `MAX_EFFECTIVE_BOUNCE` = 1.5; rebounds a mode sets itself – Portal, Grow – keep theirs) and `smashesWalls()` lets a ball whose damage reached `wallSmashThreshold` break a ring on contact in the escape modes (`SMASH_MODES`) – `engine.smashWall()` runs the wall-break effect, the "gap" sound, the split reporting and the director like a gap pass would. A grown ball is refitted by `fitBallToRings()`: moved radially clear of the rings of its corridor, bursting a ring it no longer fits inside, and – bigger than the outermost intact ring – "outgrowing" the arena: `MultiplierRuntime.outgrow()` stops the physics (`engine.update()` only moves the confetti from then on), `isSimulationFinished()` reports the end and the canvas shows the banner – which `Simulator.tsx` holds on screen for `MULT_FINISH_HOLD_MS` (2 s; `engine.endsWithMultiplierFinish()`, like the teams' winner banner) before the end screen covers it, so a recording keeps it too. A corridor that is too narrow even for the ball's un-multiplied size (many rings on a small canvas) is left as the engine always handled it.
- **Physics safety**: while multipliers are in play (`MultiplierRuntime.isActive()` – pickups on, the board mode, or any multiplier applied this run) the engine plans every 60 Hz step with `planStep()`: the bound on each ball's speed (its speed, or the fastest rebound the rings may give it, times `SPEED_MARGIN`, plus one step of gravity) over `maxMovePerSubStep()` (half its radius, at most `MAX_MOVE_PX` = 4 px) gives the sub-steps the step needs; up to `MAX_SUBSTEPS` (64) the step takes that many, beyond it `planForRatio()` halves the step until 64 suffice (**time dilation**: the simulation clock – `getElapsedMs()`, wall rotation, timers – runs slower and the HUD shows SLOW-MO x½, x¼ …). Multipliers change at step boundaries only (touched orbs and gate passes are queued and applied at the end of the step), so a plan always covers the speeds its step runs with. The swept obstacle and breathing-wall tests stay as they were on top. With more than `HASHED_PAIRS_FROM` (64) balls in a multiplier run the engine's ball-to-ball pass takes its pairs from a `SpatialHash` (the grid covers the canvas and a margin, far-flung balls are clamped into its border cells) instead of the n²/2 pair loop, which up to 64 sub-steps a step would multiply; every other run keeps the pair loop and its exact trajectories. `tests/multipliers.test.ts` proves the guarantees: a ball at ×1000 speed in Classic (and a two-ball run) never ends up outside an intact ring except through a gap or a smash, balls grown up to the arena stay inside their rings until the outgrow finish, the planner never exceeds its limits, and runs with multipliers are deterministic.
- **Pickups** (`MultiplierRuntime.stepPickups()` / `touch()` / `endStep()`, `PICKUP_MODES`): once per step the runtime schedules orbs `pickupInterval()` apart (0.5–1.5 × 10 s / `pickupRate`), places them inside the corridor of the first ball (`ballCorridor()`), drifts them off the corridor's rings and lets them fade after `pickupLifetime`; every sub-step each ball checks the few orbs afloat. At the end of the step a taken orb stacks its `PICKUP_FACTORS` entry through the cap (x2 BALLS clones the ball with a seeded turn, within the ball interaction's `maxBalls`, and calls the mode's `onBallSplit()` so Multiply marks the clone of an escaped ball), spawns a burst and queues a `"multiplier"` sound event carrying the new total. `ToneGenerator.playMultiplier()` (`src/lib/audio/multiplierTones.ts`) plays the rising arpeggio of `multiplierArpeggio()` – more notes and a higher root the bigger the stack – the way a bounce plays: the next slice while the slicer runs, the hit sample transposed per note in sample mode, otherwise the bounce instrument (a loaded melody roots it on its next note, with the melody voice), snapped to the scale, on the beat grid, ducking the music bed.
- **The Multipliers mode** (`src/lib/physics/modes/multipliers.ts`, id `multipliers`, escape family): `generateBoardLayout()` draws the rows from the seed (2–4 slots, gate kinds weighted by `mpGateMix` – six digits for count, speed, size, damage, reverse, release –, factors from `gateFactor()`, blockers with 3–8 hit points, bumpers, funnels) and `placeBoard()` lays it out in the centred square the recorder crops to, growing downwards (obstacles from `obstacles.ts`, bucketed into one band per row). The board is private to the mode: `onBallStep()` resolves each ball against the side walls and the obstacles of the bands it overlaps with `resolveBallObstacle()`, detects the gate line it crossed (each row once per ball) and the HOME line; `onPostSubStep()` resolves ball-to-ball contacts with the Collision Playground's `SpatialHash` (masses ∝ radius², damped restitution so the piles on the release doors settle); `onPostUpdate()` applies the step's gate passes (count gates clone within `mpMaxBalls` – the clones inherit the velocity with a seeded turn and scale, the multipliers and the row; speed / size / damage gates go through `ctx.getMultipliers()`; ÷2 gates absorb every second ball), removes arrivals in place, nudges a ball that has not got lower for 2.5 s (a wait on a door counts at a quarter; after 15 s a ball is lost, so every run ends), eases the camera (`view.cameraY`, simulation-timed) toward the lowest ball and finishes when the board is empty – with "N Boris made it home", which the page holds for `MULT_FINISH_HOLD_MS` before its end screen (Find Simulation adds the hold to the export length). Release doors open on their own clock and only close once no ball is half-way through. Notes: every hit plays the pentatonic "plinko piano" pitch of its x position (`boardPitch()`), count gates, doors and arrivals their own notes, at most `MAX_SOUNDS_PER_FRAME` per rendered frame (the most energetic, like the Collision Playground) plus one arpeggio for the biggest stat stacked. Settings `mpRows` (URL `mprw`), `mpGateMix` (`mpgm`), `mpStartBalls` (`mpsb`), `mpMaxBalls` (`mpmb`), `mpTarget` (`mptg`); a change restarts the board. With a target the finder (`findByCount()` in `finder.ts`) tests one seed per frame until the final HOME count is within 5 % of it (`countTolerance()`) and the page shows the count; without one it searches by duration like any mode.
- **UI**: `components/simulator/multiplierRenderer.ts` draws the board (gate bands and labels that flash on a pass, pegs, bumpers, funnels, blockers with their hit points and cracks, doors with their countdown, the HOME zone), the balls batched (one path per colour, one stroke for the speed streaks and one for the damage rims), the pickup orbs and the HUD – the stat badges in the top left of the recorded square (they pop and glow on the simulation clock when a value changes; with teams they start below the scoreboard in its default top-left corner, and wrap before it – SLOW-MO moves below it – in the top right: `TeamLayer.scoreboardRect()` says where it will be drawn), SLOW-MO in the top right, the live HOME counter – and mirrors the state into `data-mult-*` attributes (`multSpeed`, `multSize`, `multDamage`, `multBounce`, `multGravity`, `multBalls`, `multPickups`, `multOrbs`, `multSmashes`, `multSlowmo`, `multOutgrew`, and on the board `multHome`, `multActive`, `multClones`, `multGates`, `multDone`). The panel blocks are `sections/MultipliersSection.tsx` (the "Multipliers" group of the Ball section: pickups, rate, kinds, lifetime, unlimited / cap, smash threshold) and `sections/MultipliersModeSection.tsx` (the Mode row of the board: rows, start balls, max balls, gate mix, target count). The stat settings travel in `PhysicsConfig` (`multiplierConfigOf()`, resolved by `resolveMultiplierConfig()` in `setConfig()`), so the finder's headless engines get them with the config; URL keys `mpu`, `mpc`, `wst`, `mpk`, `mpr`, `mpty`, `mpl`.
- **Tests and smoke**: `tests/multipliers.test.ts` covers the stacking maths without and with a cap, the formatting, the planner and the dilation, the ring fit, the smash threshold, the outgrow finish, pickups (seeded spawns, touches, clones within the cap, the arpeggio event), Shatter / Target damage, determinism and the settings; `tests/multipliersMode.test.ts` the layout, the gate maths and cloning caps, the spatial-hash pairs against brute force, arrivals, the finish, the camera, determinism, the count finder and the settings. The smoke test checks that pickups in Classic change the HUD badges, that the board counts arrivals home and holds "made it home" – and a size-orb run its OUTGREW THE ARENA – before the end screen, that the badges of a teams run start below the scoreboard live and in the export (`data-mult-hud-top`, `data-scoreboard-bottom`), that Multiply with speed orbs stays within 200 balls at a steady frame rate and that Glass Smash's gates stack multipliers on the ball; `tests/multipliers.test.ts` also holds Multiply's cap (and the frame budget of the speed-orb run that used to explode), the hashed ball pass against the pair loop and `endsWithMultiplierFinish()`.
- **Add a multiplier type**: add the stat to `MULTIPLIER_STATS`, `unitMultipliers()` and `copyMultipliers()`, apply it in `applyMultiplier()` (if it changes the ball at once) or read `ball.mult.<stat>` where it acts, and keep that path behind a `ball.mult` check so plain balls are untouched; for an orb add a `PICKUP_KINDS` entry with its `PICKUP_FACTORS`, `PICKUP_STATS` and `MULTIPLIER_COLORS`, a word in `MultiplierLabels` (`Simulator.canvasMp<Name>`) and `Controls.pickupKind<Name>` in every messages file; for a gate add it to `GATE_KINDS` (one more digit in `mpGateMix`), `gateFactor()`, `GATE_COLORS` / `gateLabel()` in the renderer, the effect in `MultipliersMode.onPostUpdate()` and `Controls.gate<Name>`; for a HUD badge add it to `BADGES` and the view's summary (`MultiplierRuntime.summarize()`), and cover the maths in `tests/multipliers.test.ts`.

### Rebrand
Change `SITE_NAME`, `SITE_DOMAIN` and the accent colours in `src/lib/site.ts`, the theme tokens in `src/app/globals.css`, and `public/icon.svg`.

## Browser support

Chrome, Edge and Safari export MP4; Firefox exports WebM. Recording uses `canvas.captureStream()` and
`MediaRecorder`, so it needs a recent desktop browser. The simulator itself runs anywhere `<canvas>` and
Web Audio are available.

## Notes

- The tool is free of external runtime dependencies beyond Next.js, React and next-intl.
- Uploaded images, MIDI files and sounds never leave the browser.
- Melodies shipped in `public/notes` are short public-domain themes generated from note lists in `scripts/generate-midi.py`.
